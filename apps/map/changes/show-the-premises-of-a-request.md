# リクエストが読む保存済みの情報と、それを保存したリクエストを地図で読む

フローの「リクエスト」欄は、`/token` のように OP が先に保存した情報を使うリクエストについて、その上に、そのリクエストが地図の OP で読んだ記録（認可コード、リフレッシュトークン、クライアントなど。見つからなかったものも）を並べる。
記録を開くと中身と、それを保存したリクエスト（認可リクエスト、ログイン、同意、引き換え）を、送った値と書いた記録とともに出す。
実行すると、応答の下にそのリクエストが保存・変更・削除した記録を出す。
「地図の OP が持っているもの」は、設定で登録したものと、前提を作ったリクエストとその値を並べる。

この変更は地図とその解析、地図の OP（`packages/map-sandbox`）、テストカタログだけを変え、関数カタログの関数とエンドポイントの処理は変えていない。

## 背景

リクエストを書いて実行できるようになったが、`/token` のリクエストが通る道筋は、OP がどんな認可コードやトークンを保存しているかで決まる。
これまでの前提はテストの fixture を DB に直接書いたもので、どのリクエストで保存されたかは無く、中身もテストの都合（どのコードも同じ grantId、DB に無いユーザー `user-1`）で、OP が自分で保存するものと食い違っていた。
前提を、それを作るリクエストを地図の OP で動かして作り（`prepare.ts`）、リクエストが読んだ記録と書いた記録を DB で観測する（`store.ts`）ようにしたので、画面に出すものはどれも観測したもので、説明の文章を書き足していない。
ブラウザはページが作るリクエストの Cookie と Origin、応答の Set-Cookie を落とすので、前提はビルドが Node で作り、ページはそれを Web Worker の OP に渡す。

## 残ること

- DB の外に記録を持つ機能（PAR、デバイスコード、CIBA、動的クライアント登録）の記録は読めず、リクエストごとにも戻らない（地図の OP の Worker の中で残る）
- テストの画面では、テストが送ったリクエストの前に OP が持っていた記録は出ない。テストは記録を DB に直接書くので、出すにはテストの実行で DB の読み書きを記録する仕組みが別に要る
