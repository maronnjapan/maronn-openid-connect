# 前提の認可リクエストやクライアントを書き換えて、トークンエンドポイントのフローを確かめる

フローの「地図の OP が持っているもの」で、前提のグラントの認可リクエスト（`scope`、`prompt`、PKCE など）と、コードを引き換えるかどうか、クライアントの認証方式と `grant_types` を書き換え、前提を作り直せるようにした。
作り直しは地図の OP がページの中で前提のリクエスト（認可リクエスト、ログイン、同意、引き換え）を動かし直して行い、以後のリクエストはその上で動く。
あわせて、ケースを通るリクエストが見つかっていないケースに、ほかのケースのリクエストを出さないようにし、`/token` の「トークン交換」には、前提のアクセストークンを交換する、実際にそのケースを通るリクエストを見つけるようにした。

この変更は地図、地図の OP（`packages/map-sandbox`）だけを変え、関数カタログの関数とエンドポイントの処理は変えていない。

## 背景

`/token` の振る舞いの多くは、先に保存されたもの（コードの `scope`、クライアントの登録）で決まる。
リフレッシュトークンのありなしを確かめるには、認可リクエストやクライアントの登録を変えた前提が要るが、前提はビルドが作ったものに固定されていた。
ページの中では、ブラウザがリクエストの Cookie と Origin、応答の Set-Cookie を落とすため、ログインと同意が通らず、前提を作れなかった。
地図の OP が、リクエストには全部のヘッダーを持たせ、応答を作るときの Set-Cookie を控えるようにして、ページの中でも前提を作れるようにした。

`offline_access` を外しても、この OP はクライアントが `refresh_token` を登録していれば、ログインセッションに結び付いたリフレッシュトークンを発行する（`decideRefreshTokenIssuance`）。
作り直した前提で動かすと、それが記録（`sessionId` の付いたリフレッシュトークン）として見える。
