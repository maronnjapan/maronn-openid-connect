# 書き換えたリクエストが、書き換える前と道筋が分かれる関数までフローが入る

地図のフローの「リクエスト」で、ケースが準備したリクエスト（か、開いたリクエスト）を書き換えると、フローは、書き換える前のリクエストと分岐の側が違う関数まで呼び出しを開き、再生をその最初の場面へ移すようにした。
結果の欄には、分かれる所を、関数、分岐、それぞれの側で並べる（「`resolveIntrospectionToken()` `if (at)` → 不成立（書き換える前は 成立）」）。関数の名前を押すと、その場面へ移る。
書き換えても分岐の側がどれも同じなら、「書き換える前のリクエストと同じ道筋を通ります」と出す。

この変更は地図のページだけを変え、関数カタログの関数とエンドポイントの処理は変えていない。
二つのリクエストの記録を読み比べること（`followTrace` の `against`）と、歩みが `continue` と `break` で繰り返しを抜けることは、`packages/map-analysis` に先に足した。

## 背景

イントロスペクションで「有効なアクセストークンを確認する」のケースを選び、`token` を発行されていない値に書き換えても、右のフローは書き換える前と同じだった。
書き換えたリクエストは試算していて、応答は `{ "active": false }` に替わっていた。
しかし、エンドポイントの根は、トークンが見つかっても見つからなくても同じステップを通って 200 を返す。
違うのは、ステップが呼ぶ関数の中（トークンを探す `resolveIntrospectionToken` と、有効かどうかをまとめる `describeIntrospectedToken`）の分岐の側で、フローが自分から開くのは失敗した呼び出しだけだったので、フローチャートには何も出なかった。
結果の欄も、ステータスが同じ 200 で、ボディは畳んであり、「ケースが期待する応答」には「✓ ステータスと OAuth のエラーは期待どおり」と出ていたので、書き換えた値が使われていないように見えた。

## 何を変えたか

- 書き換えたリクエストを試算するときに、書き換える前のリクエストも同じ状態のコピーで試算する（一度の書き換えで `POST /__live/preview` は二つ）。前に試算した記録と比べないのは、その間にワークスペースの状態が変わっていると（認可コードを使った後など）、書き換えのせいでない違いが出るからである
- 二つの記録を読み比べて、側が違う関数まで呼び出しを開く。開いた呼び出しは、これまで失敗した呼び出しを開いていたのと同じに、次の試算で閉じる
- 再生は、分かれる最初の場面へ移る。これまでは「いまの場面にとどまる」としていたが、根のフローチャートは変わらないので、とどまると何も変わって見えなかった。分かれないときは、これまでどおりとどまる
- 呼び出しが閉じて、いた場面が無くなったときは、その関数を呼んだ場面へ移る（これまでは同じ番号の場面で、たいてい最後の場面だった）
- 書き換えたリクエストを実行したときも、送る直前に書き換える前のリクエストを試算して、同じように読み比べる。再生は、これまでどおり最初から始める
- 「ケースが期待する応答」と比べるのは、ケースが準備したリクエストの応答だけにした。比べるのはステータスと OAuth のエラーだけなので、書き換えたリクエストの `active: false` の 200 に「期待どおり」と出ていた
- 読み比べに要る木は、呼び出しを開かなくても読み込む（`RequestRun.needs`）。開くかどうかは、その木の分岐の側を読まないと決まらないからである

## 残ること

- 空欄から書いたリクエストと、ケースを選んだだけのリクエストには、書き換える前が無いので、読み比べない。「発行されていないトークンを確認する」のケースを選んだだけのフローは、有効なトークンのケースと同じ根のステップである（「一段深く」で中を通せる）
- 試算が開いた呼び出しは、失敗した呼び出しと同じく URL のハッシュに残る。再読み込みすると、読者が開いた呼び出しとして開いたままになる
- 分岐の側が同じで、式の中のオペランドや繰り返しの回数だけが違う関数は開かない。地図のフローチャートが二つのリクエストで同じだからである
- 一度の書き換えで試算が二つになる。書き換える前のリクエストの試算が届かなかったときは、読み比べずに、書き換えたリクエストの道筋だけをたどる
