# 設計案: 経路をたどる地図

PR の地図（`apps/map`）を、次の二つの目的から組み立て直す設計案である。

- エンドポイントから何段下の関数で起きた変更でも、何を変えたかと差分のコードを、その場で読める
- 関数とエンドポイントの処理の流れで、条件分岐が正しく分かれ、読者が分岐を選んで追える

この改訂では、既存の実装を活かすという前提を外した。
いまの作りを部分的に直す案は末尾の「縮小案」にまとめ、本文では目的に対して最短の形を述べる。
実装はまだ行っていない。

## 現状の計測

提案の根拠として、全機能オンでビルドした `map.json` を測った（2026-11、`main` 相当）。

| 観点 | 計測結果 |
|---|---|
| ステップの下の関数の深さ（hono） | 3 段以上のステップが 31 個、最深 7 段（`consent/issue-hybrid-response`、下に 55 関数） |
| 変えた行が図の箱に対応する割合 | 関数の宣言から本体の終わりまでの行のうち、箱が指す行は 25%（21,901 行中 5,533 行） |
| ケースが exit ケースに畳まれる関数 | 1,017 個中 52 個 |
| `/token`（hono）のケース | 条件 6 個で exit ケース 27 個。成功の終わりが 6 個、残り 21 個はステップごとのエラー応答 |
| `/authorize`（hono）のケース | 条件 8 個で exit ケース 27 個 |
| `verifyIdJagAssertion` のケース | 条件 45 個で exit ケース 23 個。うち 22 個が `→ throw invalidAssertion(…) (n)` と番号だけが違う |

README は「`/token` なら `authorization_code` と `refresh_token`」をケースの例に挙げているが、全機能オンの `/token` ではこの二つを選べない。
`refreshTokenRequest ?? (await validateAuthorizationCodeGrant(…))` の分岐は読めているのに、道筋が上限の 24 本を超えて exit ケースに畳まれ、どちらも `→ return respondToken(…)` になるからである。

## いまの作りが目的と合わない理由

症状は上の表のとおりだが、直すべきは症状ではなく、次の四つの設計上の選択である。

**流れを平らなグラフにしてから、ケースを道筋の列挙で取り戻している。**
読み取りの時点では「この `if` のどちら側か」という入れ子の構造が分かっている。
それを箱と矢印に平らにした時点で捨て、画面側で開始から終わりまでの道筋をすべて列挙して分岐を取り戻そうとする。
独立した条件が n 個合流すれば道筋は 2^n 本になり、上限を超えると名前の無い exit ケースになる。
任意項目の代入 414 個とエラーの矢印の扱いは、この方式の中では症状として現れているにすぎない。

**読む単位が「関数のページ」で、変更は関数に付いている。**
差分とメモはその関数のページにだけ出るので、関数をまたいだ瞬間に名前の一覧へ退化する。
差分はテキストの hunk で、図との対応は「箱の行と変えた行が一致するか」しかなく、箱が指す行は 25% にとどまる。
残りの行の変更は、どの箱にも現れない。

**機能の組み合わせごとに流れを作っている。**
ステップを足す機能の組み合わせ（450 組）ごとにエンドポイントの流れを作り、矢印の集合（`edgeSets`）も別に持つ。
一本の木の各ノードに機能の札を付ければ、画面で絞るだけで済む。

**読み取りがコンパイラ無しの字句解析である。**
これは CLI の配布物が依存を持てないための制約だが、確認したところ、配布された CLI は関数の流れを使わない。
配布物の `functionProject()` は焼き込んだカタログを読み、`flowOf` は常に未定義を返す。
`explain` と `graph` のコマンドも流れを参照していない。
流れの読み取りの利用者は、リポジトリ内で動く地図のビルドだけである。
したがって、ビルド時に TypeScript のコンパイラ API で読む設計は、配布物の制約に触れない。
型による呼び先の解決、正確な行の範囲、三項演算子や論理代入やコールバックの扱いは、字句解析で近似する必要がなくなる。

## 新しいモデル

四つの柱で組み立てる。
**構造化フロー木**が流れの表現、**トレース**が関数をまたぐ画面、**木の差分**が変更の表現、**決定**が分岐の選び方である。

### 1. 構造化フロー木

関数の本体を、箱と矢印ではなく、文の入れ子をそのまま持つ木として読む。

- **呼び出し**（`call`）：カタログの関数、または resolver や store のメンバーの呼び出し。呼び先の id を持つ
- **処理**（`action`）：カタログの呼び出しを含まない文（代入、フレームワークの呼び出し、計算）。一行目は文の要約、連続するものは「処理 ×n」に畳んで表示する
- **条件**（`if`）：条件式、成立側の列、不成立側の列。`&&` と `||` は条件式の中の短絡として保つ
- **分岐**（`switch`）：判別式と、`case` ごとの列（フォールスルーを含む）
- **繰り返し**（`loop`）：ヘッダと本体。コールバックの中の呼び出し（`items.map((x) => f(x))`）も「各要素で」の繰り返しとして置く
- **例外の捕捉**（`try`）：本体、`catch` の列、`finally` の列
- **式の分岐**（`cond-expr`）：三項演算子、`??`、`||`、`&&`、論理代入で、腕に呼び出しを持つもの
- **終わり**（`return` / `throw`）と、本体の末尾への到達
- **ブロック**（`block`）：Next.js の Route Handler のステップの印（`// [step-id]`）で区切られた列。hono の pipeline ではステップの関数の呼び出しがこれに当たる

どのノードも、ソースの行の範囲（開始行と終了行）と、親からの位置で決まる id（`s3.then.s1` のような形）を持つ。
行の範囲は切れ目なく関数の本体を覆うので、変えた行は必ずどれか一つのノードに属する。
エンドポイントの木は、ステップを足す機能の名前をノードの札として持ち、機能の組み合わせごとに木を作らない。

いまの図（箱と矢印）は、この木を平らにすれば得られる。
いまの「ケース」が答えようとしていたこと（どの条件でどちらへ進むとこのノードに至るか）は、木の上では列挙なしに求まる。
あるノードに至る条件は、祖先の条件で選んだ側と、手前の兄弟のうち「成立すると終わってしまう守り」を不成立で通ることの組み合わせであり、木を一度たどれば出る。

### 2. トレース

読む単位を「関数のページ」から「エンドポイントを根とする、関数をまたいだ一本の経路」に変える。
これを**トレース**と呼ぶ。

トレースは**フレーム**の木である。
根のフレームはエンドポイントの木（pipeline の本体、または Route Handler）で、その中の呼び出しノードを開くと、呼び先の木が子のフレームとしてその場に展開される。
resolver や store のメンバーは葉で、インターフェースの JSDoc を出す。
すでに経路上にある関数への呼び出しは「再帰」の葉にして止める。

トレースの中では、次の操作が一つの画面で完結する。

- ステップの関数を開いて中の分岐を読み、さらにその中の関数を開く
- 「**変更まで展開**」で、そのフレームから届くすべての変更まで、間の呼び出しを一度に開く（深さと件数の上限付き）
- 変えたノードの行の差分を、そのノードのすぐ下、または右側の差分欄で読む
- どのフレームも「このフレームを根にする」で、関数のページとして切り出せる

画面は左右二段にする。
左は**アウトライン**で、木を字下げした行として縦に読む（コードの構造をそのまま追う形）。
右は図で、焦点のフレームの木を平らにした箱と矢印を描き、アウトラインで選んだ道筋を青にする。
いまの図の配置と三色の規則は右側に残す。
狭い画面ではアウトラインと図をタブで切り替える。

開いているフレームと、後述する決定の選択は、ハッシュに書く。

```
#hono--token/s4/s4.s2;d=s4.s1:true,s12:refresh
```

`/` 区切りがフレームを開いた呼び出しノードの id、`d=` が決定の選択である。
いまの `#hono--token--authenticate-client` と `#hono--fn--<名前>` は、それぞれ「ステップを選んだトレース」「関数を根にしたトレース」として読み替える。

トレースの見え方を、`/token` で `verifyClientSecret` の 3 段下に変更がある場合で示す。

```
POST /token                                      決定: refresh_token ▾  □ エラー時
├ トークンリクエストを解析する  parseTokenRequest()
├ クライアントを認証する  authenticateTokenClient()                  下で変更 1
│  ├ if (authorization)                           成立
│  │  └ verifyClientSecret()                                        変更: 条件 +1
│  │     ├ + if (secret.length < MIN)             不成立            ← 足した条件
│  │     │    └ throw TokenError(invalid_client)                     （畳んである）
│  │     └ return timingSafeEqual(…)
│  └ …
├ ID-JAG を発行する  issueIdJag()                  不成立（続く）
├ …
├ validatedRequest = refreshTokenRequest ?? …     refresh_token あり
├ 署名鍵を選ぶ  selectTokenSigningKeys()
└ …
```

右側の差分欄には、展開したフレームの差分がトレースの順に並ぶ（後述の「経路の差分」）。

### 3. 木の差分

変更を「関数が変わった」という一つの札ではなく、木のノード単位の差分として持つ。

地図のビルドは、いまも変わったファイルの変更前のテキストを git から読んでいる。
そこで変更前の木も作り、変更後の木と突き合わせる。
突き合わせは、各列（兄弟の並び）で種類と要約（呼び先、条件式の正規化した文字列）が同じノードを順序を保って対応づけ、対応したノードの中へ再帰する。
結果は、変更後の各ノードに `追加` / `変更` / `同じ` の印、消えたノードは直前の対応したノードの後ろに「消した」ノードとして置く。

テキストの hunk は、ノードの行の範囲で切ってノードに付ける。
複数のノードにまたがる hunk は、それらを含む最小の親に付ける。
行の範囲が本体を覆うので、付け先の無い変更は生じない。

差分からは、言葉の要約を作る。

- 「条件 `secret.length < MIN` を足した」
- 「`a()` の呼び出しを `b()` に置き換えた」
- 「`return` を手前に足した（早期リターン）」
- 「引数を変えた（`issuedAt` を足した）」

呼び出しノードには、呼び先の下で起きた変更の集計を付ける。
「下で変更 3 件（条件 +1、呼び出し +2）」のように件数と種類を出し、開くと内訳が見える。
集計は深さを限って行い、再帰は一度で止める。

トレースの右側には**経路の差分**を出す。
展開しているフレームの hunk を、フレームの見出し付きでトレースの順に並べたものである。
レビューする人は、PR の差分をファイル順ではなく実行の順で読める。

宣言（引数と戻り値の型）の変更は開始ノードの変更として扱い、呼び出し側では呼び出しノードの引数のテキストが変わったときだけ `変更` を付ける。
変更メモ（`apps/map/changes/*.md`）の読み方と関数への対応づけは変えず、関数の見出しとして差分の上に出す。

### 4. 決定

ケースの列挙をやめ、**決定**の選択に置き換える。
決定は、木の中で道筋を分けるノード（`if`、`switch`、`cond-expr`、`loop` のヘッダ、`try` の `catch`）である。

アウトラインの既定の見え方は、コードと同じく全部を見せる形にする。
ただし、成立するとすぐ終わる守り（`if (!x) throw …`）は、その側を一行に畳み、本線が縦に読めるようにする。
`verifyIdJagAssertion` の 45 個の守りは 45 行の一行ずつになり、本線はその左を下りていく。

決定ごとに、どちらへ進むかを選べる。
`if` なら成立と不成立、`switch` なら `case` のラベル、`try` なら本体と `catch`、短絡なら「値あり」「null または undefined」である。
選ぶと、通らない側は一行の要約（「3 つの処理、`throw TokenError(invalid_client)` で終わる」）に畳まれ、右の図では灰色になる。
子のフレームの決定も同じ仕組みで選べ、経路全体で一本の道筋が決まる。

いまのケース欄に当たるものは、**よく使う選択**として木から計算して並べる。

- **終わり方**：`return` と `throw` のノードごとに、そこへ至る最小の決定の組み合わせ。名前は区別に要るラベルだけ（`/token` なら `exchanged: 成立`、`refreshTokenRequest: null または undefined` など）。守りを不成立で通った事実は名前に入れない
- **変更に至る道筋**：変えたノードごとに、そこへ至る決定の組み合わせ。フレームをまたぐ
- **ステップ**：エンドポイントなら、各ステップのブロックに至る決定の組み合わせ

これらは木をたどって求めるので上限が無く、exit ケースへの切り替えは無くなる。
複数を同時に選ぶと和集合になり、いまのチェックボックスの複数選択に相当する。

`??` と三項演算子のラベルは、条件式ではなく進む先の言葉を使えるようにする。
`refreshTokenRequest: null または undefined` は、進む先のブロックの見出しから `authorization_code グラントを検証する へ` と言い換えられる。

機能のオン・オフは、木のノードの機能の札で絞る。
オフの機能のブロックは木から外し、そのブロックが作る値を読む条件は「値なし」の側だけを残す。

### 失敗の流れ

関数が「どう失敗するか」を、JSDoc の `@throws` に頼らず木から求める。
`try` の外にある `throw` と、`try` の外で呼ぶ関数の失敗を合わせたものが、その関数から外へ出る失敗である。
カタログ全体でこれを不動点まで求め、各関数に「外へ出る失敗」の一覧を持たせる。

トレースでは「エラー時」をオンにすると、各呼び出しノードに「失敗すると → どこで捕まるか」を出す。
捕まる先は、トレースを上へ辿って最初に見つかる `catch`（`/token` なら根のフレームの `catch` と `respondTokenError`）である。
これで、3 段下の `throw TokenError(invalid_client)` が、どのエラー応答になって返るかを一つの画面で追える。
「終わり方」の選択にも、呼び先から伝わる失敗を「`TokenError(invalid_client)` で終わる（`verifyClientSecret` から）」として並べる。

## 画面

**エンドポイントの画面**は、エンドポイントを根にしたトレースである。
根のフレームの呼び出しノードがステップで、見出しにはステップのラベル、札には PR の変更の集計が付く。
いまの「ステップの詳細」の内容（受け取る値、次へ渡す値、仕様、失敗するとき）は、ステップのノードを選んだときに右の欄に出す。

**関数のページ**は、関数を根にしたトレースである。
「呼び出し元」欄は残し、そこから上の関数へ移るときは経路を捨てる（上へ向かう移動はトレースの定義に合わない）。

**このPRの変更**のページは、レビューの入口にする。
変わった関数ごとに、木の差分の要約、差分、変更メモ、そして「届く経路」（エンドポイント › ステップ › … と、そこに至る決定）を並べる。
届く経路を押すと、そのエンドポイントのトレースが変更まで展開され、決定が選ばれた状態で開く。
PR のコメントに書く Markdown にも、関数ごとに差分の要約と届くエンドポイントの id を一行添える。

**コードの Drawer**は残し、アウトラインの各行からその行へ飛べるようにする。
変わった関数には「差分 / 変更後の全文」の切り替えを足す。

## データとビルド

読み取りは、TypeScript のコンパイラ API を使う解析器に置き換える。
解析器は地図のビルド（`apps/map/scripts`）の一部として、各ルート（`packages/core`、`packages/experimental`、`packages/google-login`、`apps/hono`、`apps/nextjs`）の既存の `tsconfig.json` からプログラムを作り、関数ごとに木を出す。
呼び先の解決は型で行い、resolver や store のメンバーも受け取りの型から引く（名前の末尾で推定する規則は要らなくなる）。
関数の id はいまのカタログと同じ `<root>:<module>#<name>` にし、CLI のカタログ（`calls` と `calledBy`、`explain` が使う）と一致することをテストで確かめる。
CLI 側の字句解析による流れの読み取り（`extract/function-flow.ts`）は、地図が使わなくなった時点で消す。

出力は二層にする。

- `data/map.json`：エンドポイント、関数の札（名前、要約、呼ぶ関数、外へ出る失敗、変更の要約）、機能、変更メモ。木は含めない
- `data/functions/<id のハッシュ>.json`：関数の木と、変わった関数なら変更前の木、差分の印、ノードごとの hunk。トレースで開いたときに読む

これで初期の読み込みは小さくなり、`controlFlows`（3.7 MB）と `edgeSets` は無くなる。
エンドポイントの木は、ステップの印と機能の札を持つ一本だけである。

型と関数名の整理は次のとおり。

- `FunctionFlow`（平らな `nodes` と `edges`）は `FlowTree` に置き換える。図はビルド時ではなく画面側で平らにする
- `FunctionChange` には `hunks` の代わりに、ノード id をキーにした差分の印と hunk、言葉の要約、`treeBefore` を持たせる
- `MapChanges` と変更メモの扱いは変えない

## 捨てるものと残すもの

捨てるもの。

- 道筋の列挙によるケース（`deriveCases`、`exitCases`、`activeOf`、`CasePicker`）
- 機能の組み合わせごとの `controlFlows` と `edgeSets`
- 字句解析の流れの読み取り（`function-flow.ts`、`endpoint-flows.mjs`）
- 行の一致で札を付ける `nodeMark`、最短経路だけを返す `changesBelow`
- いまのハッシュの形（旧形式は読み替えて開く）

残すもの。

- 関数カタログ（`functions.ts`）と、CLI の `explain` / `graph`
- 変更の集め方（`changes.mjs` の git の差分、関数ごとの比較、変更メモの解析）。木の差分はこの上に足す
- 図の自動配置（Dagre）、三色の規則、札を灰色の濃淡で描く規則
- Shiki によるハイライトと、ソースをファイルごとに分けて置く仕組み

## 進め方

破壊的に変えてよいとしても、順序は要る。
前の段が後の段の土台になるように、四段に分ける。

1. **解析器と木**：TypeScript の解析器で全関数の木を出し、いまの平らな流れと（呼び出しの順、条件の数、終わりの数で）突き合わせるテストを書く。画面は木を平らにして今のまま動かす。ここで `controlFlows` と `edgeSets` を落とす
2. **トレースと決定**：アウトラインと決定の選択を入れ、ケースの列挙を消す。関数のページとエンドポイントの画面をトレースに統合する
3. **木の差分とレビュー**：変更前の木、ノード単位の差分、要約、経路の差分、「このPRの変更」の届く経路。過去にマージした PR をいくつか選び、その親との差分で地図を作って確かめる（`MAP_BASE=<親のコミット>` で手元に作れる）
4. **失敗の流れと仕上げ**：外へ出る失敗の計算、エラー時の表示、ハッシュの互換、スマートフォンの表示

第 1 段が終わった時点で、`/token` と `/authorize` のケースが名前付きで出ることを計測で確認する（いまの計測の指標を `scripts/` の検査として残す）。

## 縮小案との関係

既存の作りを活かすなら、次の部分的な修正で症状の多くは抑えられる（前回の案）。

- 任意項目の条件を一つの箱に畳み、エラーを「エラー時」の修飾に戻す。これで exit ケースになる 52 関数のうち 36 個が収まり、`/token` は 7 ケースになる
- 関数のページに経路（どのステップから来たか）をハッシュとパンくずで持たせ、経路に沿うケースを既定で選ぶ
- 下で変わった関数の一覧に差分を折りたたんで埋め込み、経由に分岐のラベルを添える
- 変えた行を「箱の行と一致」ではなく「箱が受け持つ行の範囲」で札にする

しかし、この修正では道筋の列挙の上限が残る（16 関数は収まらない）、関数をまたぐ読みは依然としてページの移動になる、箱の無い行の変更は「付近を変更」という弱い札にしかならない。
本文のモデルは、これらを木、トレース、木の差分でそれぞれ無くす。
縮小案の各項目は、本文のモデルの中では「決定の既定値」「変更に至る道筋」「ノードの行の範囲」として自然に含まれる。

## 決めてほしいこと

- アウトラインを主、図を従にしてよいか。いまの README は図を中心に据えている
- 解析器の置き場所。`apps/map/scripts` の中に置くか、`packages/` に独立させて CLI のビルドからも使うか
- 旧ハッシュの互換をどこまで保つか（読み替えて開ければ十分か）
- 木の差分の粒度。文単位で足りるか、条件式の中（`<` を `<=` に変えた、など）まで要るか
- 「変更まで展開」の深さと件数の上限
