# 設計案: 変更を深い関数まで追える地図と、分岐を正しく分けるケース

PR の地図（`apps/map`）に残る二つの問題を解消するための設計案である。
一つは、変更の説明と差分がエンドポイントから一段下の関数までしか見やすく届かず、階層が深くなると消える問題。
もう一つは、関数とエンドポイントの処理の流れで、条件分岐が「ケース」として正しく分かれない問題。
この文書は設計の提案であり、実装はまだ行っていない。

## 現状の把握

提案の前に、いまの地図がどこで困るのかを、ビルドしたデータ（全機能オン、`map.json`）で測った。
数値は 2026-11 時点の `main` 相当のソースによる。

### 変更の確認は一段しか届かない

いまの PR の地図は、変更を次の三つの場所で見せる。

- **エンドポイントの図**：ステップの箱に札（`変更` / `中で変更` など）が付く
- **ステップの詳細**：そのステップの関数の変更メモと差分（`ChangeDetail`）、それより下で変わった関数の名前の一覧（`ReachedList`）
- **関数のページ**：その関数の変更メモと差分、呼ぶ関数のうち変わったものの名前の一覧、変えた行の箱に `変更` の札

つまり、差分が読めるのは「いま開いている関数」だけであり、一段下からは名前と経由（`a() → b() を経由して呼ぶ`）しか見えない。
変わった関数がステップの関数から 3 段下にあれば、名前を頼りに関数のページを 3 回開くことになる。
hono の構成では、ステップの下に 3 段以上の関数を持つステップが 31 個あり、最も深いもので 7 段（`consent/issue-hybrid-response`、下に 55 関数）ある。

さらに、関数のページへ移ると文脈が消える。
URL のハッシュは `#hono--fn--verifyClientSecret` のように関数名だけを持ち、どのエンドポイントのどのステップから来たかを持たない。
「呼び出し元」欄はその関数に届くすべてのステップを並べるので、読者が辿ってきた道筋を区別できない。
ケースの選択も関数ごとに独立していて、「上の関数でこの分岐を通ってきた」という情報は下の関数のケースに反映されない。

もう一つ、差分の行と図の対応が粗い。
箱に `変更` の札が付くのは、変えた行が箱の行と一致するときだけである（`nodeMark`）。
しかし関数の宣言から本体の終わりまでの行のうち、箱が指す行は 25%（21,901 行中 5,533 行）しかない。
代入や計算、カタログ外の呼び出しの行を変えても、どの箱にも札が付かず、図からは変更が見えない。

### 条件分岐がケースとして分かれない

ケースは「開始から終わりまでの道筋」を列挙して作る（`deriveCases`）。
道筋が 24 本を超えると、終わりの箱ごとに一つの「exit ケース」へ切り替わり、分岐のラベルが名前から消える。
この切り替えが起きている関数は 1,017 個中 52 個で、その中には読者が最も開くであろう場所が含まれる。

| 対象 | 条件の数 | いまのケース |
|---|---|---|
| `/token`（hono、全機能） | 6 | exit ケース 27 個。成功の終わりが 6 個、残り 21 個はステップごとの `respondTokenError` |
| `/authorize`（hono、全機能） | 8 | exit ケース 27 個。成功の終わりが 8 個、残り 19 個は失敗元ごとのエラー応答 |
| `verifyIdJagAssertion` | 45 | exit ケース 23 個。うち 22 個が `→ throw invalidAssertion(…) (n)` と番号だけが違う |
| `buildAuthTransaction` | 14 | exit ケース 1 個（`→ return`） |

README は「`/token` なら `authorization_code` と `refresh_token`」をケースの例に挙げているが、全機能オンの `/token` ではこの二つを選べない。
`validatedRequest = refreshTokenRequest ?? (await validateAuthorizationCodeGrant(…))` の分岐は読めているのに、exit ケースに畳まれて同じ `→ return respondToken(…)` になるからである。

道筋が増える原因は三つあり、それぞれ性質が違う。

- **任意項目の条件**：`if (x !== undefined) { obj.x = x; }` のように、成立しても不成立でも次の箱へ合流し、間に箱がない条件。1,846 個の条件のうち 414 個がこれで、`buildAuthTransaction` の 14 個の条件はすべてこの形である。14 個の独立した合流で道筋は 2^14 本になる
- **エラーの矢印を道筋として数えること**：実装から読んだ図と関数の図では、`catch` へのエラーの矢印も一本の道筋になる（`errors: 'path'`）。さらに `separateErrors` が失敗元ごとに `catch` の箱を複製するので、`/token` では 21 本のエラーの道筋が成功の道筋と同じ枠を奪う
- **守り（guard）の多い関数**：`verifyIdJagAssertion` のように早期 `throw` が 40 個以上並ぶ関数。道筋の数自体は条件の数程度だが、exit ケースの名前が終わりの箱の名前なので区別がつかない

任意項目の条件を一つの箱に畳み、エラーを「エラー時」の修飾として扱うと、52 個のうち 36 個は 24 本に収まり、`/token` は次の 7 ケースになる（計測の結果）。

```
idJagIssuance: 成立 → return idJagIssuance
… › exchanged: 成立 → return exchanged
… › deviceGrantResponse: 成立 → return deviceGrantResponse
… › cibaGrantResponse: 成立 → return cibaGrantResponse
… › refreshTokenRequest: null または undefined → return respondToken(…)   ← authorization_code
… › refreshTokenRequest: null・undefined 以外 → return respondToken(…)     ← refresh_token
```

残る 16 個（`verifyIdJagAssertion` など）は、道筋を列挙する方式そのものが合わない。

最後に、関数の図には呼び先の失敗が描かれない。
JSDoc に `@throws` を持つ関数の呼び出しは 557 箇所あるが、エラーの矢印が付くのは `try` の中にある 133 箇所だけで、424 箇所（202 関数）では呼び先が投げる例外がどこへ行くのか図に出ない。
エンドポイントの図では `catch` に集まるので見えるが、関数のページではその関数が「どこで失敗して終わるか」の半分が欠ける。

## 設計の方針

二つの問題は別々に見えるが、どちらも「読者が辿っている道筋」を地図が持っていないことから来る。
変更を追うときは「エンドポイント → ステップ → 関数 → … → 変えた行」という道筋を保ちたいし、分岐を選ぶときは「どの条件でどちらへ進んだか」という道筋を選びたい。
そこで、次の二つを地図の一級の概念として導入する。

- **経路（trail）**：エンドポイントのステップから、呼び出しを下って一つの関数に至る道筋。URL に残し、画面に示し、ケースの既定値と呼び出し元の絞り込みに使う
- **決定（decision）**：処理の流れの中で道筋を分ける条件。道筋をすべて列挙する代わりに、決定ごとにどちらへ進むかを選び、その組み合わせからケースを導く

以下、変更の追跡（A 群）と分岐の表現（B 群）に分けて設計を述べる。
A 群はデータ形式をほとんど変えずに画面側（`apps/map/src`）で閉じ、B 群は CLI の流れの読み取り（`packages/cli/src/extract/function-flow.ts`）と図の組み立て（`graph.ts`、`diagram.ts`）に及ぶ。

## A. 変更を深い関数まで追える地図

### A1. 経路を URL と画面に持つ

関数のページを開くとき、どこから来たかを `View` に持たせ、ハッシュにも書く。

```
#hono--token--authenticate-client--fn--authenticateTokenClient--fn--verifyClientSecret
```

先頭はこれまでどおりエンドポイントとステップで、`--fn--<名前>` が続く分だけ下った関数を表す。
`fn` が一つもなければエンドポイントの画面、あれば最後の `fn` の関数のページを開く。
同名の関数の区別（`--<package>--<module>`）はいまの規則を各 `fn` に適用する。
既存の `#hono--fn--<名前>` と `#fn--<名前>` はそのまま読める（経路が空の関数のページ）。

関数のページには見出しの下に経路をパンくずで示す。

```
token（トークン） › クライアントを認証する › authenticateTokenClient() › verifyClientSecret()
```

各要素はその画面へ戻るリンクで、`← 戻る` は履歴ではなく経路の一つ上へ戻す。
経路が空のとき（検索や「この関数を呼ぶ関数」から来たとき）はパンくずを出さず、いまの表示と同じにする。

経路があるとき、「呼び出し元」欄は経路に沿う呼び出し元を先頭に固定し、残りを「ほかの呼び出し元」として続ける。
図の箱を選んで下の関数へ進むときは、いまの関数を経路に足す。
「この関数を呼ぶ関数」から上へ進むときは、経路を捨てる（上へ向かう移動は経路の定義に合わない）。

### A2. 経路に沿うケースを既定で選ぶ

経路の次の要素（一段下の関数）を呼ぶ箱は、いまの関数の図のどこかにある。
関数のページを経路付きで開いたときは、その箱を通るケースだけを既定でチェックし、箱を選択状態にする。
読者は「上の関数のどの分岐を通ると、次の関数へ進むのか」を開いた瞬間に見られる。
通らないケースは灰色の点線のままなので、三色の規則は変えない。

この既定値は `checked` が未設定のときだけ効く。
読者がケースを変えたら、いまと同じくその選択を保つ。

### A3. 下で変わった関数の差分を、その場で読む

`ReachedList`（ステップの詳細と関数のページの「このPRで変えた関数」）の各行に、折りたたんだ差分と変更メモを付ける。
行を開くと、いまその関数のページに出している `ChangeDetail`（札、変更メモ、`差分を見る`）がそのまま出る。
データは `FunctionChange.hunks` と `notes` に揃っているので、ビルドの変更は要らない。

行の経由（`a() → b() を経由して呼ぶ`）は、各関数名を経路付きのリンクにする。
`b()` を押せば、経路 `ステップ › a() › b()` で `b()` のページが開く（A1）。
最後の関数名を押せば、変えた関数のページが経路付きで開き、A2 によって変更の箱に至る分岐が選ばれている。

経由には、各段で通る分岐のラベルも添える（A4）。

### A4. 経由に分岐の条件を添える

いまの経由は関数名の列であり、「`a()` の中のどの分岐を通ると `b()` を呼ぶのか」を言わない。
各段について、その関数の流れの開始の箱から次の関数を呼ぶ箱までの最短の道筋を取り、その上の分岐の矢印のラベルを並べる。

```
authenticateTokenClient()  ─ authorization: 成立 ─▶  verifyClientSecret()
```

ラベルは `diagram.ts` の `edgeText` と同じ言葉遣い（成立、不成立、それ以外、`case 'x'`）にする。
ラベルのない段（無条件に呼ぶ）は矢印だけにする。
複数の道筋があるときは最短の一本を示し、「ほか n 通り」と添える。
計算は `FunctionFlow` の `edges` だけで済み、`changesBelow` と `endpointsUsing` の `via` に矢印のラベルを足す形で入れられる。

B 群の決定の分類（B1）が入れば、ラベルを「決定」のものに限って短くできる。

### A5. 箱のない行の変更も札にする

`nodeMark` の「変えた行 = 箱の行」の対応を、範囲の対応に変える。
関数の流れの箱をソースの行で並べ、各箱に「自分の行から次の箱の手前の行まで」を受け持たせる。
変えた行がどの箱の範囲に入るかで札を付け、箱の行そのものを変えたときは `変更`、受け持つ範囲の行を変えたときは `付近を変更`（灰色、`変更` より弱い）とする。
ツールチップには変えた行番号を列挙する。
開始の箱は宣言から最初の箱の手前までを受け持ち、いまの `declarationLine` の扱いはこれに含まれる。

範囲は `card.flow.nodes[].line` と `card.source.end` から画面側で決まるので、データ形式は変えない。
これで、関数の中で変えた行は必ずどこかの箱に現れる。

### A6. 変更から届くエンドポイントを「このPRの変更」に並べる

「このPRの変更」のページは、変わった関数を種類ごとに並べ、横に札の付くエンドポイントを置く。
ここに、変わった関数ごとに「届くエンドポイントとステップ」を足す。
`endpointsUsing` がすでに `via` を返すので、各行を経路付きのリンク（A1）にし、A4 の分岐のラベルを添える。

レビューする人は、変更から始めて「どのエンドポイントの、どのケースで、この変更が効くのか」を一画面で把握できる。
PR のコメントに書く Markdown（`changesMarkdown`）にも、関数ごとに届くエンドポイントの id を 1 行添える。

### A7. コードの Drawer に差分の表示を足す

Drawer の「表示するコード」の一覧で、この PR で変わった関数に札を付け、その関数を選んだときに「差分 / 変更後の全文」を切り替えられるようにする。
エンドポイントの Drawer は呼び先を core まで列挙する（`endpointSources`）ので、エンドポイントの画面から離れずに、深い関数の差分へ飛べる。
差分の描画は `DiffView` を使い回す。

### A 群の優先順位

A3、A5、A4 はデータ形式を変えず、既存の純粋関数（`changes.ts`、`model.ts`）の拡張とテストで閉じる。
A1 と A2 はハッシュと `App.tsx` の状態に手を入れるので、その次に置く。
A6 と A7 は A1 のリンクがあると価値が上がるので最後にする。

## B. 分岐を正しく分けるケース

### B1. 条件を「決定」と「任意の処理」に分ける

条件の箱を、流れの形で三つに分類する。

- **守り（guard）**：一方の矢印が `return` / `throw` / 終了にすぐ至る条件。早期リターンの検査
- **分かれ道（fork）**：両方の矢印の先に別々の箱があり、合流するまでに処理が違う条件。`switch` の `case`、`??` や三項演算子で呼び先が変わる場合を含む
- **任意の処理（optional）**：両方の矢印が同じ箱へ至り、成立側に箱がない条件。任意項目の代入や設定

計測では、守りが 999、分かれ道が 433、任意の処理が 414 である。
決定と呼ぶのは守りと分かれ道で、ケースの列挙と名前付けには決定だけを使う。

任意の処理は、条件の箱と二本の矢印の代わりに一つの箱で描く。
箱の一行目は条件、二行目は成立したときに行うこと（代入先の名前、または手前のコメント）とし、矢印は一本にする。
`buildAuthTransaction` の 14 個の条件は 14 個の箱の列になり、道筋は 1 本になる。
二行目に書く内容はソースから読む必要があるので、この畳み込みは CLI の読み取り（`function-flow.ts`）で行い、箱の種類 `optional` として `FunctionFlowNode.kind` に足す。
画面側で合流の形だけを見て畳む案もあるが、それでは「成立すると何をするか」を示せない。

### B2. エラーは関数の図でも「エラー時」の修飾にする

実装から読んだエンドポイントの図と関数の図は、`catch` へのエラーの矢印を一本の道筋として数えている。
これを従来のステップの図と同じ「エラー時」のケース（修飾）に戻す。
エラー時をチェックすると、表示中のケースの箱から出るエラーの矢印と、その先の `catch` の箱が加わる。
失敗元ごとに `catch` を分ける `separateErrors` はそのまま使い、分けた箱は表示中のケースの箱から届くものだけを出す。

`catch` の中に分岐があり、分岐先が違う応答になる場合（`respondTokenError` の中の分岐など）は、`catch` の中の決定をエラー時のサブケースとして列挙する。
`catch` の外の決定とは掛け合わせない。

### B3. 呼び先の失敗を描く

JSDoc に `@throws` を持つ関数を呼ぶ箱には、エラーの矢印を一本足す。
行き先は、`try` の中なら `catch`、外なら「呼び先の例外で終わる」という `throw` の箱（関数ごとに一つ、赤）である。
これらの矢印は B2 の「エラー時」をチェックしたときだけ描くので、既定の図は変わらない。
呼び先の `throws` は `FunctionCard.throws` にあるので、データの追加は要らない。
`FunctionFlowNode.kind` に `'propagated'` を足すか、`throw` の箱に印を付けるかは実装時に決める。

### B4. 決定ごとに選ぶケース

道筋の列挙を、決定の組み合わせの選択に置き換える。

ケース欄には、決定を上から順に並べ、各決定でどちらへ進むかを選ぶ。
守りは「成立（ここで終わる） / 不成立（続く）」、分かれ道は矢印のラベル（`case 'a'`、`成立`、`null または undefined`）の選択肢になる。
選んだ組み合わせから一本の道筋を求め、通る箱と矢印を青にする。
選択に依存しない決定（選んだ道筋が通らない条件）は灰色にし、選べなくする。

既定の選択は「最も長い道筋」、つまり守りをすべて不成立で通る道筋とする（いまの既定と同じ）。
決定の数が少ない関数（決定が 4 個以下など）では、道筋の列挙と名前（B5）を「よく通る道筋」として先に並べ、決定の選択はその下に置く。
exit ケースへの切り替えは廃止する。

複数のケースを同時に表示する操作（いまのチェックボックスの複数選択）は、「よく通る道筋」の複数選択として残す。

### B5. ケースの名前は、区別に要るラベルだけにする

列挙した道筋の名前は、通ったラベルを `›` でつないだものになっていて、`/token` の 7 ケースでは `idJagIssuance: 不成立 › idJagRedemption: 不成立 › …` と前置きが長い。
ほかのケースと区別できる最小の接尾を名前にする。
`/token` なら `exchanged: 成立`、`refreshTokenRequest: null または undefined` の一語で区別できる。
守りの「不成立」は省く（通ったことは名前に要らない）。
終わりの箱の名前は、ラベルで区別できないときだけ添える。

`??` と三項演算子のラベルには、条件の式ではなくステップの言葉を使えるようにする。
`refreshTokenRequest: null または undefined` は、箱の二行目（ステップのラベルや JSDoc）から `authorization_code グラントを検証する へ` と言い換えられる。
矢印の先の箱の一行目を使う規則を `diagram.ts` に足す。

### B6. 読み取りの漏れ

計測で見つかった、分岐の読み取りが実際の評価と違う形を直す。

- 論理代入（`x ??= f()`、25 箇所）：右辺の呼び出しを無条件の箱にしている。`??` と同じ短絡の分岐にする
- コールバックの中の呼び出し（`.map((x) => f(x))` など、47 箇所）：ループの中の呼び出しとして、`for` と同じく矢印に「各要素で」のラベルを付ける
- `catch` の無い `try … finally`：いまは例外の出所を外へ渡しているので正しい。変更なし

呼び出しの引数の中の三項演算子（`f(ok ? a() : b())`）は、両腕に呼び出しを持つものがリポジトリに無かったので、対応は後回しにする。

### B 群の優先順位

B1 の分類と B2 のエラーの修飾は、`/token` と `/authorize` の exit ケースを無くす最短の道で、計測で効果を確かめてある。
B1 の `optional` の箱は CLI の変更（`function-flow.ts` とそのテスト、`types.ts`）を伴う。
B4 の決定の選択は画面の変更が大きいので、B1 と B2 で残る 16 関数の様子を見てから着手する。
B3 と B6 は独立に進められる。

- `graph.ts` / `diagram.ts` / `changes.ts` / `model.ts` のテスト（`apps/map/src/lib/*.test.ts`）に、A4 の分岐のラベル、A5 の範囲の札、B1 の畳み込み後のケース数、B5 の名前を足す
