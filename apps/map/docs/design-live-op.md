# 地図の OP：デプロイした OP でリクエストを動かし、動いた順に読む

地図のフローで書いたリクエストと、ケースのリクエストは、地図と一緒にデプロイした OP（地図の OP、`packages/live-op`）で動かす。
この文書は、その OP の形と、リクエストが通った道筋を地図がどう求めるかを決めた理由を書く。
画面の操作は [README](../README.md) の「フロー」、変更の経緯は [変更メモ](../changes/run-requests-on-the-live-op.md) にある。
以前の形（ページの Web Worker の OP と、ビルド時に作る前提）は [design-request-premises.md](design-request-premises.md) にあり、この文書がそれに代わる。

## 求めること

地図が見せる道筋は、読者が書いた値で本物の OP が動いたときの道筋でなければならない。
そのためには次の三つが要る。

1. 動かす OP が、デプロイされる OP と同じものであること。コードも設定も状態の持ち方も
2. 一つのリクエストが動かしたコードを、呼び出しごとに、動いた順に知ること
3. その記録を、地図の木の決定の側に、推測を足さずに写すこと

以前の形はどれも満たしていなかった。
OP はページの中で、ビルド時の前提の写しの上で毎回新しく作られ、時計は止まり、外へのリクエストは断っていた。
道筋は、リクエスト全体の Istanbul の計数を行の規則で読んだもので、同じ関数の二度の呼び出し、リストの末尾で失敗する呼び出し、ハンドラーの組から作った根を読めず、読めない分岐は仮の側（多くは成功の側）へ進んだ。

## 地図の OP

### 何を動かすか

`apps/hono/src/app.ts` の `createServerApp(env)` を、そのまま動かす。
`maronn-oidc generate hono` が出すコード（`oidc-provider/`）を、`apps/hono` がデプロイされるときと同じ配線（`applyOidc` とその options、`settings.ts` が読む環境変数）で使う。
環境変数は `packages/live-op/src/seed.ts` が作り、クライアントは `OIDC_CLIENTS_JSON` で登録する（ケースが使うクライアントごとに一つ。秘密の値も鍵もこのリポジトリに公開している遊び場の値）。
署名鍵はワークスペースが作って保ち、`OIDC_SIGNING_KEY_JWK` で渡す。ホストが眠って起き直しても、前に発行したトークンが検証できる。

### ワークスペース

読者ごとにワークスペースを一つ持つ。
ワークスペースは OP の状態（メモリの DB、機能のストア、署名鍵、時計を進めた秒数）と、答えたリクエスト（交換、exchange）の記録である。
状態はリクエストの間で保つ。使った認可コードは使ったまま、ログインしたセッションはログインしたまま、時計は本物の時計である。
期限切れのようにすぐには起きないことは、「時計を進める」（`POST /__live/clock`）で起こす。時計を進めたことはケースの準備の記録にも残る。

ページはワークスペースの id を `localStorage` に置き、同じ値を Cookie `map_workspace` にも置く。
地図のページと OP は同じオリジンなので、読者が別のタブで開いた認可リクエストやログイン画面も、同じワークスペースに届く。
Cookie も id のヘッダーも無いリクエスト（curl やクライアントのバックチャネル）は、共有のワークスペース `public` に届く。

`apps/hono` は DB を `globalThis` に置き（`db/memory/database.ts`）、機能（PAR、デバイス、CIBA、動的クライアント登録）はストアをモジュールに一つ持つ。
一つの isolate（Workers）や一つのプロセス（Node）に複数のワークスペースが載るので、リクエストは isolate の中で一つずつ動かし、その間だけ、グローバルの DB、機能のストアのメソッド、時計を、そのワークスペースのものにする（`workspace.ts` の `exclusive`）。
計数も isolate に一つなので、一つずつ動かすことは記録の正しさにも要る。

### ホスト

- Cloudflare Workers：地図の Worker（`apps/map/worker`）が、OP のパスと `/__live/*` をワークスペースの Durable Object（SQLite 版。Free プランで動く）へ渡し、ほかは静的アセット（地図のページ）を返す。状態は Durable Object のストレージに置く。7 日リクエストの無いワークスペースは消す
- Node：`packages/live-op/dist/node.js` がワークスペースをメモリに持つ。Vite の開発サーバーとプレビューはこれをミドルウェアにして、ページと同じオリジンで OP に答える（`@maronn-openid-connect/live-op/vite`）。地図のビルドもこれでケースを動かす

`issuer` はリクエストのオリジンである。OP の画面のパスは `issuer` のオリジンの下の絶対パスなので（`endpoints/authorize/page.ts` の `screenUrl`）、OP はオリジンの根に置く。地図のページとパスが重ならないので、同じ Worker の根に両方を置ける。

PR のプレビューは、PR ごとの Worker に `wrangler deploy` する。Worker Previews は Durable Object の名前空間を本番と共有するので、PR の地図が main の OP のコードの記録を読むことになるからである。

### 制御の API

| パス | 何をするか |
|---|---|
| `POST /__live/run` | 読者が書いたリクエストを OP に送り、交換を返す |
| `POST /__live/preview` | 読者が書いたリクエストを、ワークスペースの状態のコピーで動かし、交換（`source` は `preview`、id は `p<n>`）を返す。コピーも交換も残さない |
| `POST /__live/scenario` | ケースのリクエストを、それに要るリクエストを OP に送って準備する |
| `POST /__live/grant` | 認可をブラウザとクライアントのように行う（認可リクエスト、ログイン、同意、引き換え） |
| `GET /__live/exchanges`、`/__live/exchanges/<id>` | 交換の一覧と、一つの交換 |
| `GET /__live/state`、`POST /__live/reset`、`POST /__live/clock` | ワークスペースの状態、作り直し、時計を進める |
| `GET /__live/probes` | プローブの表 |

OP のパスへの応答には、その交換の id をヘッダー `x-map-exchange` に付ける。curl で送ったリクエストも、地図で開ける。

フローは、送る前のリクエストにも従う。
ケースが準備したリクエストと、読者が書き換えたリクエスト（書き換えが 0.4 秒止まったとき）を `POST /__live/preview` で動かし、送ったリクエストと同じ `followTrace` でその交換をたどる（`apps/map/src/lib/preview.ts`、`apps/map/src/components/useRun.ts` の `show`）。
書き換えたリクエストは、書き換える前のリクエストも続けて試算し、二つを読み比べる（後の「書き換える前のリクエストと読み比べる」）。
試算はワークスペースの DB と機能のストアを写した上で、同じ時計で動くので、いま送れば通る道筋と同じになり、使っていない認可コードは使わないまま残る。
新しい試算を頼むと、それより前の試算の結果は捨てる。
送ったリクエストと「最近のリクエスト」から開いたリクエストは、書き換えて元に戻したときに、試算せずその記録をたどり直す。

### 制限

地図の OP は誰でもリクエストを送れる遊び場なので、ワークスペースが壊れたままにならず、膨らみ続けず、ほかのサイトから動かされないように、次を守る。
どれも遊び場の制限で、OP（`apps/hono`）の制限ではない。

- ボディは 64 KiB、URL は 16 KiB までとし、超えたリクエストは OP を動かす前に 413 で断る（`api.ts` の `REQUEST_BODY_LIMIT`、`REQUEST_URL_LIMIT`。`relay.ts` の `refusalOf`）。地図が中継するリクエストも同じである
- 機能のストアの書き込みのうち、PAR、デバイス、CIBA の記録のものは、最後の書き込みから 1 時間で捨てる。記録は数分で切れるので、作り直しても同じである。動的に登録したクライアントの書き込みは残す
- ワークスペースの状態（`WorkspaceSnapshot` の JSON）が 8 MiB を超えたら、ワークスペースを作り直す
- 保存していた状態を読めない、または作り直せないとき、OP のコードか設定が変わったとき（スナップショットの `build`：プローブの表のハッシュと、クライアント、ユーザー、ログアウトの登録のハッシュ）も、ワークスペースを作り直す。理由は状態の `notice` に残り、読者が作り直すまで返す。交換の id は続きから振る
- 一つのワークスペースのリクエスト、作り直し、時計を進めることは、一つずつ動かす（`workspace.ts` の `serial`）。作り直しと並んだリクエストが、同じ交換の id を得ることはない
- 制御の API は、ワークスペースをヘッダー `x-map-workspace` だけで選ぶ。Cookie で選ぶのは OP のパスだけである。ほかのサイトがブラウザに送らせるリクエストにも、Cookie は付くからである。`GET` と `HEAD` のほかの制御のリクエストは、`Sec-Fetch-Site` が `same-origin` か `none` でなければ 403、`content-type` が `application/json` でなければ 415 で断る。ワークスペースの id でないヘッダーは、`public` に落とさず 400 で断る
- 交換には、ホストが足したヘッダー（`cf-*`、`x-forwarded-*`、`x-real-ip`）を残さない。誰でも読める `public` では、`authorization` と `cookie` の値を隠して残す
- Worker は、ワークスペースが答えたリクエストでだけ、消すアラームを延ばす。開けないワークスペースが、断ったリクエストで生き続けることはない

次は制限していない。

- ワークスペースは誰でも作れる。数や頻度は制限せず、Cloudflare の制限（Workers と Durable Objects の利用の上限）だけがかかる
- isolate に一つのキュー（`exclusive`）は、OP が外へ送るリクエスト（クライアントの `jwks_uri`、`request_uri`）の応答も待つ。遅い先を指すリクエストは、同じ isolate のほかのワークスペースのリクエストも待たせる
- 使われないワークスペースは、最後のリクエストから 7 日で消える。それまでは Durable Object のストレージに残る

## 動いた順の記録

### プローブ

OP のバンドル（`packages/live-op/dist/live-op.js`）は、計測したテストと同じ設定で Istanbul が数える（`istanbul.ts`）。
数える文、分岐の側、関数の入口の一つ一つをプローブと呼ぶ。
Istanbul が作るコードは、数えるたびにファイルの計数のオブジェクトを読み直す（`cov().s[3]++`）。
記録器（`recorder.ts`）は、モジュールを読み込んだ後に、それぞれの計数をプロパティに置き換え、リクエストを記録している間は、上がるたびにそのプローブの番号を列に足す。
計数の値は変えないので、計数を読むもの（`test-reach`）はそのまま読める。

プローブの表は、プローブごとの元のソースの場所（Istanbul が持つ入力のソースマップで戻す）、分岐の種類と側、関数の名前を持つ。
文のプローブには、それが `throw` か `return` かの印を付ける。Istanbul が数えるコードの文の始まりの語で、計数のプラグインが決める。

### 呼び出しへ分ける

地図の解析（`packages/map-analysis/src/traced.ts`）は、記録の列を呼び出しに分ける。

- 関数の入口のプローブ（地図のフレームの宣言の行にあるもの）は、そのフレームの呼び出しを一つ始める。直前の既定の引数の分岐は、その呼び出しのものである
- フレームの宣言の行に無い関数の入口（フレームの中で作った関数）は、そのフレームの呼び出しが動いている間なら、その呼び出しの中のコールバック（地図の木が呼び出しの中に並べるもの）で、そうでなければ名前の無い呼び出しを一つ始める。工場の関数が返したメソッドを後で呼んでも、工場の呼び出しには混ざらない
- それ以外のプローブは、行が入る最も内側のフレームの、最も新しい呼び出しのものである
- 呼び出しの親は、そのフレームを呼ぶ（関数カタログの `calls`）呼び出しのうち最も新しく動いたもので、無ければ最後に動いた呼び出しである。`throw` の直後に始まった呼び出しは投げた呼び出しの子である
- 呼び出しが投げたのは、最後に動いたのが `throw` の文のとき（`throw` の式が呼ぶ関数は文の後に動くので、それに関わらず）、最後に動いたのが投げた呼び出しのとき、そして最後に動いた文の次のノードが動かず、その後に始まった呼び出しも無いとき（地図の外のコード、`atob` や `JSON.parse` が投げた）である

地図のフレームは、根からの呼び出しのノードの列（`s0b1s0.s2`）で名指す。
親の呼び出しが呼んだその関数の呼び出しは、始まった順に、呼んだ文の中にあるその関数の呼び出しのノードへ、木の順に一つずつ割り当てる。一つの文の中で同じ関数を何度呼んでも（`return { a: optional(…), b: optional(…) }`）、それぞれのノードに別の呼び出しが付く。

### 決定の側

呼び出しごとに、その呼び出しが動かしたものだけの計数を作り、これまでと同じ規則（`observe.ts`）で読む。
同じ決定が別の呼び出しで別の側に進んでも、混ざらない。

- 呼び出しのノードは、その呼び出しが投げたなら失敗し、投げなかったなら先へ進む。リストの末尾の呼び出しでも決まる
- 規則で決まらない決定（`??=`、三つ以上の項の `&&`、ローカルのコールバックの繰り返し）は、地図の関数の呼び出しが動いた側が一つだけなら、その側に進む
- 一つの呼び出しの中で両方の側に進んだ決定（繰り返しの中の `if`）は、最後に進んだ側に進む。繰り返しの最後の一回が、そのフレームの終わり方につながる
- ただし、最後に進んだ側が繰り返しを抜ける側（`continue`、`break`）で、その先の本体に、ほかの回で呼んだ地図の関数の呼び出しがあるときは、抜けない側に進む（`sideOfLastPass`）。歩みは本体を一度しか通らないので、抜ける側に進むと、その呼び出しをどれも通らなくなるからである（JWKS は、同じ `kid` の二つ目の鍵を `continue` で飛ばし、一つ目の鍵は公開鍵に変換している）
- 条件や引数の中の呼び出しのうち、短絡で評価されなかったもの（`a && f(x)` の `f`）は、呼ばなかったとして飛ばす（`skips`）
- `continue` と `break` は、その繰り返しを抜ける。歩みは繰り返しの本体を一度だけ通るので、どちらも本体の残りを通らずに、繰り返しの後へ進む（`walk.ts` の `leavesLoop`）。仮の側は、繰り返しを抜ける側ではない側にする（`return` する守りを通り抜けるのと同じ）
- ハンドラーを振り分ける根は、リクエストが動かしたハンドラーの側に進み、その先を開く。ハンドラーの組から作った根（`GET | POST /login`、`/consent`）はそのハンドラーのフレームを、ハンドラーを本体に書いた根（`GET | POST /device`、`/ciba`、`/logout`）は、動いたハンドラーが呼んだ地図の関数のフレームを開く（`handlersRoot`）

`followTrace` は、地図のページと同じ手順で道筋をたどる。開いたフレームの決定を読み、失敗した呼び出しのフレームを開いて、投げた `throw` まで下りる。
根が動いていないリクエスト（ルーティングやミドルウェアが答えた 405 など）は、そう示して道筋を出さない。
記録が上限（`MAX_EVENTS`）で切れたリクエストは、道筋が途中で止まることがあるとそう示す。

### 書き換える前のリクエストと読み比べる

エンドポイントの根の流れは、失敗しない呼び出しの中で分かれる二つのリクエストに対して同じである。
イントロスペクションは、トークンが見つかっても見つからなくても、同じステップを通って 200 を返す。違うのは、トークンを探す関数（`resolveIntrospectionToken`）と、有効かどうかをまとめる関数（`describeIntrospectedToken`）の中の分岐の側である。
失敗した呼び出しは `throw` まで開くが、失敗しない呼び出しは開かないので、値を書き換えても、根のフローチャートは変わらなかった。

`followTrace` は、`against`（書き換える前のリクエストの記録）を渡すと、二つを読み比べる。

- 二つの呼び出しが同じに動いたかは、プローブの列で決める（`sameRun`）。自分の行で動かしたプローブが同じ順に同じで、地図の関数の呼び出しも同じ順に同じで、それぞれが同じに動いたときである。フレームが作って後で呼ばれた関数（名前の無い呼び出し）は比べない。署名鍵のキャッシュのように、最初の一度だけ別の動きをするものがあるからである
- 同じ呼び出しのノードから二つとも呼んでいて、同じには動かなかった呼び出しを、地図が分岐の側（決定の側、失敗する呼び出し、評価されない呼び出し）を別に読むフレームまで下って開く（`readsApart`）。プローブは違っても側がどれも同じ呼び出し（値の一文字ごとに動くコールバック、式の中のオペランド）は、フローチャートが同じなので開かない
- 分かれる所（`Parting`）として挙げるのは、側が違い、かつ、自分の行が別の動きをする前に呼んだ地図の関数に、側が違うものが無いフレームである。呼び出した関数が投げたために `catch` へ進んだ根のように、下で分かれた後の続きは挙げない。挙げるフレームには、歩みが最初に通る、側の違うノードと、それぞれの側を添える
- 読むのに要る木（同じには動かなかった呼び出しの木）は、開くかどうかに関わらず `needs` に挙げる。ページは木を読み込んでからもう一度たどる
- 別のビルドの OP の記録と、根を動かしていない記録とは読み比べない

ページは、書き換えたリクエストを試算するときに、書き換える前のリクエストも同じ状態のコピーで試算して `against` にする（`useRun.ts` の `show`）。
前に試算した記録と比べないのは、その間にワークスペースの状態が変わっていると（認可コードを使った後など）、書き換えのせいでない違いが出るからである。
ケースの値を一か所ずつ変えた 1,006 のリクエスト（130 ケースの、クエリ、フォーム、ヘッダーの値を消すか壊す）で確かめた。同じリクエストを二度試算して分かれる所が出たものは無く、ステータスか OAuth のエラーが変わったのに分かれる所が無いものも無く、開いたフレームを通る歩みに食い違いは無かった。

### 道筋を確かめる

`walkMismatches` は、再生する道筋と、そのリクエストが動かしたものが両方の向きで合うかを確かめる。

- 道筋が通るノードはその呼び出しで動いていること（Istanbul が数える文があるもの）、開くフレームは呼ばれていること、失敗させる呼び出しは投げていること
- 道筋が入ったフレームで動いた地図の関数の呼び出しを、道筋が飛ばしていないこと
- 記録から側が分かる決定で、道筋が別の側に進んでいないこと

地図のビルドは全ケースのリクエストを地図の OP で動かし、動いたフレームをすべて開いて、どのリクエストもこの食い違いが無いことを確かめる。
規則で読めない形は仮の側へ進むが、その道筋も実際に動いた行を通り、動いた呼び出しを飛ばさない限り食い違いにはならない。
ケースの値を一か所ずつ変えた 4,621 のリクエスト（欄を消す、壊れた値、二重の欄、メソッドやクライアント認証や Content-Type を変える）でも食い違いは無かった。

## ケース

ケース（`packages/test-catalog/src/scenarios` の目的と期待する応答）ごとに、リクエストの作り方（`packages/live-op/src/scenarios`）を持つ。
作り方は、要るものを OP へのリクエストで得る。認可コードはブラウザのように認可リクエストからログインと同意を経て、トークンはその引き換えで、CSRF トークンは画面のフォームから、Cookie は応答の Set-Cookie から得る。
OP が発行していない値を作って入れるのは、「発行されていないトークン」のように、それがケースの目的のときだけである。
ワークスペースは状態を保つので、作り方は、同じワークスペースで何度準備しても同じ結果になるように書く（`live-op` のテストが、全ケースを同じワークスペースで二度動かして確かめる）。

## 採らなかった形

- ページの中の OP を残し、前提を引き継ぐようにする：本物の OP をデプロイしていることにならず、読者が別のタブで開いた画面や、外のクライアントからのリクエストを扱えない
- 計数の差分を細かく取る（関数の入口ごとに計数を写す）：呼び出しの境目は分かるが、非同期の処理が交互に進むと写す時点がずれる。入口のプローブを記録の列の中に置けば、同じことが順序つきで分かる
- OP のコードにトレースの呼び出しを書き足す：生成するコードに地図の都合が入り、`maronn-oidc generate` が出すものと動かすものが違ってしまう
- 地図のパスの下（`/op/*`）に OP を置く：OP の画面のパスは `issuer` のオリジンの下の絶対パスで、生成するコードはオリジンの下のパスへの組み込みに対応していない
