# 設計案: 想定リクエストから読む地図とテスト

地図（`apps/map`）、テストの画面（`apps/tests`）、PR のコメントを、「想定するリクエスト」を起点に読める形へ組み替える設計案である。
この文書は実装の指示書で、実装はまだ無い。
別のセッション（Claude Code、Codex）がこの文書を読んで実装することを想定している。

## 解決したいこと

地図とテストの画面の目的は、コードレビューの負荷を下げることである。
全体像と、個々の処理が何をしているかを、コードを全部読まずに把握したい。
いまの画面は、次の問いに答えにくい。

| 問い | いまの答え方 | 足りないこと |
|---|---|---|
| このリクエストを送ると、何が起きて何が返るか | ステップの一覧と、コードの分岐から選ぶ道筋 | リクエストから選べない。返るものが出ない |
| PAR のリクエストだと、通常と何が違うか | 機能の札と、全ステップの一覧 | そのリクエストで働くステップと素通りするステップが同じ重さで並ぶ |
| このステップは、このリクエストで何をしたか | ステップを開いて全分岐を読む | 通らなかった行も並ぶ |
| このリクエストについて、何がテストされているか | エンドポイントの全テストと、コードの道筋ごとの数 | API と E2E のテストがリクエストに結び付いていない |
| テストは必要なパターンを満たしているか | 失敗ごとの印（✓ △ ✗） | 何が「必要なパターン」かの一覧が無い |
| この PR で、何の振る舞いが変わるか | 変わった関数の表 | 関数の数が多いと読めない。リクエストの言葉になっていない |
| 動きは分かった。コードはどうなっているか | Drawer、GitHub、手元のエディタ | Drawer は関数単位。GitHub は遅い。手元は準備が要る |

## 現状の計測

全機能オンでビルドした地図（`main`、2026-11-20）を、ブラウザで開いて確かめた。

- hono の `/authorize` で選べる道筋は 56 件ある。内訳はステップへ進む道筋 4、終わり方 8、失敗で終わる 44 である
- 道筋の名前は、ステップの見出し、コードの条件（`'kind' in parsed: 成立`、`silent !== undefined: 成立 › 'kind' in silent: 成立`）、投げる関数（`validateMaxAge から`）である。「PAR でプッシュしたリクエスト」のようにリクエストを言う名前は無い
- フローの既定の道筋「おまかせ」は、決まっていない分岐を仮の側へ進む。既定の機能の `/authorize` では、18 場面のうち 8 個の分岐が仮である。つまり既定の再生は、実在するどのリクエストの動きでもない
- アウトラインは 20 ステップを同じ重さで並べる。通常の認可コードのリクエストでは、PAR、Request Object、JARM、`form_post`、フラグメント、インプリシット、ハイブリッドのステップは何もせずに次へ進むが、画面からは分からない
- テストの画面の `/authorize` は、E2E 24、API 17、ユニット 181 を持つ。ケースの表示は「テストがどの道筋を通るかはコードから読み取れないので、E2E と API のテストはケースごとに分けていません」と書いている
- PR #205（DPoP）のコメントは、関数 154 個の表（40 行で打ち切り）、関数の外の変更があるファイルの列挙、エンドポイントごとの追加テストと関連関数の列挙からなる。discovery のテスト 1 件の期待値の変更だけで、数千字の差分が本文に入っている
- PR #207（未マージ）は、API テストが送ったリクエストと応答、その間に動いた Istanbul の計数を記録し、コードの道筋（ケース）に例として結ぶ。631 ケースのうち例が付いたのは 64 ケース、記録した 246 リクエストのうちケースに結べたのは 151 件である

## 原因

症状は別々に見えるが、原因は一つである。
**読む軸が、コードの形（ステップ、分岐、関数）だけである。**

地図の道筋は、木の分岐から計算する。
これは正確で漏れが無いが、読者が持ってくる問いは「このリクエストだと」で始まる。
コードの分岐の名前から、それがどんなリクエストに当たるかを読者が逆算している。

PR #207 はリクエストの例を足したが、軸はコードの道筋のままである。
道筋を選ぶと例が出る（例の無い道筋が 9 割）。
欲しいのは逆で、リクエストを選ぶと道筋が出ることである。

## 設計の方針

**想定リクエスト**を、地図、テスト、PR の三つに共通の、もう一つの軸として足す。
コードの軸（アウトライン、決定、道筋）は残し、置き換えない。

想定リクエストは「こういう前提で、こういうリクエストを送ると、こう返る」を一件で言うものである。
例：「PAR でプッシュ済みの `request_uri` を渡す → ログイン画面へ 302」。

方針は四つである。

1. **定義は人が読める一覧に置く。** エンドポイントごとに、想定リクエストの名前、前提、期待する結果、仕様の節を YAML に書く。これが「どんなパターンを想定しているか」の一覧になる
2. **結び付けは宣言で行う。** テストが、自分がどの想定リクエストを送るかをコメントで宣言する。テストの名前やパラメータから推測しない（既存の「規則であって推測ではない」という方針に合わせる）
3. **道筋は観測で求める。** 宣言したテストが実際に送ったリクエスト、返った応答、その間に動いた行（PR #207 の記録）から、通ったステップと行を求める。仮の分岐は無い
4. **差を見せる。** 想定リクエストごとに、ステップを「働いた」「素通りした」「通らない」に分ける。基準の想定リクエスト（通常の認可コード）との違いを一行で言う

識別子の名前には注意が要る。
`scenario` は Gherkin のタグ `@scenario:`（`.github/scripts/lint-features.mjs` の `SUBJECT_PREFIXES`）、`case` は `EndpointCase` と `TestCase`、`scene` はフローの場面が使っている。
この文書は、想定リクエストの識別子を仮に `premise` と書く。

## 1. 想定リクエストの定義

`tests/catalog/premises/<endpoint>.yaml` に置く（`tests/catalog/aspects.yaml` の隣）。

```yaml
endpoint: authorize
baseline: code-pkce          # 差を言うときの基準
premises:
  - id: code-pkce
    title: 認可コード + PKCE で送る（未ログイン）
    group: 基本
    request: response_type=code と code_challenge を付ける
    expect: ログイン画面へリダイレクトする
    spec: [OIDC Core 1.0 §3.1.2.1, OAuth 2.1 §4.1.1]

  - id: par-pushed
    title: PAR でプッシュ済みの request_uri を渡す
    group: PAR
    features: [par]
    given: [/par でプッシュ済み, 未使用, 期限内]
    request: request_uri に /par が返した URN を付ける
    expect: ログイン画面へリダイレクトする
    spec: [RFC 9126 §4]

  - id: par-used
    title: 使用済みの request_uri を渡す
    group: PAR
    features: [par]
    given: [同じ request_uri で一度リクエスト済み]
    expect: invalid_request_uri を OP の画面で返す（リダイレクトしない）
    check: { status: 400, error: invalid_request_uri }
    spec: [RFC 9126 §4, RFC 9126 §7.3]
```

- `title`、`given`、`request`、`expect` は人が読む言葉である。機械は解釈しない
- `check` は任意で、観測した応答と照らす（ステータス、OAuth のエラーコード、リダイレクトの有無）。食い違えばビルドが警告する
- `features` は、その想定リクエストが要る機能である。地図の機能のオン・オフで絞る
- `group` は一覧のまとまりである（基本、PAR、Request Object、Implicit、Hybrid、prompt と SSO、エラー）
- id はエンドポイントの中で一意にし、全体では `<endpoint>/<id>`（`authorize/par-pushed`）と書く

最初の一覧は人が書かない。
記録したリクエストを、観測した道筋（通ったステップと終わり方）でまとめ、YAML の雛形を書くコマンドを足す（`pnpm --filter @maronn-openid-connect/map premises:draft`、既存の `changes:draft` と同じ考え）。
雛形には、まとめごとの代表のリクエスト、応答、テストの名前を HTML コメントで添える。
名前（`title`）と期待（`expect`）は、実装するセッションがテストと仕様から書き、人は一覧を見て直す。

## 2. テストとの結び付け

テストコードでは、`it` か `describe` の直上のコメントで宣言する。
既存の `// @feature par`、`// @aspect boundary`、`// @test-id` と同じ読み方である（`packages/test-catalog/src/read-code.ts`）。

```ts
// @premise authorize/par-pushed
it('should expand a pushed request_uri into the pushed parameters', async () => { ... });
```

- `describe` の宣言は中のテストに引き継ぐ。`it` の宣言が優先する
- 機能ファイルでは `@premise:authorize/par-pushed` のタグにする
- 一つのテストが同じエンドポイントへ何度もリクエストするときは、最後のリクエストを採る。準備のリクエストが先に来るからである。別のものを採るときは `// @premise authorize/par-used #2` と番号を書く
- E2E テストは、通るエンドポイントごとに宣言できる（`// @premise authorize/par-pushed token/code-pkce`）。E2E の記録にはリクエストの URL があるので、GET の `/authorize` はクエリまで出せる

宣言の無い API テストは「未分類」として数える。
未分類は検査で落とさず、数を画面と PR のコメントに出す。
一覧に無い id を宣言したとき、同じ id の定義が重なるときは、`.github/scripts/lint-tests.mjs` で落とす。

## 3. 観測した道筋

PR #207 の記録（`packages/test-reach/src/exchanges.js`、`exchanges/vitest-<pkg>.jsonl`）を土台にする。
記録一件は、リクエスト、応答、その間に動いた文・分岐・関数の計数（ファイルと行）を持つ。

想定リクエストごとに、次を求める。

- **代表の例**：宣言したテストのリクエストと応答。複数あれば、成功したテストのうちファイルと行の順で最初のもの。ほかは「ほかの例」として持つ
- **動いた行**：ファイルごとの行の範囲。アウトラインの行とコードリーダーの印に使う
- **ステップの状態**：下の規則で決める
- **選んだ側**：動いた行から決まる決定の側（PR #207 の `packages/test-catalog/src/examples.ts` の読み方）。フローの再生に使う

木のノードは行の範囲を持つ（`FlowTree`）。
ノードが動いたかは、そのノード自身の行に動いた文があるかで決める。
決定の側を読めない場所があっても、行の印は付けられる。

### ステップの状態

| 状態 | 規則 |
|---|---|
| 通らない | そのステップのブロックの文が一つも動いていない |
| ここで失敗 | ステップの中から例外が出た（PR #207 の `failed`） |
| ここで応答 | パイプラインがそのステップの後の `return` で終わった |
| 素通り | ステップの関数が、最後の文より前の `return` で終わり、その `return` が値を返さないか、`undefined`、`null`、自分の引数の名前をそのまま返す |
| 働いた | 上のどれでもない |

素通りの規則は、機能のステップの書き方に合わせてある。
`resolvePushedAuthorizationRequest()` は、`request_uri` が PAR の URN でなければ `if (pushedParams === null) return params;` で終わる。
`resolveFormPostResponseContext()` は、`response_mode=form_post` でなければ `undefined` を返す。
規則で読めないステップは「働いた」に倒す。
素通りと誤って畳むと処理を見落とすが、働いたと誤っても一行増えるだけだからである。

同じ想定リクエストを宣言したテストの間でステップの状態が食い違えば、ビルドが警告する。
その想定リクエストは二つに分けるべきだという合図である。

### データ

- `apps/tests/public/data/tests/premises/<hash>.json`：エンドポイント一つ分。想定リクエストごとに、定義、宣言したテストの id、代表の例とほかの例、ステップの状態、選んだ側、基準との違い
- `apps/map/public/data/premises/<framework>--<endpoint>.json`：同じ内容から、地図が使う分（定義、代表の例、ステップの状態、選んだ側、動いた行）
- 索引（`tests.json`、`map.json`）には、エンドポイントごとの想定リクエストの数と url だけを置く

計測した実行が無いビルド（手元の `pnpm run build:map`）では、定義と宣言だけが入る。
道筋は「計測なし」と表示し、いまの道筋の選択へ案内する。

## 4. 地図の画面

エンドポイントの画面の最初の選択を、想定リクエストにする。
いまの「道筋を選ぶ」は「コードの分岐から選ぶ」として残す。

```
認可エンドポイント  GET | POST /authorize                       [コードを読む ↗]  [テスト ↗]

想定リクエスト  [ PAR でプッシュ済みの request_uri を渡す ▾ ]    --enable par    テスト: API 2 · E2E 1
基準（認可コード + PKCE）との違い: ステップ 2「プッシュされた request_uri を展開する」が働く

① リクエスト                 ② 処理   働いた 6 · 素通り 9 · 通らない 5           ③ レスポンス
GET /authorize               1  認可リクエストを解析する          → params        302 Found
  ?client_id=test-client     2  プッシュされた request_uri を展開する   [par]      Location: /login
  &request_uri=urn:ietf:…         PAR の URN か → 成立                              ?transaction_id=…
                                  ストアから取り出して消す（1 回限り）             Set-Cookie: …
前提                              プッシュ済みのパラメータに置き換える → params
・/par でプッシュ済み        3  クライアントを特定する            → client
・未使用、期限内             ⋯  素通り 2: request_uri の取得、Request Object の検証
                             6  redirect_uri を確定し、エラーの返し先を決める
                             ⋯  素通り 3: JARM、form_post、フラグメント
                             10 リクエストのパラメータを検証する
                             ⋯  素通り 2: インプリシット、ハイブリッドの検証
                             13 認可トランザクションを作って保存する
                             ⋯  素通り 4: prompt=none の併用、id_token_hint、prompt=none、SSO
                             18 ログイン画面へ進む               ← ここで応答
```

- ② の行は、いまのアウトラインの行と同じ言葉である（`apps/map/src/lib/words.ts`）。違いは、動いた行だけを出すことである。いまは通らない行を灰色で残すが、想定リクエストの表示では出さない
- 働いたステップは開いた状態で、その中の動いた行を二段まで出す。それより下は ▸ で開く
- 素通りのステップは「素通り n」の一行に畳み、開くと、どの `return` で終わったかを言う（「`request_uri` が無い → `params` をそのまま返す」）
- 通らないステップは出さず、数だけ言う
- 「全部の行を出す」で、いまのアウトライン（通らない行は灰色）に切り替える。レビューで、通らなかった分岐を確かめるためである
- ① と ③ は代表の例をそのまま出す。長い値（JWT、トークン）は省略し、押すと開く。複数の例は ‹ › で切り替える
- 「比べる」で、もう一つの想定リクエストを選ぶと、状態の違うステップだけに印を付けて左右に並べる
- フロー（`;p`）は、想定リクエストを道筋として再生する。選んだ側は観測なので「仮」の札は出ない
- ハッシュに想定リクエストを書く（`#hono--authorize;r=par-pushed`）

想定リクエストの一覧（選択を開いたとき）は、まとまりごとに並べ、期待する結果とテストの数を添える。
テストの無いものには「テストなし」と出し、選ぶと定義だけを表示する。

変えるファイルの見当は次のとおりである。
`src/components/EndpointScreen.tsx`、`SelectionBar.tsx`、`Trace.tsx`、`FlowPlayer.tsx`、`src/lib/trace.ts`（行を出すかどうかに「動いた行」を足す）、`src/lib/playback.ts`、`src/lib/hash.ts`。

## 5. テストの画面

エンドポイントのページの最初のタブを「想定リクエストで見る」にする。
「テスト一覧」と、いまの「ケースで確かめる」（コードの道筋ごと）は残す。

```
想定リクエスト                               期待する結果                    API  E2E  ユニット  状態
基本
  認可コード + PKCE で送る（未ログイン）      ログイン画面へ                   3    6    42      ✓
  ログイン済みで同意もある                    認可コードを返す                 2    4    51      ✓
PAR                                                                 --enable par
  PAR でプッシュ済みの request_uri を渡す     ログイン画面へ                   2    1    38      ✓
  使用済みの request_uri を渡す               invalid_request_uri（画面）      1    0     8      ✓
  期限切れの request_uri を渡す               invalid_request_uri（画面）      0    0     8      ✗ リクエストのテストなし
…
未分類の API テスト 9 件
```

- API と E2E は、その想定リクエストを宣言したテストである
- ユニットは、その想定リクエストで働いたステップの関数のユニットテストである。素通りと通らないステップのユニットテストは数えない
- 状態は規則で決める。✓ は宣言したテストがあり、`check` と観測が合う。✗ は宣言したテストが無い。△ は `check` と観測が食い違う、または宣言したテストの間で道筋が食い違う
- 行を選ぶと、地図と同じ ① ② ③ と、そのテストの一覧を出す
- 表の下に「入力の網羅」を出す。パラメータごとに、API と E2E のテストが実際に送った値と件数を並べる（`response_type`: `code` 14、`id_token` 6、`code id_token` 5 …、`prompt`: 無し 31、`none` 7、`login` 2）。正解を定義しなくても、どの入力を試したかは事実として見える

PR のビルドでは、この表に PR の印を付ける（追加した想定リクエスト、道筋が変わった想定リクエスト）。

変えるファイルの見当は次のとおりである。
`packages/test-catalog/src/`（`premises.ts` を足す。`read-code.ts`、`read-feature.ts`、`model.ts`、`build.ts`）、`apps/tests/src/components/EndpointPage.tsx`、`CasePanel.tsx` の隣に新しい部品。

## 6. コードを読むページ

動きが分かった後に、コードの中身を速く読めるようにする。
地図と同じ Worker の `/code/` に、別タブで開くページを足す（`apps/code`、または `apps/map` の別エントリ）。

- 地図とテストの画面の「コードを読む ↗」「`</>`」から、ファイルと行を指して別タブで開く（`/code/#apps/hono/src/oidc-provider/features/par/steps/resolve-pushed-request.ts:L52-L74;r=authorize/par-pushed`）
- 左にファイルの木（地図の根だけ）と、想定リクエストを選んでいれば「このリクエストで動いたファイル」を通る順に並べる
- 本文は、ビルド時に Shiki で作ったハイライト済みのソースを読む（いまの `sources/<hash>.json` をそのまま使う）。ブラウザでは解析しない
- 想定リクエストを選ぶと、動いた行に印を付け、動かなかった行を薄くする
- 関数の名前を押すと定義へ移る。呼び出し元の一覧も出す。第一段は関数カタログの `calls` と `calledBy` で引く。第二段で、ビルド時に TypeScript の型検査器から「識別子 → 宣言の場所」の表を作り、型や定数にも飛べるようにする
- PR のビルドでは、変わった行に印を付ける
- 手元のエディタで開くリンクを添える。設定にリポジトリのパスを入れると、`zed://file/<パス>:<行>` と `vscode://file/<パス>:<行>` のリンクが出る。未設定なら `https://github.dev/...` を出す

自前のページにする理由は、ハイライト済みのソースと呼び出し関係が、すでにビルドの出力にあるからである。
GitHub より速く、手元の準備が要らず、動いた行の印はほかの道具では出せない。

## 7. PR

### 地図の「このPRの変更」

先頭に「この PR で動きが変わる想定リクエスト」を置く。

- **足した想定リクエスト**：YAML の差分で分かる
- **動きが変わる想定リクエスト**：その想定リクエストで動いた行と、PR が変えた行が重なるもの
- **どの想定リクエストも通らない変更**：変えた行のうち、どの想定リクエストでも動かなかった行。リクエストの単位では確かめられていない変更なので、レビューで見る場所になる

それぞれから、変えた行に印を付けた想定リクエストの表示へ移れる。
いまの関数の一覧と届く経路は、その下に残す。

### PR のコメント

コメントは 30 行以内を目安にし、一覧はすべて地図へのリンクにする（`packages/map-analysis/src/changes.ts` の `changesMarkdown()`、`packages/test-catalog/src/markdown.ts`、`.github/workflows/ci.yml` の本文の組み立て）。

```md
## OIDC Provider Map

**DPoP（RFC 9449）を拡張機能として加える** — 変更メモの一段落目（300 字まで）

**動きが変わるリクエスト**（足した 14 · 変わる 3 · 変わらない 61）
- 足した: /token「DPoP proof を付けて認可コードを引き換える」→ DPoP トークンを返す
- 足した: /userinfo「束縛したトークンを Bearer で提示する」→ invalid_token
- 変わる: /authorize「認可コード + PKCE で送る」— 認可トランザクションを作って保存する
- ほか 14 件 → 地図

**確かめること**
- 説明の無い変更 0 · テストを変えていない変更 0
- リクエストのテストが無い想定リクエスト 2 · どの想定リクエストも通らない変更 3 か所

**開く**
[変更](…#changes) · [テスト](…/tests/#/pr) · [Codecov](…)

<details><summary>変わった関数 154（追加 110 · 変更 43 · 削除 1）</summary> … </details>
```

- 関数の表、関数の外の変更があるファイルの列挙、エンドポイントごとのテストと関連関数の列挙は、本文から外す。`<details>` に入れるか、地図だけに置く
- テストの期待の変更は、変わった語だけを出す（いまは期待の全文を前後とも出す）
- 検査が落ちたときの「説明の無い変更」と雛形は、いまのとおり先頭に出す
- 末尾の英語の説明文（`Built from … The map shows …`）は一行にする

想定リクエストがまだ無い段階でも、この形の「確かめること」と「開く」は先に入れられる。

### PR の本文

人が読むのは、概要、実装したこと、影響の三つである。
`.github/pull_request_template.md` を足し、`skills/provider-map-implementation/SKILL.md` の「引き渡す」に同じ規則を書く。

```md
## 概要
何を、なぜ。2〜3 行。

## 実装したこと
利用者から見える単位で 7 項目まで。ファイルや関数の一覧は書かない（地図にある）。

## 影響
利用者に見える変化、互換性、未対応と制限。無ければ「なし」。

## 確認
地図: <プレビューの URL>#changes ／ テスト: <プレビューの URL>/tests/#/pr
```

- 実行したコマンドとテストの件数、レビューで直した項目の履歴、生成されるファイルの表は本文に書かない。要るものはコミットメッセージか変更メモに書く
- 本文は `<details>` の外で 40 行以内を目安にする。検査で落とすかは運用を見て決める

## 8. 仕様の要求の一覧（任意、後の段）

「テストは必要なパターンを満たしているか」には、正解の一覧が要る。
人が一から定義するのは難しいので、外にある一覧を取り込む。

- **OIDF の Conformance Suite の module**：このリポジトリは Basic、Implicit、Hybrid、Dynamic、Config の五つのプランを実行できる（`tests/conformance`）。module（`oidcc-ensure-request-without-nonce-fails` など）は、OpenID Foundation が定義した「このリクエストにはこう返す」である。プランごとの module の一覧を `tests/catalog/requirements/oidf-<plan>.yaml` に置き、想定リクエストに `satisfies: [oidcc-ensure-request-without-nonce-fails]` で結ぶ
- **仕様の MUST と SHOULD**：仕様の節ごとに、要求を一文ずつ書いた一覧（`tests/catalog/requirements/rfc9126.yaml` など）。実装するセッションが仕様から下書きし、人は抜き取りで確かめる。コードの `@spec` とステップの `spec` が節を持つので、節の単位では機械で照らせる

画面は、要求 → 想定リクエスト → テストの順にたどる表と、「結び付く想定リクエストの無い要求」の一覧を出す。
人の仕事は、正解を定義することから、仕様から作った一覧を確かめることに変わる。

## 貢献者に課す規則

足す規則は一つだけにする。

- API テストと E2E テストは、どの想定リクエストを送るかを `// @premise` で宣言する。宣言が無くても検査は落ちず、「未分類」として数に出る。一覧に無い id と重複した id は lint で落とす

想定リクエストの一覧（YAML）は、機能を足す PR が一緒に足す。
足さなくても検査は落ちないが、その機能のリクエストは地図で選べず、PR のコメントの「どの想定リクエストも通らない変更」に数が出る。
`skills/provider-map-implementation/SKILL.md` に、この二つを手順として書く。

## 決めていないこと

実装の前に、リポジトリの持ち主が決める。

1. 想定リクエストを YAML と宣言で持つか、記録から自動でまとめるだけにするか（YAML と宣言。自動のまとめは名前が付かず、「想定している一覧」にならない）
2. PR #207 をマージしてから始めるか、記録の部分だけを取り込むか（記録の部分は活かす。表示は 4 節と 5 節に置き換える）
3. コードを読むページを作るか、エディタへのリンクだけにするか（作る。データはすでにある）
4. 識別子の名前（`premise` は仮）
5. 仕様の要求の一覧を今回の範囲に入れるか（後に回す）
