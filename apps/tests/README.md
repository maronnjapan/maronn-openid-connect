# テスト（OIDC Provider のテストの一覧）

OIDC Provider にどんなテストがあるかを見るページです。
地図（apps/map）とは別のアプリで、地図と同じ Worker の `/tests/` で配信します。
実装の詳細：テストの読み取りから計測、PR の検査、この画面、CI までの作り方は [docs/README.md](docs/README.md) にあります。

## 見られるもの

- ホーム：テストの数（E2E / API / ユニット / ツール）、最新の実行の結果、正常系と異常系の割合、テストの種類と、エンドポイントごとのテストの数です。
  プルリクエストのビルドでは、一番上にその PR のテストへの一行と印の凡例が出ます（下の「この PR の印」）。
- テストの種類（`#/kind/e2e`・`#/kind/api`・`#/kind/unit`）：E2E は spec・シナリオのファイルごと（見出しの名前の順）、API はエンドポイントごと（Hono / Next.js）、ユニットはパッケージごとの一覧です。
  API のエンドポイントの後の「テストやアプリのルートへのリクエスト」は、テストが自分で登録したルートや、アプリの `/health`・運用者の API など、OP のエンドポイントではないルートにリクエストを送る API テストを、describe に書いた関数やクラスごとに並べます（関数が無ければ describe の名前、ファイルの順）。
  URL がコードに無く、パスが実行時に決まるリクエストだけの API テストは、最後の「パスが実行時に決まるリクエスト」に同じように並べます。
  `it.each` の表（テスト自身の配列、ファイルの定数、テストの支援モジュールの定数）のパスは、行ごとのリクエストとして読むので、`should hand OPTIONS $path to the provider` は表のエンドポイントそれぞれの API テストです。
  ユニットはモジュールを畳んで並べ、モジュールを開くと関数とテストの数が、関数を開くとそのテストが出ます。
- テストの種類、エンドポイント、検索、この PR の一覧の行には「対象」が出ます（ファイルのページの行には出ません）。
  ユニットテストは関数、API テストは確かめるエンドポイントとその後に関数（`POST /token · applyOidc（web/express）`）、E2E テストは通るエンドポイントの順（`/authorize → /login → /token`、計測した実行のリクエストの順）です。
  OP のエンドポイントに届かないリクエストは、届かない理由のラベルに続けて薄く示します：テストが自分で登録したルートは「テストのルート」（`テストのルート POST /token`）、アプリのエンドポイントではないルートは「アプリのルート」（`アプリのルート GET /health`）、URL がコードに無いものは「パスは実行時に決まる」とメソッドです。
  多くのエンドポイントにリクエストする API テストは最初の 3 件（エンドポイントのページではそのエンドポイントを先頭）と「ほか n 件」です。
  同じ名前の関数がほかにもあるときは、パッケージかモジュールのディレクトリを添えます。
  E2E テストの経路では、テストのコードがリクエストするエンドポイントを普通の色で、実行で通っただけのものを薄い色で示し、スマートフォンではリクエストするものと経路の長さ（`経路 6`）だけを示します。
  一覧の見出しが言っていること（手順の関数だけのユニットテスト、そのエンドポイントへの API テストのリクエスト）は省きます。
- エンドポイント：処理の流れ（手順）と手順ごとのユニットテストの数、そのエンドポイントのテストを E2E・API・ユニットに分けた一覧です。
  エンドポイントのテストは、その API・E2E のテストと、手順の関数のユニットテストです（Next.js の手順は、そのブロックが呼ぶ関数のユニットテスト）。
  ユニットテストの無い手順には「テストなし」と出ます。
  手順を選ぶと、その手順のユニットテストだけに絞り込みます。
  手順より下で届く関数（cookie、データベース、ストアなど）は「ほかの関数」に畳んであり、選ぶとその関数のユニットテストに絞り込みます。
  「コード」でエンドポイントの本体のコードを、手順の `</>` で手順のコード（Hono は手順の関数、Next.js は Route Handler の `// [手順]` のブロックと、そのブロックが呼ぶ関数）を横のパネルに開きます。
  手順の印が無く、呼ぶ関数も分からない手順（Route Handler に印の無い Next.js のエンドポイントの手順）には `</>` がありません。
- テストの詳細：タイトル（英語と日本語）、対象、結果（ターゲットごとの時間）、確かめていること（最初の 6 件）、送るリクエストと、コードです。
  コードは「テスト」「テスト対象」「ヘルパー」のタブで切り替えます。
  「テスト対象」は、ユニットテストはその関数、E2E・API・シナリオは確かめているエンドポイントのコードを先に、その後にテストが名前を挙げる関数のコードです。
  エンドポイントの API テストは、エンドポイントの本体の後に、テストのファイルが確かめるモジュール（`page.test.ts` なら `page.ts`）の関数のコードも並べます（HTTP の層）。
  エンドポイントに届かないリクエストのある API テストは、そのリクエストの一行（「テストのルート」など）と、それに答えるコード「ルートの実装」（describe が名前を挙げるアプリ・ルーター・関数を import から型でたどった宣言：`WebRouter`、`createOperatorApp`、`createServerApp`。関数のカタログに無くても）を先に出します。
  describe が名前を挙げるのがテストの関数（カタログの関数）なら、その関数のコードです。
  E2E テストは開いたエンドポイントのページのエンドポイント（なければテストのコードがリクエストする最初のエンドポイント）から開き、実行で通っただけのエンドポイントは薄く示します。
  詳細の「対象」の名前を選ぶと、「テスト対象」でそのコードを開きます。
  「ヘルパー」は、テストが自分で呼ぶヘルパーを並べ、そのヘルパーが中で呼ぶヘルパーを下に畳みます。
  シナリオではタブが「ステップ 12 · ヘルパー 5」のように中身を言い、ステップの定義と、ステップの定義が呼ぶヘルパーを並べます。
  ツールのテストには「テスト対象」のタブがありません。
- ファイル：テストのファイルの一覧と、ファイルごとのテストとコードです。
  テストを選ぶと、横のコードでそのテストの行に印が付きます（スマートフォンでは詳細が開きます）。
- この PR：プルリクエストのビルドでは、削除・変更・名前の変更・追加したテスト（少ないものから）と、関連するテストが変わっていない実装の変更です。
  上の数のタイルを選ぶとその節へ移ります。節の見出しが状態を言うので、行は左の線だけで、ラベルと色を付けません。

テストの不足のうち画面に出すのは、ユニットテストの無い手順だけです。
ほかの不足（`tests.json` の `gaps`）と、対象や観点を読めなかったテストの数（`unknown`）はデータに残し、画面には一覧にしません。

画面はすべて URL のハッシュ（`#/endpoint/hono/token` など）で開けます。
横のパネルは、テストを `?test=<id>`、コードを `?code=fn:<関数の id>`・`?code=endpoint:hono:token`・`?code=step:hono:token:<手順>` で開きます。

### この PR の印

プルリクエストのビルド（`tests.json` の `diff: true`）では、`tests/diff.json` を一度だけ読み、PR が触れたテストに印を付けます。

- 一覧の行（エンドポイント、テストの種類、ファイル、検索、この PR、手順の絞り込み）は、行全体の薄い色、左の 3px の線と、タイトルの前のラベルで示します：追加（緑）、変更（黄）、削除（ローズ）。
  名前を変えたテストは変更で、タイトルの下に「旧名」を薄く出します（取り消し線は削除の印なので使いません）。
  成功・失敗のアイコン（✓ ✗）はそのままで、印は色だけでなく必ず言葉を持ち、削除の色は失敗の赤と分けています。
  テストのコードで開いたテストの行の印は、変更の黄と分けて中立の青です。
- 削除したテストは、元の場所に取り消し線の行で出て、何を確かめていたか（「対象」）も出ます：エンドポイントでは API・E2E はそのエンドポイント、ユニットは describe に書いた関数か宣言した関数（diff のカードの `functions`。期待値で結果を確かめただけの関数 `calls` では置きません）、テストの種類ではその種類（ユニットは `functions` と `calls` の関数ごと）、ファイルではそのファイル。
  選ぶと小さなパネルに、タイトル、対象、ファイルと行（PR の前の行）、describe、種類、正常系・異常系を出します（コードはありません）。
- 変更したテストの詳細には「この PR での変更」（名前・期待・対象・リクエスト・本体）を出し、確かめていることでは加えた期待を「＋」で緑に、外した期待を「−」で取り消し線で示します。
  名前を変えたテストは旧名を、追加したテストは「追加」のラベルを出します。
- 一覧の「この PR の変更だけ」で、変わっていないテストを隠します（ハッシュの `changed=1`）。
- 数は 0 でない部分だけを出します（`+1 −1`）。ホームの PR の一行と凡例は 3 つとも言葉で（`追加 314 変更 0 削除 0`）出します。
  エンドポイントの見出しでは、結果の横ではなく別の行に「この PR 追加 8 変更 3 削除 3」のボタンを出し、選ぶと一覧を変わったテストだけにして一覧へ移ります。
  ホームのエンドポイントのカードとテストの種類のカード、テストの種類のページのリンク、ファイルの一覧（ルートの見出しとファイル名の横）、一覧の種類の見出しに数を、手順にはその手順で変わったユニットテストの数を点で出します（状態が混ざるときは灰色）。
  スマートフォンのファイルの一覧は、PR で変わったテストのあるルートを開いた状態で出します。

## データ

データは地図のデータの手順（apps/map/scripts/build-data.mjs）が `apps/tests/public/data` に書き出します。
このアプリの `build` はデータを作りません。
リポジトリのルートで次のどちらかを実行してください。

```sh
pnpm run build:map
# 地図のパッケージをビルド済みなら、データだけ
pnpm --filter @maronn-openid-connect/map run data
```

データが無いときは、ページにこの手順を表示します。

## 開発

```sh
pnpm --filter @maronn-openid-connect/tests dev        # http://127.0.0.1:3620（PORT で変更）
pnpm --filter @maronn-openid-connect/tests build      # dist/ に public/data も含めて出力
pnpm --filter @maronn-openid-connect/tests preview
pnpm --filter @maronn-openid-connect/tests typecheck
pnpm --filter @maronn-openid-connect/tests test       # src/lib のテスト
```

## 配信

地図のビルド（`pnpm --filter @maronn-openid-connect/map build`）が、このアプリをビルドして `apps/map/dist/tests/` にコピーします。
地図の Worker（apps/map/wrangler.jsonc）がそれを `<地図の URL>/tests/` で配信するので、プルリクエストのプレビューにもこのページが付きます。
ページはデータを `./data/` から相対パスで読むので、`/tests/` のようにサブパスに置いても動きます。
