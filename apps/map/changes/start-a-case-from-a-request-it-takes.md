# ケースを選ぶと、地図の OP でそのケースを通ると確かめたリクエストから始める

フローの「道筋」でケースを選ぶと、「リクエスト」欄は、地図の OP でそのケースを通ると確かめたリクエストから始まる。
地図のビルドが、地図の OP が試すリクエスト（クライアントが送るリクエストと、それを一か所ずつ変えたもの）を順に動かし、テストのリクエストと同じ規則でケースに当てて、ケースごとに最初に通ったものを残す。
どのリクエストも通らないケースは、地図の OP がエンドポイントに応えたリクエストから始め、その旨を書く。
この欄はテストとは結び付けず、テストが送ったリクエストは出さない（テストの画面で読む）。地図のデータ（`requests/`）も、地図の OP で確かめたリクエストだけを持つ。

この変更は地図とその解析、地図の OP（`packages/map-sandbox`）、テストカタログだけを変え、関数カタログの関数とエンドポイントの処理は変えていない。

## 背景

リクエストを書いて実行すると通った道筋を再生できるようになったが、書き始めのリクエストは、計測したテストがそのケースで送ったものしか無く（`/token` の 135 ケースのうち 1 割ほど）、欄がテストのコードの記録に結び付いていた。
地図のリクエストの欄はテストと結び付けることを想定していない。
ケースごとのリクエストを手で書くと、コードと食い違ったまま残る。
地図の OP で実際に動かし、テストの例と同じ規則で通ったと確かめたものだけを残せば、選んだケースを必ず通るリクエストから始められる。
いまは `/token` で 135 ケース中 29 ケースに見つかる。残りは、デバイスコードや CIBA の状態、署名したアサーションなど、前提に無い値が要るケースである。
