private_key_jwt のクライアント認証（OIDC Core 1.0 §9、RFC 7523 §3）と、`request_uri` による Request Object の取得（OIDC Core 1.0 §6.2、RFC 9101 §5.2）の部品を追加し、署名鍵のキャッシュを破棄できるようにする

- クライアントアサーションの検証を、責務ごとの関数として追加する。`decodeClientAssertion()`（JWS の分解。`crit` と空の署名を拒否）、`validateClientAssertionAlg()`（`none` と HS 系、登録した `token_endpoint_auth_signing_alg` と違う alg、受け付けない alg を拒否）、`validateClientAssertionClaims()`（`iss` と `sub` が client_id、`aud` にエンドポイントの URL か issuer、`exp` 必須、`iat` と `nbf` は時計のずれ 60 秒を許して検査、`jti` 必須。個別の `validateClientAssertionSubject()`、`validateClientAssertionAudience()`、`validateClientAssertionTimes()`、`requireClientAssertionJti()` も公開する）、`loadClientAssertionKeys()`（`ClientKeyResolver` の `private_key_jwt` の用途から `kid` で鍵を読む。`ClientJwksUriError` は固定文言の `invalid_client` に変える）、`verifyClientAssertionSignature()`、`consumeClientAssertionJti()`（`ClientAssertionJtiStore` に client_id と `jti` を期限まで記録し、2 回目を拒否する）。どの失敗も `invalid_client` になる。定数 `CLIENT_ASSERTION_TYPE_JWT_BEARER`、`SUPPORTED_CLIENT_ASSERTION_SIGNING_ALGS`（RS256、RS384、RS512、ES256、ES384、ES512）、`DEFAULT_CLIENT_ASSERTION_LEEWAY_SECONDS` も追加する
- 型の拡張: `ClientAuthMethod` に `'private_key_jwt'` を、`TokenClientInfo` に `tokenEndpointAuthSigningAlg` を、`PresentedClientCredentials` に `clientAssertion` を足す。`ClientAuthMethod` を網羅する `switch` を書いている利用者は、`'private_key_jwt'` の分岐が要る
- 挙動の変化: `extractClientCredentials()` は `client_assertion_type` と `client_assertion` を先に読み、あれば方式 `private_key_jwt` として返す。片方だけのリクエストと、Basic 認証か `client_secret` との併用は `invalid_request`、jwt-bearer 以外の `client_assertion_type` は `invalid_client` で拒否する。これまではこの 2 つのパラメータを無視していた。`client_id` が無ければアサーションの `sub` を client_id にする（RFC 7521 §4.2）。アサーションの無いリクエストの扱いは変わらない。`validateClientAuthMethod()` は private_key_jwt のクライアントにシークレットの登録を求めない。補助の `extractClientAssertion()`、`validateClientAssertionNotCombined()`、`resolveClientAssertionClientId()` も公開する
- 挙動の変化（セキュリティ）: `verifyClientSecretValue()`（`clientSecretHash` を登録していないクライアントの `verifyClientSecret()`）は、提示されたシークレットが無いか空文字列なら比べずに `invalid_client` で拒否する。これまでは提示値も登録値も無いときに一致したものとして扱い、提示の有無の確認を `validateClientAuthMethod()` に頼っていた。`validateClientAuthMethod()` は private_key_jwt の提示にシークレットを求めないので、`extractClientCredentials()`、`resolveAuthenticatedTokenClient()`、`validateClientAuthMethod()`、`verifyClientSecret()` の順に呼ぶ既存のコードが、シークレットを持たない private_key_jwt のクライアントを、アサーションを検証せずに通さないようにするためである。private_key_jwt のクライアントは、`verifyClientSecret()` ではなくクライアントアサーションの検証で認証する
- `buildProviderMetadata()` に `tokenEndpointAuthSigningAlgValuesSupported` を足し、`token_endpoint_auth_signing_alg_values_supported` を出す（`none` を含む設定は例外）。渡さなければ出さない
- `request_uri` の部品を追加する。`validateRequestUri()`（既定 512 文字まで、https の公開ホスト。宛先の検査は `validateClientJwksUri()` と同じ）、`requestUriFetchUrl()`（フラグメントを除く）、`matchesRegisteredRequestUri()`（登録した `request_uris` との完全一致）、`fetchRequestObjectByReference()`（`Accept: application/jwt` の GET。リダイレクトに従わず、タイムアウト既定 3 秒と本文の上限既定 64 KiB を持ち、`fetch` を注入できる）、`resolveRequestUriParams()`（`request` との併用は `invalid_request`、未登録と取得の失敗は理由を含まない `invalid_request_uri` で拒否し、取得した JWT を `request` に置き換えたパラメータを返す）、`RequestUriError`、`isRequestUriError()`、`DEFAULT_REQUEST_URI_OPTIONS`
- `rejectUnsupportedRequestParams()` に `requestUriParameterSupported` オプションを足す。true のときだけ `request_uri` を通し、`request` との併用は `invalid_request` にする。オプションを渡さなければ、これまでどおり `request_uri_not_supported` で拒否する
- `createCachedSigningKeyProvider()` の戻り値を `CachedSigningKeyProvider`（`SigningKeyProvider` に `invalidate()` を足したもの）にする。`invalidate()` でキャッシュを捨てると、次の呼び出しから元のプロバイダーの新しい鍵を使う（運用中の鍵ローテーション。OIDC Core 1.0 §10.1.1）。`SigningKeyProvider` として使う既存のコードはそのまま型に合う
