# OIDC Provider Map

生成される OpenID Provider の地図。
`maronn-oidc generate` のフレームワークと機能を選ぶと、その構成のエンドポイントを一覧し、エンドポイントの処理を呼び出しの先まで一つの画面でたどれる。
PR の地図では、その PR が変えた関数がエンドポイントから何段下にあっても、何を変えたか（構造と式の差分）と差分のコードをその場で読める。

設計の考え方は [docs/design-change-trail-and-decision-cases.md](docs/design-change-trail-and-decision-cases.md) にある。

## トレース：エンドポイントの処理を根にした木

エンドポイントの画面の中心はアウトラインで、エンドポイントの処理本体（hono の pipeline のハンドラー、Next.js の Route Handler）を、上から下へ一行ずつ読む。
一行は処理の流れの木のノード一つ（決定の側一つや、言葉の無い文の続き一つのこともある）で、まずその処理が何をするかを自然言語で書き、コードは言葉が無いところにだけ出す。

- ステップ：`// [step-id]` の印で囲んだブロックは、その見出し（「クライアントを認証する」）の一行に畳む。▸ で中を開く。中身がフレームのある関数の呼び出し一つだけのステップ（hono のステップ）は、その呼び出しの行になり、▸ でその関数の流れを開く
- 呼び出し：呼び先の関数の JSDoc の一行目（lint が求めるもの）、resolver や store のメソッドなら interface のメンバーの JSDoc
- 条件や処理：文の手前のコメント。条件が真偽を返す関数の呼び出し一つ（`if (!isPublicTokenClient(client))` のような否定を含む）なら、その関数の JSDoc を条件の形にした言葉（「パブリッククライアントか」）。どちらも無ければコード（`if (!keys)` など）で、コードから作った条件の言葉は行に重ねたときの表示に出す
- 言葉の無い文の続き：変数の定義や代入のように言葉の無い文が二つ以上続くところは「コード n 行」の一行にまとめ、何を用意するか（「`a`、`b` を用意する」）か、何に入れるか（「`x.y` に入れる」）を書く。ほかの文が混じれば「処理: …」と並べる。▸ でその文を一行ずつ開く。一つだけの文と、PR が変えた文はまとめない
- 終わり：`return` と `throw` には「終わり」「失敗」の札を付ける。`return` は、呼び出しをそのまま返すならその関数の JSDoc で、名前を返すなら「`x` を返す」「`a`、`b` を返す」と言う。コールバックの中の `return` はフレームを終えないので、札を付けない
- 守り（`if (!client) throw ...`）と任意項目の `if` は、`if (!client) → 失敗: TokenError(invalid_client) を投げる` のように一行で読む。ただし、その `if` か中を PR が変えたとき、成立側でフレームのある関数を呼ぶとき（その関数を開けるように）、成立側に決定があるときは、畳まずに全部の行を出す
- `try` は「ここから例外を捕まえる」の見出しの下に、捕まえる範囲の行を一段下げて並べ、最後に「例外が起きたとき → …」の行を置く

ざっと眺められるよう、どの行も一行に収める。
収まらない言葉は省略し、全文は行に重ねたときの表示と `</>` で読める。
`</>` はその行のコード、詳しい説明（コメントの全文、メソッドの説明と実装）、PR の変更の全部を開く。
上の「言葉 / コード」は、全部の行を言葉の一行かコードの一行に切り替える（コードにすると、言葉の無い文の続きも一文ずつに戻る）。
選んだ表示はこのブラウザに残る。
PR の変更は、札の横に一つ目の変更（「`<` を `<=` に変えた」）を同じ行で示し、「エラー時」の捕まる先（「失敗 → POST /token の catch」）も同じ行に出す。
条件や `throw` の直前に呼ぶ関数と、`return` がそのまま返す呼び出しは、その行が受け持ち、▸ でその関数を開ける。
ほかに先に評価する呼び出しは、その行の上に「先に」の行として出す。

呼び出しの ▸ を押すと、呼び先の関数の流れをその場で一段下げて開く。
何段でも開け、再帰はその関数の二度目で止める。
↗ はその関数を根にしたトレース（関数のページ）へ移る。
型で呼び先を引けない呼び出しは「追えない呼び出し」と示し、理由を添える。

行を押すと、その行を選び、右の欄がその行のフレームに移る。
欄のタブは変えず、図ならその行の箱を囲んで見える所まで動かし、詳細ならその行の説明を足す。
別の関数の行なら、図の上のパンくず（`POST /token › authenticateTokenClient()`）が今どこを見ているかを示す。

### 決定を選んでたどる

決定の行には進む側のボタン（成立 / 不成立など）が並び、側の行（「成立」「例外が起きたとき」）を押しても選べる。
選ぶと、その側の行は活性のまま、ほかの側の行と、選んだ道筋では通らない後の行が灰色（不活性）になる。
行は消さないので、どこが選ばれていないかが見える。
もう一度押すと選択を外し、すべての行が活性に戻る。
子フレームの決定も同じ仕組みで選べ、エンドポイントから下の関数まで一本の道筋が決まる。
選んだ決定を中に持つステップは開く。

呼び出しには「ここで失敗する」という側もあり、よく使う選択の「失敗で終わる」がこの側を選ぶ（ハッシュでは `;d=s0b1s0:fails`）。
そう選んだ呼び出しの行には「ここで失敗」の札が付き、同じ並びの後の行は灰色になる。
失敗は、そのフレームでその呼び出しを囲む `catch` のある `try` のうち最も内側のものへ進み、その `catch` を通って `try` の後から続く。
そういう `try` が無ければ、フレームはそこで終わる。

機能のオン・オフはノードの機能の札で絞る。
オフの機能のブロックは木から外し、そのブロックが作る値を読む条件は値の無い側だけを残す。

### よく使う選択

画面上部の「よく使う選択」に、木から計算した選択を並べる。
選ぶとその決定の組み合わせになり、複数選ぶと和集合になる。
「すべて表示」で選択を外す。

- ステップ：エンドポイントの各ステップに至る決定。名前はステップの見出し（`/token` なら「refresh_token グラントを検証する」「authorization_code グラントを検証する」）
- 変更に至る道筋：PR の地図で、変えたところに至る決定。名前は変えた関数と通るステップ（「sign()（device_code を引き換える から）」）で、何を変えたかを添える。関数の中の二か所以上を変えたときは、変えたところごとに並ぶ（同じフレームを開いて同じ側を選ぶものは一つにまとめ、変えたところを並べて添える）。フレームをまたぎ、選ぶと間の呼び出しを開いて、変えた行を選ぶ。オフの機能を通る道筋は並べない
- 終わり方：`return` と本体の終わりごとに、そこへ至る決定。名前は区別に要るラベル（Next.js の `/token` なら `!keys: 成立`）だけで、守りを不成立で通った事実は書かない
- 失敗で終わる：`throw` と、呼び先から伝わる失敗。エラーごとにまとめ、呼び先からのものは「`verifyClientSecretHash` から」と投げる関数で示す。選ぶとその `throw` までのフレームを開き、途中の呼び出しをどれも「ここで失敗する」側にする

選択は木をたどって求めるので上限が無く、道筋の列挙や名前の無い「exit ケース」は無い。

### 失敗の流れとエラー時

関数がどう失敗するかは、JSDoc の `@throws` に頼らず木から求める。
`try` の外の `throw` と、`try` の外で呼ぶ関数の失敗を、カタログ全体で不動点まで集めたものが、その関数から外へ出る失敗である。
`catch` で受けた例外をそのまま投げ直す `try` は、捕まえなかったものとして数える。

「エラー時」をオンにすると、各呼び出しに「失敗すると → どこで捕まるか」を出す。
捕まる先は、トレースを上へたどって最初に見つかる `catch` である（`/token` なら根のフレームの `catch` と `respondTokenError`）。

### 図と詳細

アウトラインの右の欄に、図、差分、詳細、テストのタブを置く（関数のページでは、図の前に呼び出し元）。
欄は図のタブで始まり、読者が選んだタブをそのまま保つ。
アウトラインの行や図の箱を選んでも、タブは変わらない。
どのタブも、図が見せているフレーム（パンくずの最後）について述べる。

- 図：そのフレーム一つ分の流れの形を一行の箱と矢印で描き、選んだ道筋を青にする
- 差分：そのフレームと、アウトラインがその下に開いているフレームのうち、この PR が変えたものの差分を実行順に並べる。interface のメンバーの呼び出しの先で変えた実装は、その呼び出しの位置に、メンバーの実装の行の範囲で並べる
- 詳細：何も選んでいなくても、そのフレームの説明（JSDoc、場所、仕様、失敗するとき、PR の変更、「コードを見る」、根でない関数なら「この関数を根にして開く」）を出す。行か箱を選ぶと、その下に選んだ行の説明（コード、行の範囲、呼び先の JSDoc、interface のメンバーの説明と実装、ステップなら受け取る値と次へ渡す値）を足す
- テスト：そのフレームのテスト（後の「テスト」の節）。行を選ぶと、その行が呼ぶ関数のテストになる

図はアウトラインと同じ畳み方と言葉で、流れの形を描く。
ざっと眺められるよう、箱はどれも一行で、高さはそろえる。

- 箱の見出しはアウトラインの行と同じ言葉（ステップの見出し、呼び先の JSDoc、コメント）で、言葉が無いところはコード。収まらない分は省略する
- 終わり方は行を増やさず、見出しの末尾の札で示す（`→ 終わり`、赤の `→ 失敗`、いくつもあれば `×3`）
- 守りと任意項目の `if` は、アウトラインで一行になるものだけを一つの箱にし、すぐ終わる側は札にする。分かれ道の側、`switch` の case でも、すぐ終わるものは札にする
- 言葉の無い文が続くところ（変数の用意など）は一つの箱にし、何を用意するかを見出しにする
- `try` は箱にせず、捕まえる範囲を枠で囲み、枠の見出しに例外が起きたときを書く（`→ 例外: 失敗`、`→ 例外は無視して先へ`）。すぐ終わらない `catch` は、枠から出る赤い矢印の先に描く
- エンドポイントの本体は、ステップ一つを一つの箱にする。フレームのある関数の呼び出し一つだけのステップは、その呼び出しの箱になる
- ステップは、アウトラインで開いているものが図でも開く。PR が変えたノード、下に開いたフレーム、選んだ決定を中に持つステップは開いた状態で始まる。アウトラインの ▸ / ▾ でも、カードの「その場で開く / 畳む」でも、開け閉めすると両方が同時に変わる
- PR が変えたノードは、ほかの箱に畳まない
- 決定と終わりは、箱、札、枠、畳んだステップのどれかに必ず入る（`src/lib/diagram.data.test.ts` が全フレームで確かめる）

箱を押すと、その箱を選んでアウトラインの対応する行を示すだけで、ほかの関数へは移らない。
箱に重ねる（キーボードでは箱に移る、タッチでは触れる）と、カードにコード、言葉の全文、終わり方の全部が出る。
関数の中へ潜るのはカードの「中の流れを見る」で行う。
カードには、その箱が受け持つ呼び出しのうちアウトラインで開けるもの（箱の呼び出し、条件や `return` のために先に呼ぶ関数、箱に畳んだ側の呼び出し）ごとに、このボタンが並ぶ。
ステップをその場で開いたり畳んだりするのは、カードの「その場で開く / 畳む」で行う。
図の上のパンくず（`POST /token › authenticateTokenClient()`）が、根から今見ている関数までの道を示し、押すとその関数の図に戻る。
パンくずが四つ以上になると、根と、今の関数とその一つ上だけを残して間を「…」にまとめ、押すと間の関数を選べる（スマートフォンでは三つ以上で、根と今の関数だけを残す）。

箱の幅は 320px で、横に二つ並ぶ段があるときだけ 200px にする。
幅は配置だけで決め、欄の幅では変えないので、どの画面でも同じ配置になる。
選んだ道筋で変わるのは色だけで、箱は動かない。

図は、箱の見出しが 11px 以上になる倍率で開く。
幅に合わせた倍率がそれより小さくなるときは 0.88 倍で開き、選んだ箱（なければ始まりの箱）を中央に置く。
アウトラインの行を押すと、図はその箱を囲んで見える所まで同じ倍率で動く（ほかのタブを開いているときは、次に図を開いたときにその箱から見せる）。
別の関数の行なら、図もその関数へ移る。
アウトラインと図の欄の幅は、間の仕切りをドラッグして変えられる（左右の矢印キーでも変わり、ダブルクリックで元に戻る）。幅はこのブラウザに残る。

図の色は 3 つに限る。
灰色は選んだ道筋で通らない部分、青は通る部分と選んだ箱、赤は `throw`、`catch` の行とエラーの矢印である。
PR の札（後の節）はこの 3 色を使わない。

図は Dagre で接続関係に沿って自動配置する。
図の上部の一行で、向き（↓ 縦 / → 横）、拡大縮小、「幅」（幅に合わせる）、「全体」（全体を表示）、「戻す」（開いたときの倍率と位置に戻す）を操作する。
縮尺の数値を押すと 100% に戻る。
ドラッグで移動し、ピンチ（スマートフォンとトラックパッド）で拡大・縮小する。
2 本指スクロールとマウスホイールは移動に使い、図にフォーカスすると矢印キーで移動、`+` / `-` キーで拡大・縮小できる。
Tab で箱へ移ると、その箱が見える所まで図が動いてカードが出る。Enter か Space で選び、Tab でカードのボタンへ進み、Escape でカードを閉じる。
これらの操作には `react-zoom-pan-pinch` を使う。

開いたフレームと選んだ決定は URL のハッシュに書くので、たどった道筋をそのままリンクで渡せる（`#hono--token/s0b1s0/s0b1s0.s2;d=s0b1s0.s1:true;f=s0b1s0.s2`）。
ステップを名指すリンク（`#hono--token--select-signing-keys`）は、そのステップの行を選んで見せ、そのステップかエンドポイントを足す機能がオフならオンにする。

## 関数のページ

関数を選ぶと、その関数を根にしたトレースを開く。
読み方はエンドポイントの画面と同じで、呼び出しの先をその場で開ける。
右の欄の「呼び出し元」タブには、使われるエンドポイント（その関数が処理の本体であるもの、その関数を置くファイルが実装するもの）、その関数に届くエンドポイントのステップ（間に挟まる関数を順に）、その関数を直接呼ぶ関数を並べる。
ほかのタブと同じく図が見せている関数について述べるので、呼び出しの中へ潜ると、潜った先の関数の呼び出し元になる。
呼び出し元へ移るときは、たどった経路を捨てて、その関数かエンドポイントのトレースを新しく開く。

## テスト

テストのカタログ（[`@maronn-openid-connect/test-catalog`](../../packages/test-catalog)）を、エンドポイントと関数に重ねる。
設計は [docs/design-test-catalog.md](docs/design-test-catalog.md) にある。
テストのデータは `map.json` の後に読むので、最初の表示はテストを待たない。
テストのデータが無い地図でもページは欠けず、テストのタブ、札、一覧のボタンが出ないだけである。

### テストのタブ

図がエンドポイントの根を見せているとき、タブはエンドポイントのテスト全体を述べる。

- 見出し：種類ごとの数（「テスト 1303（API 29 / E2E 30 / ユニット 1244）」）、最新の実行結果、正常系と異常系と観点ごとの数、根拠（静的に読んだもの、実行で到達したもの）
- 不足：規則で求めた不足（外へ出る失敗を検証するテストが無い、求める観点のテストが無い、どのテストも通らないステップ、ユニットテストが無い関数）
- API テスト：入力（リクエストのパラメーターと認証方式）、期待、観点、最新の表
- E2E：このエンドポイントを通るテストと、通るエンドポイントの順（到達の記録があればその順、無ければコードから読んだリクエスト）、実行先ごとの結果
- ユニットテスト：このエンドポイントが届く関数ごとのユニットテスト。関数を開くと、その関数のテストを読み込む

行を選ぶと、タブはその行が呼ぶ関数（ステップならその関数）について述べる。
関数について述べるときは、describe がその関数を名指すユニットテスト、正常系と異常系と境界値の数、不足、ほかに関連するテスト（期待の中で呼ぶもの、実行で到達したもの）を並べる。
一つの関数ではないステップ（Next.js の Route Handler のブロック）は、中で呼ぶ関数ごとにまとめる。
関数のページでも同じタブが、呼び出し元と並んで出る。

テストの名前を押すと、そのテストの札を開く。
札には、対象、仕様、期待結果、期待するエラー、リクエスト、シナリオの手順、根拠、結果、到達を出す。
「ソース」に切り替えると、テストのファイルの本文を、そのテストの行に地を付け、その行まで送って開く。
テストのファイルは大きいので、ハイライトせずに出す。

タブの上の「English / 日本語」で、テストの名前、手順、期待結果を英語か日本語訳に切り替える。
訳の無い記述は英語のまま出し、EN の印を付ける。
シナリオのキーワードは日本語のもの（機能、シナリオ、前提、もし、ならば、かつ）にする。
選んだ表示はこのブラウザに残る。

### アウトラインの札と左の一覧

アウトラインの行のうち、呼び出しかステップがユニットテストのある関数に当たるものに、灰色の札を付ける（「ユニット 9（境界値 1） 到達 38」）。
到達は、到達の記録（`MARONN_REACH=1` の実行）があるときだけ出す。
札に重ねると、正常系、異常系、境界値の内訳が出る。
スマートフォンでは境界値の部分を外す。

左の一覧の各エンドポイントには、テストの数と、実行結果があれば最新の結果を付ける。
失敗があるときだけ赤にする。

### テストの一覧

上の「テスト」（`#<framework>--tests`、`#tests`）は、テスト全体を一覧する。

- 数：種類、期待（正常系、異常系、期待結果が読めない）、観点、根拠、最新の結果ごとの数
- エンドポイントごと：表示しているフレームワークの実装（hono か nextjs）のエンドポイントごとの数、不足の数、最新の結果
- 機能ごと：機能が足すエンドポイントのテストと、そこを通る E2E の数、機能が足すステップの関数のユニットテストの数
- 不足：種類ごとに並べる。ユニットテストが無い関数は一度だけ挙げ、そこへ届くエンドポイントを添える
- 規則で読めなかったテスト：対象不明、期待結果が読めない、観点なし。ファイルと名前を並べる
- 日本語の訳が無い言い回し：訳の表に無い言い回しの数と一覧

上の欄の文字で、すべての一覧を絞る。
絞ると、名前かファイルが合うテストも並べる。
エンドポイントと関数の行は、そのページをテストのタブで開く。

## PR の地図：このPRの変更

PR の地図は、その PR が変えた関数とエンドポイントの処理本体に札を付ける。
札は灰色の濃淡で示す。

- `追加` `変更`：その関数を足した、またはコードを変えた。アウトラインでは、足した行と変えた行と、変えた関数を呼ぶ行にも付く
- `下で変更`：その呼び出しの先（さらに下を含む）のコードを変えた。interface のメンバーの呼び出しなら、表示しているフレームワークで動く実装か、その実装が呼ぶ先を変えた
- `説明` `移動` `メモ` `削除`：JSDoc だけ変えた、コードはそのままで別のファイルへ移した、コードは変えていないが変更メモが説明している、消した

下で変えたものがある呼び出しの行には、下で変えた関数の数と変更の集計（「下で変更 2（条件 +1、呼び出し 変更 1）」）を添える。
メンバーの呼び出しでは、変えた実装のうち、そのメンバーの実装の行の範囲にある変更だけを数える。
アウトラインの行と図の箱は、同じ規則で札を付ける（受け持つノードの札と、呼ぶ関数とメンバーの札のうち強い方）。

「変更まで展開」は、根から届くすべての変更まで、間の呼び出しを一度に開く。
深さと件数の上限は無い。
interface のメンバーの実装を変えたときは、そのメンバーを呼ぶ行まで開き、その行の「差分」で実装の差分を読む。

アウトラインでは、変えた行の札の横に一つ目の式の差分（「`<` を `<=` に変えた」「引数 `issuedAt` を足した」）を同じ行で示し、残りは「ほか n」として `</>` に並べる。
行の「差分」は、その行が受け持つノード（畳んだステップや一行の守りなら、その中のすべて）の hunk を、その行の下に開く。
フレームの宣言と JSDoc の変更は、そのフレームを開いた呼び出しの行に付き、根のフレームなら先頭の「宣言」の行に付く。
interface のメンバーの呼び出しの行の「差分」は、変えた実装の差分を、そのメンバーの実装の行の範囲で開く。
消したノードは、消した位置に打ち消し線で残す。

「このPRの変更」のページ（`#<framework>--changes`）は、先頭に説明の無い変更を並べる。
続けて、関連するテストに変更の無い実装の変更、テストを変えない理由が書かれた変更、変更メモ（PR 全体の説明と、関数に当たらない節）、変えた関数の一覧（足したもの、コードを変えたもの、…の種類ごと）、関数の外の変更、テストを置く。
右には、変更が届くエンドポイントと、そこへの経路の数を並べる。
見出しの下には、変えた関数の数、テストのファイルの変更の数、テストでもなく地図にも載らないファイルの変更の数を出す。
変えた関数ごとに次を置く。

- 自動要約：木の差分から作った言葉（「条件 `expiresAt <= now`: `<` を `<=` に変えた」「条件 `secret.length < 8` を足した（失敗で抜ける）」）と件数。新しく外へ出る失敗とそれを捕まえる場所（「catch で捕まえて `respondTokenError(…)` が応答する」）、外へ出なくなった失敗、実装を変えた interface のメンバー、この変更を呼ぶかもしれない追えない呼び出し（後の「影響範囲」）も添える
- メモ：変更メモの、その関数の節
- 差分：その関数の hunk を行の順に並べたもの。どのノードの変更かは、トレースの行で読む
- 届く経路：その変更に届くエンドポイント、ステップ、間の関数（メンバーを通るなら、そのメンバーと変えた実装）、決定の数、要る機能、新しい失敗が捕まる場所。関数の中の二か所以上を変えたときは、変えたところごとにまとめる。押すと、トレースが変更まで展開され、決定が選ばれ、要る機能がオンになり、変えた行を選んだ状態で開く
- 関連するテスト：その関数を対象にするか、到達するテストの数と、そのうちこの PR が足したか変えたもの。テストを変えない理由、新しく外へ出る失敗のうち期待するテストが無いもの、関連するテストの観点と期待するエラーの変化も添える

関連するテストに変更の無い実装の変更は、説明が要る変更（エンドポイントに届く実装の変更とエンドポイントの処理の変更）のうち、関連するテストをこの PR が足しも変えもしておらず、変更メモのその関数の節に `テストを変えない理由:` の行も無いものである。
地図の検査が落ちる。
テストの節は、テストケースの数の変化（種類ごと）、テストの数が変わったエンドポイント、足した、変えた、名前を変えた、消したテスト（名前は英語のまま）、変えた関数ごとの関連するテスト、新しく外へ出る失敗を期待するテストが無いものを並べる。
テストの結果とカバレッジの変化は Codecov のコメントに任せる。

### 木の差分

変更前の木も同じ解析で作り、変更後の木と枝ごとに、ノードの種類と正規化した要約で順序を保って対応づける。
対応づいたノードのコードが違えば `変更`、対応の無い変更後のノードは `追加`、対応の無い変更前のノードは消したノードである。
コメントと書き方（空白、末尾のカンマやセミコロン）だけの違いは、ノードの変更にしない。
コードがそれだけ違う関数は「コメントや書き方だけを変えた（木は同じ）」として一覧に載せ、CI の検査には入れない。
変えたノードは式の中まで比べ、演算子、リテラル、引数、呼び先の置き換えを言葉にする。
足した部分と消した部分は、ソースのその部分をそのまま引く（「`.trim()` を足した」）。
interface のメンバーの実装を持つノードの要約は、そのメンバーの名前から始める（「`AuthorizationCodeStorage.consume` の実装: …」）。
対応づかない書き換えは前後のコードを並べる。
差分の hunk は、変えた行の続きごとに、それを含む最小のノードに付け、前後の文脈の行はそのノードの行に収める。
どのノードにも属さない行（JSDoc と宣言）の変更は、フレームの始まりの変更として扱う。
呼び出し元には、下の変更の集計を上げる。

### 影響範囲

変更がどこに効くかは地図が計算する。

- 呼び先は TypeScript の型で解決する。interface のメンバーを通る呼び出しも追い、store や resolver の実装を変えると、そのメンバーの全呼び出し箇所に届く。実装の中から別のメンバーや関数を呼ぶなら、その先も同じように上へたどる（store の実装 → それを呼ぶ resolver の実装 → resolver のメンバーを呼ぶ core の関数 → エンドポイント）
- `apps/hono` の実装は Hono・Express・Fastify のエンドポイントにだけ、`apps/nextjs` の実装は Next.js のエンドポイントにだけ届く。`packages/` の関数はどちらにも届く
- エンドポイントごとに、変更までの経路（開くフレームと決定の組み合わせ）と、その経路に要る機能を求める。関数の中の二か所以上を変えたときは、変えたところごとに経路を求める
- 外へ出る失敗が増えたり減ったりした関数は、その変化を示す。新しい失敗には、経路ごとにどの `catch` が捕まえるか（どこでも捕まえずにエンドポイントの外へ出るか）を添える
- hono（Express と Fastify はその写し）と Next.js の写しは別々に数える
- 型で呼び先を引けない呼び出しは「追えない」と明示する。そのうち、変更へ上がる道筋にあるメンバーと同じ名前のメソッドを呼ぶものは、変更を呼ぶかもしれない呼び出しとして挙げる。届く経路と CI の検査には入れない

### 変更メモと CI

何を変えたかは木の差分が、どこに効くかは地図が示し、変更メモ（[changes/](changes/README.md)）には意図と背景を書く。
地図のビルドは、変更メモの見出しが名前を挙げる関数が実在するかを確かめ、コードを変えた関数で節の無いものを「説明の無い変更」として PR コメントの先頭に一覧する。
CI（`.github/workflows/ci.yml` の `map` ジョブの地図のビルド）を落とすのは、エンドポイントに届く関数か、エンドポイントの処理本体に説明の節が無いときと、それらの関連するテストをこの PR が足しも変えもせず、節に `テストを変えない理由:` の行も無いときである。
コメントや書き方だけの変更と、追えない呼び出しのほかからは届かない変更では落とさない。
本文の質は検査せず、自動要約を隣に並べる。
PR のコメントは、説明の無い変更（と足す節の雛形）、変更メモの要旨、変わった関数の表（札、関数、場所、自動要約、届くエンドポイント、メモの一行目）、新しい失敗が捕まる場所と追えない呼び出し、テストの節、プレビューの URL の順に並べる。

節の雛形は次のコマンドで作れる。
MAP_BASE からの差分で、まだ節の無い関数ごとに見出し（`## 名前 <!-- id -->`）と、自動要約と届く先の HTML コメントを書き、意図の欄を空けておく。

```bash
MAP_BASE=origin/main pnpm --filter @maronn-openid-connect/map changes:draft
```

## コードの Drawer

エンドポイントの見出しの「コードを見る」や、詳細と関数のページの「コードを見る」で、右からコードの Drawer を開く。
「表示するコード」で、エンドポイントのファイル全体、ステップの関数、そこから呼ぶ関数（core まで）を切り替える。
関数には JSDoc とオーバーロードを含め、元ファイルの行番号を表示する。
PR の地図で変えた関数は、「差分」と「変更後の全文」を切り替えられる。
Drawer は関数を単位に開き、アウトラインの一行のコードはその行の `</>` で読む。

TypeScript と TSX のハイライトは [Shiki](https://shiki.style/) でビルド時に生成する。
配色と背景は付属の `github-light` / `github-dark` テーマを使い、ページの明暗設定に従って切り替える。
ファイル全体を解析してから関数の範囲を表示するため、複数行のコメントや文字列の文脈を保つ。
差分の削除行は変更前、追加行と文脈行は変更後のファイル全体を解析した色で表示する。
ブラウザには Shiki を含めず、ハイライト済みのデータを必要なときだけ読み込む。

表示するのはリポジトリの全機能を含むソースで、Express と Fastify は生成元である Hono のソースを表示する。
閉じるボタン、Escape キー、Drawer の外側のクリックで閉じ、開いたボタンにフォーカスを戻す。

## スマートフォン

幅 900px 未満の画面では、アウトラインだけを表示する。
アウトラインの上の帯には、左上のメニューのボタンの横に、根の名前と「言葉 / コード」を置く。
図、差分、詳細、テスト（関数のページでは呼び出し元も）は、画面下のボタンからドロワーで開く。
図のドロワーは画面の幅いっぱいに開き、操作は一行にまとめる（拡大縮小はピンチで行い、縮尺の数値だけを残す）。
アウトラインの行は言葉に幅の 4 割を残し、下の変更の集計の言葉、変更の一行、決定のボタン、↗ と「差分」は行から外して `</>` の中に置く。
左上のメニューから、検索、フレームワーク・機能・エンドポイントの選択、画面の説明、よく使う選択を操作できる。

## データとビルド

React + Vite の静的ページで、Cloudflare Workers に静的アセットとして置く（`wrangler.jsonc`）。
ページは表示だけを受け持ち、解析は非公開のワークスペースパッケージ [`@maronn-openid-connect/map-analysis`](../../packages/map-analysis) と [`@maronn-openid-connect/test-catalog`](../../packages/test-catalog) がビルド時に行う。

1. CLI の `explain --format json` を全機能オンで 4 フレームワーク分まとめ、関数カタログを読む
2. 関数とエンドポイントの処理本体を TypeScript のコンパイラ API で読み、処理の流れの木にする。呼び先は型で解決する
3. MAP_BASE があれば、変更前のコードからも木を作り、木の差分、式の差分、影響範囲、変更メモの対応づけを求める
4. テストを読んでカタログにし、関数カタログとエンドポイントに結び付ける。MAP_TEST_REPORTS があれば、その実行の結果と到達も結び付ける。MAP_BASE があれば、変更前のカタログとの差分を求める
5. 次のファイルを `public/data/` に書く

- `map.json`：索引。フレームワーク、コマンド、機能、エンドポイントとステップ、関数カタログ（呼び先、呼び出し元、外へ出る失敗）、interface のメンバー（説明、実装、実装が呼ぶもの）、PR の変更の一覧、テストのデータの場所と数（`tests`）。木は含まない
- `functions/<hash>.json`：フレーム一つ分。木、よく使う選択、PR の地図では変更前の木、ノードの差分、式の差分、ノードごとの hunk。フレームを開いたときに読む
- `sources/<hash>.json`：ハイライト済みのソース。Drawer を開いたときに読む
- `changes.md`：PR の変更の Markdown。PR のコメントがこれを引用する
- `tests.json`：テストの索引。全テストの名前、種類、対象、観点、結果の要約と、フレームとエンドポイントごとの数、不足、訳の無い言い回し。期待結果と本文は含めない。`map.json` の後に読む
- `tests/by-frame/<hash>.json`：フレームごとの、関連するテストの札の全文。テストのタブでその関数を見るときに読む
- `tests/by-endpoint/<hash>.json`：エンドポイントごとの、API と E2E のテストの札の全文と、届く関数ごとのユニットテストの id。テストのタブでそのエンドポイントを見るときに読む
- `tests/sources/<hash>.json`：テストのファイルの本文（ハイライトしない）。テストの札の「ソース」で読む
- `tests/results.json`：MAP_TEST_REPORTS の実行の結果。結果と到達は札と索引にも入っているので、ページは読まない
- `tests/diff.json`：PR の地図の、テストの差分。「このPRの変更」で読む

関数の id はカタログと同じ `<root>:<module>#<name>`、hono のエンドポイントの処理本体は `endpoint:<id>` である。
解析パッケージのテストは、木から求めた呼び先が CLI のカタログの calls / calledBy と一致すること、本体の全行がどれかのノードに属することを確かめる。

ビルドの最後に `scripts/check-map.mjs` が地図の出力を検査し、次の数を出す。
名前の無い選択（exit ケース）と、同じフレームで重なる名前（番号だけで区別した名前を含む）、ノードに属さない行、PR が変えた行のうちノードに属さないもの、説明の無い変更である。
全機能オンの `/token` に、refresh_token と authorization_code の名前付きの選択があることも確かめる。
これは地図の出力に対する検査で、貢献者のコードの形には向けない。
図の検査（`src/lib/diagram.data.test.ts`）も同じ考えで、ビルドしたデータがあるときだけ走る（`ci.yml` の `map` ジョブでは `build:map` の後のテスト）。
決定と終わりがどのフレームの図からも欠けないこと、`try` の枠が自分の箱だけを囲むこと、図がステップと守りをアウトラインと同じに畳むこと、幅に合わせて見出しが 11px に届くフレームが 9 割を下回らないことを確かめる。

`MAP_PR`、`MAP_PR_TITLE`、`MAP_PR_URL` は、ページに出す PR の番号、タイトル、URL である。
`MAP_TEST_REPORTS` は、テストの実行が書いたディレクトリ（Vitest と Playwright の JSON、到達の記録）である。
無ければ、テストの札はコードから読んだものだけになる。

```bash
# ルートで: CLI と解析パッケージをビルドしてから地図をビルドする（dist/ に静的ページ）
pnpm run build:map

# このディレクトリで
pnpm run dev              # データを作って Vite の開発サーバー（http://127.0.0.1:3610）
MAP_BASE=origin/main pnpm run dev   # origin/main からの変更（コミットしていないものを含む）を載せた地図
MAP_BASE=origin/main pnpm run data  # 開発サーバーを動かしたまま、データだけを作り直す（ページを読み込み直すと載る）
pnpm run build            # データを作って dist/ にビルドし、地図の出力を検査する
pnpm run check            # public/data の地図の出力だけを検査する
pnpm run changes:draft    # MAP_BASE からの差分で変更メモの雛形を書く
pnpm run deploy           # ビルドして wrangler deploy（https://maronn-oidc-map.<subdomain>.workers.dev）
pnpm run deploy:preview   # ビルドして wrangler versions upload（プレビュー URL が出る。本番は変わらない）
pnpm test                 # ページの純粋な部分（トレース、決定、図、ハッシュ、変更の札、検索、テストの表示）のテスト
```

データのビルドは `public/data` のファイルをその場で書き、前のビルドの残りだけを最後に消す（ディレクトリを消して作り直さない）。
そのため、変更メモを書いた直後などに開発サーバーを止めずに `pnpm run data` で作り直してよい。
それでも古いデータや「読み込めませんでした」が出るときは、開発サーバーを起動し直す。

`wrangler deploy` は `CLOUDFLARE_API_TOKEN` と `CLOUDFLARE_ACCOUNT_ID`（または `wrangler login`）を使う。
Worker の名前は `wrangler.jsonc` の `name` で変える。

## PR ごとのプレビューと main のデプロイ

`.github/workflows/ci.yml` の `map` ジョブが、`test` ジョブの後に、リポジトリのシークレット `CLOUDFLARE_API_TOKEN` と `CLOUDFLARE_ACCOUNT_ID` で次を行う。
`test` ジョブが書いたテストの結果と到達（`work/test-reports` の artifact `test-reports`）を `MAP_TEST_REPORTS` で受け取り、地図に載せる。
テストが落ちても、そこまでの結果で地図を作る。

- **PR**（opened / synchronize / reopened）：その PR のコードから地図をビルドし、同じ Worker の **Worker Preview** `pr-<番号>`（`wrangler preview --name pr-<番号>`）を作る・更新する。PR ごとに固定の URL を持ち、push のたびに同じ URL が新しくなる。URL と変更の表は PR のコメントに書く（push ごとに同じコメントを書き換える）。説明の無い変更で地図のビルドが落ちても、デプロイとコメントは行い、ジョブは失敗のままにする
- **PR を閉じた**：`.github/workflows/map-preview.yml` が、その Preview を `wrangler preview delete --name pr-<番号>` で消す
- **main への push**：`wrangler deploy` で本番（いまは `https://maronn-oidc-map.<subdomain>.workers.dev`）を更新する

Worker Previews はオープンベータ（wrangler 4.135 以降）なので、`wrangler preview` が失敗したときは `.github/scripts/map-preview.mjs` が PR ごとの Worker `maronn-oidc-map-pr-<番号>` へ `wrangler deploy` し、閉じたときにその Worker も消す。
どの場合も Actions の artifact（`oidc-provider-map`）にビルド結果が残り、`dist/` を静的に配信すれば同じ地図が見られる。

## 直接呼ばれない配線

上の「追えない配線」は、ミドルウェア登録、コンテキストへの書込み、コールバック、モジュール初期化を場所と理由付きで一覧する。届く先を証明できないものを、実行トレースに混ぜず残す。ファイル、コード、理由で絞り込み、型で分かる参照先は関数のページへ開ける。`#hono--wiring` / `#nextjs--wiring` で共有できる。機能をオフにしたときの配線除去までは確定しない。

`map.json.wiring` は索引の関数を持たないモジュールも読む。動的なキー・外部 callback の呼び先・middleware の mount や実行順を推測しない。設計と調査の根拠は [配線の設計](docs/design-traceable-wiring.md)、再現可能な全件棚卸しは [監査記録](docs/wiring-audit/README.md)、今後の作業手順は [実装用・レビュー用 skills](../../skills/README.md) にある。

## 構成

- `src/lib/trace.ts`：トレースの状態（開いたフレーム、選んだ決定）、選んだ決定で走るノード（「ここで失敗」を含む）、ノードへ至る決定、ステップと守りの畳み方（図と共通）、変更まで開くフレームと下の変更の到達、アウトラインの行、失敗を捕まえる `catch`
- `src/lib/diagram.ts`：焦点のフレームの木をアウトラインと同じ畳み方で箱と矢印にし、選んだ道筋の箱、行、矢印と、箱の札を求める
- `src/lib/graph.ts`：Dagre による図の自動配置、箱の幅、見出しを一行に収める省略
- `src/lib/camera.ts`：図を開く倍率と位置、選んだ箱が見える所までの移動
- `src/lib/hash.ts`：URL のハッシュ（`#hono--token/s4/s4.s2;d=s4.s1:true`、`#hono--fn--verifyClientSecret`、`#hono--changes`、`#hono--wiring`、`#hono--tests`）
- `src/lib/tests.ts`：テストの数と結果の言葉、行の札、英語と日本語訳の選び方、シナリオの日本語のキーワード、通るエンドポイントの順、テストのタブが述べるもの、不足のまとめ方、規則で読めなかったテスト、機能ごとの数、PR のテストの差分の数
- `src/lib/changes.ts`：PR の変更の札（行と箱で共通）、下の変更の集計、変更に至る道筋の選択、届く経路の名前とまとめ方、失敗が捕まる場所、差分の行番号、変更メモの本文
- `src/lib/words.ts`：アウトラインの行と図の箱の言葉（JSDoc、コメント、言葉の無い文の続き、`return` が返すもの、決定の側の名前）
- `src/lib/model.ts`：機能の絞り込み、`generate` のコマンドライン、関数に届くステップと呼び出し元、検索
- `src/lib/source.ts`, `src/components/CodeDrawer.tsx`：コードの選択肢とソースを読む Drawer
- `src/components/Trace.tsx`, `TraceView.tsx`, `SelectionBar.tsx`：アウトライン、決定のボタン、よく使う選択、図・差分・詳細のタブ
- `src/components/TestsTab.tsx`, `TestParts.tsx`, `TestsScreen.tsx`, `useTests.ts`：テストのタブ、テストの札とソース、テストの一覧のページ、テストのデータの読み込みと「English / 日本語」の記憶
- `src/components/`：ほかに、エンドポイントの画面、関数のページ、このPRの変更のページ、左の一覧、検索、メニュー
- `src/types.ts`：データの形（`@maronn-openid-connect/map-analysis/model` と `@maronn-openid-connect/test-catalog/model` の再輸出）
- `scripts/build-data.mjs`, `scripts/check-map.mjs`, `scripts/draft-notes.mjs`：解析パッケージを呼ぶデータのビルド、地図の出力の検査、変更メモの雛形
- `changes/`：PR ごとの変更メモ（[書き方](changes/README.md)）
