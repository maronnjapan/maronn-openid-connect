# テスト（OIDC Provider のテストの一覧）

OIDC Provider にどんなテストがあるかを見るページです。
地図（apps/map）とは別のアプリで、地図と同じ Worker の `/tests/` で配信します。

## 見られるもの

- ホーム：テストの数（E2E / API / ユニット / ツール）、最新の実行の結果、正常系と異常系の割合、テストの種類と、エンドポイントごとのテストの数です。
  プルリクエストのビルドでは、一番上にその PR のテストへの一行が出ます。
- テストの種類（`#/kind/e2e`・`#/kind/api`・`#/kind/unit`）：E2E は spec・シナリオのファイルごと（見出しの名前の順）、API はエンドポイントごと（Hono / Next.js）、ユニットはパッケージごとの一覧です。
  ユニットはモジュールを畳んで並べ、モジュールを開くと関数とテストの数が、関数を開くとそのテストが出ます。
- テストの種類、エンドポイント、検索、この PR の一覧の行には「対象」が出ます（ファイルのページの行には出ません）。
  ユニットテストは関数、API テストは確かめる関数とエンドポイント（`applyOidc（web/express） · POST /token`）、E2E テストは通るエンドポイントの順（`/authorize → /login → /token`、計測した実行のリクエストの順）です。
  同じ名前の関数がほかにもあるときは、パッケージかモジュールのディレクトリを添えます。
  E2E テストの経路では、テストのコードがリクエストするエンドポイントを普通の色で、実行で通っただけのものを薄い色で示し、スマートフォンではリクエストするものと経路の長さ（`経路 6`）だけを示します。
  一覧の見出しが言っていること（手順の関数だけのユニットテスト、そのエンドポイントへの API テストのリクエスト）は省きます。
- エンドポイント：処理の流れ（手順）と手順ごとのユニットテストの数、そのエンドポイントのテストを E2E・API・ユニットに分けた一覧です。
  エンドポイントのテストは、その API・E2E のテストと、手順の関数のユニットテストです（Next.js の手順は、そのブロックが呼ぶ関数のユニットテスト）。
  ユニットテストの無い手順には「テストなし」と出ます。
  手順を選ぶと、その手順のユニットテストだけに絞り込みます。
  手順より下で届く関数（cookie、データベース、ストアなど）は「ほかの関数」に畳んであり、選ぶとその関数のユニットテストに絞り込みます。
  「コード」でエンドポイントの本体のコードを、手順の `</>` で手順のコード（Hono は手順の関数、Next.js は Route Handler の `// [手順]` のブロックと、そのブロックが呼ぶ関数）を横のパネルに開きます。
  手順の印が無く、呼ぶ関数も分からない手順（Route Handler に印の無い Next.js のエンドポイントの手順）には `</>` がありません。
- テストの詳細：タイトル（英語と日本語）、対象、結果（ターゲットごとの時間）、確かめていること（最初の 6 件）、送るリクエストと、コードです。
  コードは「テスト」「テスト対象」「ヘルパー」のタブで切り替えます。
  「テスト対象」は、関数を確かめるテストはその関数、E2E・API・シナリオは確かめているエンドポイントのコードです。
  E2E テストは開いたエンドポイントのページのエンドポイント（なければテストのコードがリクエストする最初のエンドポイント）から開き、実行で通っただけのエンドポイントは薄く示します。
  詳細の「対象」の名前を選ぶと、「テスト対象」でそのコードを開きます。
  「ヘルパー」は、テストが自分で呼ぶヘルパーを並べ、そのヘルパーが中で呼ぶヘルパーを下に畳みます。
  シナリオではタブが「ステップ 12 · ヘルパー 5」のように中身を言い、ステップの定義と、ステップの定義が呼ぶヘルパーを並べます。
  ツールのテストには「テスト対象」のタブがありません。
- ファイル：テストのファイルの一覧と、ファイルごとのテストとコードです。
  テストを選ぶと、横のコードでそのテストの行に印が付きます（スマートフォンでは詳細が開きます）。
- この PR：プルリクエストのビルドでは、追加・変更・名前の変更・削除したテストと、関連するテストが変わっていない実装の変更です。

テストの不足のうち画面に出すのは、ユニットテストの無い手順だけです。
ほかの不足（`tests.json` の `gaps`）と、対象や観点を読めなかったテストの数（`unknown`）はデータに残し、画面には一覧にしません。

画面はすべて URL のハッシュ（`#/endpoint/hono/token` など）で開けます。
横のパネルは、テストを `?test=<id>`、コードを `?code=fn:<関数の id>`・`?code=endpoint:hono:token`・`?code=step:hono:token:<手順>` で開きます。

## データ

データは地図のデータの手順（apps/map/scripts/build-data.mjs）が `apps/tests/public/data` に書き出します。
このアプリの `build` はデータを作りません。
リポジトリのルートで次のどちらかを実行してください。

```sh
pnpm run build:map
# 地図のパッケージをビルド済みなら、データだけ
pnpm --filter @maronn-openid-connect/map run data
```

データが無いときは、ページにこの手順を表示します。

## 開発

```sh
pnpm --filter @maronn-openid-connect/tests dev        # http://127.0.0.1:3620（PORT で変更）
pnpm --filter @maronn-openid-connect/tests build      # dist/ に public/data も含めて出力
pnpm --filter @maronn-openid-connect/tests preview
pnpm --filter @maronn-openid-connect/tests typecheck
pnpm --filter @maronn-openid-connect/tests test       # src/lib のテスト
```

## 配信

地図のビルド（`pnpm --filter @maronn-openid-connect/map build`）が、このアプリをビルドして `apps/map/dist/tests/` にコピーします。
地図の Worker（apps/map/wrangler.jsonc）がそれを `<地図の URL>/tests/` で配信するので、プルリクエストのプレビューにもこのページが付きます。
ページはデータを `./data/` から相対パスで読むので、`/tests/` のようにサブパスに置いても動きます。
