# 設計案: 経路をたどる地図

PR の地図（`apps/map`）を、次の二つの目的から組み立て直す設計案である。

- エンドポイントから何段下の関数で起きた変更でも、何を変えたかと差分のコードを、その場で読める
- 関数とエンドポイントの処理の流れで、条件分岐が正しく分かれ、読者が分岐を選んで追える

この改訂では、既存の実装を活かすという前提を外した。
一方で、このリポジトリは OSS であり、地図の実装も、地図が読むコードも、生成 AI だけが書くわけではない。
そこで、人が普通に書いたコードと PR からそのまま地図が作れることを設計の前提に置き、貢献者に課す規則は「貢献者に課す規則」の節で限定する。
いまの作りを部分的に直す案は末尾の「縮小案」にまとめ、本文では目的に対して最短の形を述べる。
この設計は `packages/map-analysis`（解析）と `apps/map`（表示）に実装した。
使い方は [apps/map/README.md](../README.md) と [changes/README.md](../changes/README.md) にあり、実装で決めた細部は末尾の「残る細部」に記す。
「現状の計測」と「いまの作りが目的と合わない理由」は、作り直す前の地図についての記録である。

## 現状の計測

提案の根拠として、全機能オンでビルドした `map.json` を測った（2026-11、`main` 相当）。

| 観点 | 計測結果 |
|---|---|
| ステップの下の関数の深さ（hono） | 3 段以上のステップが 31 個、最深 7 段（`consent/issue-hybrid-response`、下に 55 関数） |
| 変えた行が図の箱に対応する割合 | 関数の宣言から本体の終わりまでの行のうち、箱が指す行は 25%（21,901 行中 5,533 行） |
| ケースが exit ケースに畳まれる関数 | 1,017 個中 52 個 |
| `/token`（hono）のケース | 条件 6 個で exit ケース 27 個。成功の終わりが 6 個、残り 21 個はステップごとのエラー応答 |
| `/authorize`（hono）のケース | 条件 8 個で exit ケース 27 個 |
| `verifyIdJagAssertion` のケース | 条件 45 個で exit ケース 23 個。うち 22 個が `→ throw invalidAssertion(…) (n)` と番号だけが違う |
| 条件の内訳（1,846 個） | 守り（片側がすぐ終わる）999、分かれ道 433、任意項目の代入（両側がすぐ合流）414 |
| `@throws` を持つ関数の呼び出し | 557 箇所中 424 箇所（202 関数）にエラーの矢印が無い |
| `map.json` の大きさ | 6.4 MB。うち機能の組み合わせごとのエンドポイントの流れ（`controlFlows`、450 組）が 3.7 MB |

README は「`/token` なら `authorization_code` と `refresh_token`」をケースの例に挙げているが、全機能オンの `/token` ではこの二つを選べない。
`refreshTokenRequest ?? (await validateAuthorizationCodeGrant(…))` の分岐は読めているのに、道筋が上限の 24 本を超えて exit ケースに畳まれ、どちらも `→ return respondToken(…)` になるからである。

## いまの作りが目的と合わない理由

症状は上の表のとおりだが、直すべきは症状ではなく、次の四つの設計上の選択である。

**流れを平らなグラフにしてから、ケースを道筋の列挙で取り戻している。**
読み取りの時点では「この `if` のどちら側か」という入れ子の構造が分かっている。
それを箱と矢印に平らにした時点で捨て、画面側で開始から終わりまでの道筋をすべて列挙して分岐を取り戻そうとする。
独立した条件が n 個合流すれば道筋は 2^n 本になり、上限を超えると名前の無い exit ケースになる。
任意項目の代入 414 個とエラーの矢印の扱いは、この方式の中では症状として現れているにすぎない。

**読む単位が「関数のページ」で、変更は関数に付いている。**
差分とメモはその関数のページにだけ出るので、関数をまたいだ瞬間に名前の一覧へ退化する。
差分はテキストの hunk で、図との対応は「箱の行と変えた行が一致するか」しかなく、箱が指す行は 25% にとどまる。
残りの行の変更は、どの箱にも現れない。

**機能の組み合わせごとに流れを作っている。**
ステップを足す機能の組み合わせ（450 組）ごとにエンドポイントの流れを作り、矢印の集合（`edgeSets`）も別に持つ。
一本の木の各ノードに機能の札を付ければ、画面で絞るだけで済む。

**読み取りがコンパイラ無しの字句解析である。**
これは CLI の配布物が依存を持てないための制約だが、確認したところ、配布された CLI は関数の流れを使わない。
配布物の `functionProject()` は焼き込んだカタログを読み、`flowOf` は常に未定義を返す。
`explain` と `graph` のコマンドも流れを参照していない。
流れの読み取りの利用者は、リポジトリ内で動く地図のビルドだけである。
したがって、ビルド時に TypeScript のコンパイラ API で読む設計は、配布物の制約に触れない。
型による呼び先の解決、正確な行の範囲、三項演算子や論理代入やコールバックの扱いは、字句解析で近似する必要がなくなる。

## 貢献者に課す規則

地図が成り立つために貢献者に求めることは、生成器がどのみち必要とするものに限る。
それ以外の書き方は、あれば表示の言葉が良くなるが、無くても地図が欠けたり CI が落ちたりしないようにする。
この線引きを先に置くのは、作り直す前の地図がすでに書き手の規律に寄りかかっていたからである。
その地図は、箱の二行目を JSDoc の一行目に、条件の説明を手前のコメントに、変更の説明を PR ごとの変更メモに頼っていて、どれも「毎回そのとおりに書く」ことを前提にしていた。
生成 AI が書く PR ではこの前提が保てるが、人が書く PR に同じ密度を求めるのは現実的でない。

**課す規則**（生成器が要るもの、または lint で検査して続けると決めたもの）。

- Next.js の Route Handler と hono の pipeline に、ステップの印（`// [step-id] …`、機能のブロックには `(feature: <id>)`）を置く。生成器がステップを切り出すために要る
- カタログに載せる関数を `function` 宣言で書く。カタログの id（`<root>:<module>#<name>`）と生成器の読み方がこれに依る。TypeScript の解析器にすればアロー関数も読めるが、id と生成器の両方に手が入って複雑になるので、この規則は緩めない。モジュール直下の変数や default export に arrow/function 式の本体を置く形も禁止し、`.github/scripts/lint-function-forms.mjs` が AST で検査する。型注釈を付けても本体がカタログから落ちるためであり、単なる関数の別名や factory の戻り値にはこの禁止を課さない
- 関数の JSDoc の一行目に振る舞いを一文で書く。`.github/scripts/lint-function-docs.mjs` の検査を続ける。地図はこれを、アウトラインの行と図の箱の言葉、要約に使う
- 変更メモ（`apps/map/changes/*.md`）を PR に添える。存在と関数への対応づけは機械で確かめる。何を求め、何を地図が計算するかは「変更メモと影響範囲」の節で述べる
- エンドポイントに届く実装の変更で、その関数に関連するテストを足しも変えもしないときは、変更メモのその関数の節に `テストを変えない理由:` の行を書く。地図のビルドの検査（`MapChanges.untested`、`packages/test-catalog` の diff.ts）が確かめる。テストを変えないという判断を毎回人にさせるためで、理由と関連するテストの決め方は [design-test-catalog.md](design-test-catalog.md) の「関連するテストに変更が無い実装の変更」にある
- テストの `expect` は `it` のコールバック本体に置く。Playwright の `test` と `playwright-bdd` の登録済み step には同じ規則を適用する。共通 helper・support module・suite・ライフサイクル hook に検証を置くと、そのテストが何を保証するかが本体から読めず、カタログにも期待値が載らない。helper は値を返し、呼び出し元で検証する。`expect.any` 等も含め、`.github/scripts/lint-expect-scope.mjs` が全ソースの AST を検査する（`pnpm run lint`）

**あれば良くなるもの**（無くても欠けない）。

- 条件の手前のコメント：条件の説明に使う。無ければ、条件が真偽を返す関数の呼び出し一つ（否定を含む）ならその関数の JSDoc を条件の形にしたもの（「パブリッククライアントか」）を、ほかは条件式を言葉にした説明（作り直す前の `conditionSummary` の規則）を添える。後者のとき、アウトラインの行はコードを出し、言葉は重ねたときの表示で読む
- JSDoc の `@throws`：参考情報として残すが、失敗の流れは木から求めるので、書かれていなくても失敗の矢印は出る
- JSDoc の一行目は lint で保証されるが、地図は無いときの代替（呼び出しの式と戻り値の型）も持つ。lint の対象外のものと、書きかけの作業ツリーで地図を作るときのためである

**課さない規則**（いまの作りに暗黙に入っていて、この設計で外すもの）。

- 字句解析が読める形にコードを保つこと（一文一宣言の import、JSX の文中のアポストロフィを避ける、など）。コンパイラで読むので要らない
- resolver や store の変数名を `…Resolver` / `…Store` で終えること。受け取りの型で引くので要らない
- 変更メモに「何を変えたか」と「どこに効くか」を書くこと。どちらも地図が計算する。メモに書くのは意図と背景である
- 一文ごとにコメントを書くこと。木の差分と呼び出し先の要約で足りる

地図の CI の検査は、地図自身の出力（ケースに名前が付く、変えた行がどれかのノードに属する、追えない呼び出しと配線に場所と理由がある）に対して行う。上で明記した function 宣言の規則は lint がコードの形に対して検査する。ミドルウェアやフックの適用先を手書きさせる規則は課さない。

エンドポイントから直接呼ばれない配線の境界、比較した案と選択は [design-traceable-wiring.md](design-traceable-wiring.md) に記す。エンドポイントの振る舞いを追加する場合は型付き helper の明示的な呼び出しを優先し、残る動的な配線は地図の「追えない配線」で確認する。

## 新しいモデル

四つの柱で組み立てる。
**構造化フロー木**が流れの表現、**トレース**が関数をまたぐ画面、**木の差分**が変更の表現、**決定**が分岐の選び方である。

### 1. 構造化フロー木

関数の本体を、箱と矢印ではなく、文の入れ子をそのまま持つ木として読む。

- **呼び出し**（`call`）：カタログの関数、または resolver や store のメンバーの呼び出し。呼び先の id を持つ
- **処理**（`action`）：カタログの呼び出しを含まない文（代入、フレームワークの呼び出し、計算）。言葉の無いものが続くところは「コード n 行」の一行に畳み、何を用意するか（`a`、`b` を用意する）を言う
- **条件**（`if`）：条件式、成立側の列、不成立側の列。`&&` と `||` は条件式の中の短絡として保つ
- **分岐**（`switch`）：判別式と、`case` ごとの列（フォールスルーを含む）
- **繰り返し**（`loop`）：ヘッダと本体。コールバックの中の呼び出し（`items.map((x) => f(x))`）も「各要素で」の繰り返しとして置く
- **例外の捕捉**（`try`）：本体、`catch` の列、`finally` の列
- **式の分岐**（`cond-expr`）：三項演算子、`??`、`||`、`&&`、論理代入で、腕に呼び出しを持つもの
- **終わり**（`return` / `throw`）と、本体の末尾への到達
- **ブロック**（`block`）：Next.js の Route Handler のステップの印（`// [step-id]`）で区切られた列。hono の pipeline ではステップの関数の呼び出しがこれに当たる

どのノードも、ソースの行の範囲（開始行と終了行）と、親からの位置で決まる id（`s3.then.s1` のような形）を持つ。
行の範囲は切れ目なく関数の本体を覆うので、変えた行は必ずどれか一つのノードに属する。
エンドポイントの木は、ステップを足す機能の名前をノードの札として持ち、機能の組み合わせごとに木を作らない。

ノードに書く言葉は、まずコードから作る。
呼び出しなら呼び先の名前と引数、条件なら条件式を言葉にしたもの、処理なら文の要約である。
呼び先の JSDoc や手前のコメントがあれば、その言葉で置き換える。

いまの図（箱と矢印）は、この木を平らにすれば得られる。
畳み方はアウトラインに合わせる（「2. トレース」）。
いまの「ケース」が答えようとしていたこと（どの条件でどちらへ進むとこのノードに至るか）は、木の上では列挙なしに求まる。
あるノードに至る条件は、祖先の条件で選んだ側と、手前の兄弟のうち「成立すると終わってしまう守り」を不成立で通ることの組み合わせであり、木を一度たどれば出る。

### 2. トレース

読む単位を「関数のページ」から「エンドポイントを根とする、関数をまたいだ一本の経路」に変える。
これを**トレース**と呼ぶ。

トレースは**フレーム**の木である。
根のフレームはエンドポイントの木（pipeline の本体、または Route Handler）で、その中の呼び出しノードを開くと、呼び先の木が子のフレームとしてその場に展開される。
resolver や store のメンバーは葉で、インターフェースの JSDoc を出す。
すでに経路上にある関数への呼び出しは「再帰」の葉にして止める。

トレースの中では、次の操作が一つの画面で完結する。

- ステップの関数を開いて中の分岐を読み、さらにその中の関数を開く
- 「**変更まで展開**」で、そのフレームから届くすべての変更まで、間の呼び出しを一度に開く。深さにも件数にも上限を設けない
- 変えたノードの行の差分を、そのノードのすぐ下、または右側の差分欄で読む
- どのフレームも「このフレームを根にする」で、関数のページとして切り出せる

画面はアウトラインを主、図を従にする。
**アウトライン**は木を字下げした行として縦に読むもので、コードの構造をそのまま追う形である。
関数をまたいで 7 段開いても字下げが深くなるだけで、畳んだ分岐の要約と差分を行の間に置ける。
一行はまず、その処理が何をするかを自然言語で一行に書く（ステップの見出し、呼び先の JSDoc の一行目、メンバーの JSDoc、文の手前のコメント）。
コードは、言葉が無いところ（一つだけの変数の定義や、コメントの無い条件）と、読者が開いた行にだけ出す。
読者が詳しく見たいのは気になった所だけで、ほかはまず言葉で流れを追えれば足りるからである。
ステップは見出しの一行に畳み、開くと中の行が出る。
PR が変えたノード、下に開いたフレーム、選んだ決定を中に持つステップは、開いた状態で出す。
読者がステップを開け閉めした記録はアウトラインと図で一つにし、どちらで開け閉めしても両方が変わる。
分岐の選択は行を消さずに、選ばなかった側と通らない後の行を灰色にする。消えた行が分からなくならないようにするためである。
箱と矢印の図では、フレームを入れ子にすると数段で読めなくなり、差分を置く場所もない。
図は焦点のフレーム一つ分だけを描き、アウトラインで選んだ道筋を青にして、流れの形を見るために使う。
文はアウトラインが読むので、図は木をアウトラインと同じ畳み方で平らにし、流れの形だけを描く。
ざっと眺められるよう、箱はどれも一行にし、見出しはアウトラインと同じ言葉にする。
守りと任意項目の `if` は、アウトラインで一行になるもの（後述の「4. 決定」）を一つの箱にし、すぐ終わる側は見出しの末尾の札（`→ 失敗`）にする。
分かれ道の側でも、すぐ終わるものは札にする。
言葉の無い文が続くところは一つの箱にする。
エンドポイントの本体はステップ一つを一つの箱にし、終わり方を見出しの末尾の札にする。
フレームのある関数の呼び出し一つだけのステップは、その呼び出しの箱にする。
`try` は箱にせず、捕まえる範囲を囲む枠で示し、例外が起きたときにどうなるかを枠の見出しに書く。
配置（Dagre）と三色の規則は残す。すぐ終わる `catch` の行は赤にする。箱の幅は 320px とし、横に二つ並ぶ段があれば 200px にする。図は箱の見出しが 11px 以上になる倍率で開く。
図の箱を押すと、その箱を選んでアウトラインの行を示すだけで、ほかのフレームへは移らない。
箱に重ねる（キーボードでは箱に移る、タッチでは触れる）と詳しい内容のカードが出て、その中のボタンで関数の中へ潜ったりステップをその場で開いたりする。
クリックで勝手に潜ると、今どこを見ているかが分からなくなるからである。
カードは、その箱が受け持つ呼び出しのうちアウトラインで開けるものごとに、潜るボタンを出す。
図の上のパンくずが、根から焦点のフレームまでの道を示す。
右の欄のタブ（図、差分、詳細、関数のページの呼び出し元）は、どれも図が見せているフレームについて述べる。
詳細は、選択が無くてもそのフレームを出し、選んだ行はその下に足す。
アウトラインの行を押すと、その行を選び、右の欄はその行のフレームに移る。
図はその行の箱を囲んで見える所まで動かす。
欄は図のタブで始まり、行や箱を押してもタブは変えず、読者が選んだタブを保つ。
アウトラインと図の欄の幅は、間の仕切りをドラッグ（またはキー）で読者が変えられる。
狭い画面ではアウトラインだけを出し、図は開いたときに重ねる。

上限を設けずに展開しても動くように、次の三つで支える。
関数の木はフレームを開いたときに関数ごとのファイルから読み、変更まで展開のときは変更に至る経路上のフレームだけを読む。
同じ関数が経路上に二度現れたら「再帰」の葉で止める。
行数が増えたときは、見えている行だけを描く（仮想スクロール）。
`consent/issue-hybrid-response` の下の 55 関数をすべて開いても、行は数百のオーダーである。

開いているフレームと、後述する決定の選択は、ハッシュに書く。

```
#hono--token/s4/s4.s2;d=s4.s1:true,s12:refresh
```

`/` 区切りがフレームを開いた呼び出しノードの id、`d=` が決定の選択である。
ハッシュの形は新しく決め、いまの形との互換は取らない。

トレースの見え方を、`/token` で `verifyClientSecret` の 3 段下に変更がある場合で示す。

```

├ トークンリクエストを解析する  parseTokenRequest()
├ クライアントを認証する  authenticateTokenClient()                  下で変更 1
│  ├ if (authorization)                           成立
│  │  └ verifyClientSecret()                                        変更: 条件 +1
│  │     ├ + if (secret.length < MIN)             不成立            ← 足した条件
│  │     │    └ throw TokenError(invalid_client)                     （畳んである）
│  │     └ return timingSafeEqual(…)
│  └ …
├ ID-JAG を発行する  issueIdJag()                  不成立（続く）
├ …
├ validatedRequest = refreshTokenRequest ?? …     refresh_token あり
├ 署名鍵を選ぶ  selectTokenSigningKeys()
└ …
```

右の欄の「差分」には、図が見せているフレームと、その下に開いたフレームの差分がトレースの順に並ぶ（後述の「経路の差分」）。

### 3. 木の差分

変更を「関数が変わった」という一つの札ではなく、木のノード単位の差分として持つ。

地図のビルドは、いまも変わったファイルの変更前のテキストを git から読んでいる。
そこで変更前の木も作り、変更後の木と突き合わせる。
突き合わせは、各列（兄弟の並び）で種類と要約（呼び先、条件式の正規化した文字列）が同じノードを順序を保って対応づけ、対応したノードの中へ再帰する。
結果は、変更後の各ノードに `追加` / `変更` / `同じ` の印、消えたノードは直前の対応したノードの後ろに「消した」ノードとして置く。

`変更` の印が付いたノードは、式の中まで差分を取る。
条件式や引数は構文木の部分木なので、同じ形のノードを対応づけながら下り、違う葉（演算子、リテラル、識別子）を見つける。
`expiresAt < now` を `expiresAt <= now` に変えた場合は「`<` を `<=` に変えた」、引数を足した場合は「引数 `issuedAt` を足した」と要約し、差分の表示でも変わった語だけを強調する。
式の形が大きく変わって対応づけられないときは「式を書き換えた」として、前後の式を並べて出す。

差分の対象には、エンドポイントの処理の本体（hono の pipeline の handler、Next.js の Route Handler）も含める。
いまの地図はカタログの関数の本体だけを比べるので、hono の pipeline の handler の中に `if` を一つ足しても、変更は 0 件、地図に載らないファイルも 0 件と報告される（作業ツリーで試して確認した）。
エンドポイントの木は関数の木と同じ形なので、同じ差分がそのまま効く。

テキストの hunk は、変えた行の続きごとに、それを含む最小のノードに付け、前後の文脈の行はそのノードの行に収める。
一つのノードに収まらない続きは、最上位のノードの境目で切る。
どのノードにも属さない行（JSDoc と宣言）の変更は、フレームの始まりに付ける。
行の範囲が本体を覆うので、付け先の無い変更は生じない。

差分からは、言葉の要約を作る。

- 「条件 `secret.length < MIN` を足した」
- 「`a()` の呼び出しを `b()` に置き換えた」
- 「`return` を手前に足した（早期リターン）」
- 「引数を変えた（`issuedAt` を足した）」

呼び出しノードには、呼び先の下で起きた変更の集計を付ける。
「下で変更 3 件（条件 +1、呼び出し +2）」のように件数と種類を出し、開くと内訳が見える。
interface のメンバーの呼び出しには、そのメンバーの実装（とその実装が呼ぶ先）の変更の集計を付ける。
集計は下のすべての変更に及び、深さの上限は設けない（「変更まで展開」と同じ。同じ関数は一度だけ数える）。

トレースの右側には**経路の差分**（右の欄の「差分」）を出す。
図が見せているフレームと、アウトラインがその下に開いているフレームの hunk を、フレームの見出し付きでトレースの順に並べたものである。
レビューする人は、PR の差分をファイル順ではなく実行の順で読める。

宣言（引数と戻り値の型）の変更は開始ノードの変更として扱い、そのフレームを開いた呼び出しの行に出す。
呼び出し側では、呼び出しノードの引数のテキストが変わったときだけ `変更` を付ける。
変更メモ（`apps/map/changes/*.md`）の読み方と関数への対応づけは変えず、あれば関数の見出しとして差分の上に出す。
無ければ木の差分の要約がその場所に入るので、メモの無い PR でも「何を変えたか」は欠けない。

### 4. 決定

ケースの列挙をやめ、**決定**の選択に置き換える。
決定は、木の中で道筋を分けるノード（`if`、`switch`、`cond-expr`、`loop` のヘッダ、`try` の `catch`）である。

アウトラインの既定の見え方は、コードと同じく全部を見せる形にする。
ただし、成立するとすぐ終わる守り（`if (!x) throw …`）は、その側を一行に畳み、本線が縦に読めるようにする。
`verifyIdJagAssertion` の 45 個の守りは 45 行の一行ずつになり、本線はその左を下りていく。
PR が変えた守り、成立側でフレームのある関数を呼ぶ守り、成立側に決定がある守りは畳まない。
その関数を開き、その決定を選べるようにするためである。
図もこの規則で畳む。

決定ごとに、どちらへ進むかを選べる。
`if` なら成立と不成立、`switch` なら `case` のラベル、`try` なら本体と `catch`、短絡なら「値あり」「null または undefined」である。
選ぶと、選ばなかった側と通らない後の行が灰色になり（行は消さない）、右の図でも灰色になる。
子のフレームの決定も同じ仕組みで選べ、経路全体で一本の道筋が決まる。
呼び出しには「ここで失敗する」（`fails`）という側も持たせる（「失敗で終わる」の選択とハッシュがこの側を選ぶ）。
その呼び出しの後の行は灰色になり、失敗はそのフレームで囲む `catch` のある `try` のうち最も内側のものへ進む。
そういう `try` が無ければ、フレームはそこで終わる。

いまのケース欄に当たるものは、**よく使う選択**として木から計算して並べる。

- **終わり方**：`return` のノードと本体の終わりごとに、そこへ至る最小の決定の組み合わせ。名前は区別に要るラベルだけ（Next.js の `/token` なら `!keys: 成立`、`例外が起きたとき › error instanceof TokenError: 成立` など）。守りを不成立で通った事実は名前に入れない。`throw` と呼び先から伝わる失敗は「失敗で終わる」に分けて並べる（後述の「失敗の流れ」）
- **変更に至る道筋**：変えたノードごとに、そこへ至る決定の組み合わせ。フレームをまたぐ
- **ステップ**：エンドポイントなら、各ステップのブロックに至る決定の組み合わせ

これらは木をたどって求めるので上限が無く、exit ケースへの切り替えは無くなる。
複数を同時に選ぶと和集合になり、いまのチェックボックスの複数選択に相当する。

`??` と三項演算子のラベルは、条件式ではなく進む先の言葉を使えるようにする。
`refreshTokenRequest: null または undefined` は、進む先のブロックの見出しから `authorization_code グラントを検証する へ` と言い換えられる。

機能のオン・オフは、木のノードの機能の札で絞る。
オフの機能のブロックは木から外し、そのブロックが作る値を読む条件は「値なし」の側だけを残す。

### 失敗の流れ

関数が「どう失敗するか」を、JSDoc の `@throws` に頼らず木から求める。
`try` の外にある `throw` と、`try` の外で呼ぶ関数の失敗を合わせたものが、その関数から外へ出る失敗である。
カタログ全体でこれを不動点まで求め、各関数に「外へ出る失敗」の一覧を持たせる。

トレースでは「エラー時」をオンにすると、各呼び出しノードに「失敗すると → どこで捕まるか」を出す。
捕まる先は、トレースを上へ辿って最初に見つかる `catch`（`/token` なら根のフレームの `catch` と `respondTokenError`）である。
これで、3 段下の `throw TokenError(invalid_client)` が、どのエラー応答になって返るかを一つの画面で追える。
よく使う選択の「失敗で終わる」に、呼び先から伝わる失敗を「`TokenError(invalid_client)` で終わる（`verifyClientSecret` から）」として並べる。
選ぶと、その `throw` までのフレームを開き、途中の呼び出しをどれも「ここで失敗する」側にするので、失敗した後に通らない行が灰色になる。

## 変更メモと影響範囲

変更メモは PR の中で最も重要な文書だが、機械で保証できるのは存在と対応づけまでで、内容の質は保証できない。
「aaaaa」と書いた節を lint で弾く方法はなく、長さや語句の検査を入れても迂回されて形骸化する。
そこで、メモに書いてもらうことを意図と背景に絞り、「何を変えたか」と「どこに効くか」は地図が計算して添える。
計算した事実とメモの記述が食い違っても、読者は計算の側を見られる。

### 役割の分担

| 問い | 答えるもの |
|---|---|
| 何を変えたか | 地図。木の差分の要約と差分 |
| どこに効くか | 地図。届く経路、必要な機能、失敗の変化 |
| なぜ変えたか、何に気をつけるか | 変更メモ |

いまの変更メモの書き方（`##` 見出しで関数を名指し、本文で説明する）は変えない。
見出しは人が名前で書けるものにとどめ（`## verifyClientSecret`）、id を手で書かせない。
エンドポイントの処理を変えたときは、エンドポイントの id を見出しにする（`## token`）。
変わるのは、本文に「どう変えたか」を書かなくても地図とコメントが欠けなくなることと、見出しの対応づけを雛形で正しくすることである。

### 影響範囲の計算

「どこに効くか」は手で書かせず、次の規則で計算する。

- 呼び先は型で解決する。別名の import、再 export、メソッドの呼び出しを名前の一致で見落とさない
- インターフェースのメンバーを通る到達を含める。store や resolver の実装（`createProviderStores` が返すオブジェクトのメソッドなど）を変えたとき、そのメンバーを呼ぶすべての箇所に届いたことにする。実装の本体がどのメンバーかは、オブジェクトリテラルのプロパティ名と、それを返す関数の戻り値の型から引く。実装の中から別のメンバーや関数を呼ぶなら、その先も同じように上へたどる（store の実装 → それを呼ぶ resolver の実装 → resolver のメンバーを呼ぶ core の関数 → エンドポイント）。`apps/hono` の実装は Hono・Express・Fastify のエンドポイントにだけ、`apps/nextjs` の実装は Next.js のエンドポイントにだけ届く
- 届く経路は、エンドポイントとステップだけでなく、そこに至る決定の組み合わせまで出す（「変更に至る道筋」）。その経路が要る機能（オフなら経路が無い）も添える
- 失敗の変化を含める。外へ出る失敗の集合が変わった関数（新しい `throw` を足した、`catch` で握るようにした）は、その失敗が捕まる場所（エンドポイントのエラー応答）まで影響として出す
- hono と Next.js に同名の写しがある関数は、どちらを変えたかを別々に出す
- 型で引けない動的な呼び出し（文字列のキーで取り出すものなど）は「追えない呼び出しあり」と明示し、黙って無いことにしない。そのうち、変更へ上がる道筋にあるメンバーと同じ名前のメソッドを呼ぶものは、変更を呼ぶかもしれない呼び出しとして挙げる（届く経路には入れない）

これらは地図の「このPRの変更」と PR のコメントの両方に出す。
コメントの表は、札、関数、場所、自動要約、届くエンドポイント、メモの一行目（無ければ「説明なし」）の列にする。

### 検査と CI

- 見出しが名指す関数がカタログにあることの検査（既存の警告）を続ける
- コードを変えた関数のうち、メモに節が無いものを「説明の無い変更」として PR のコメントの先頭に一覧する。名前、場所、自動要約、届くエンドポイントを添える
- CI を落とすのは、コードを変え、かつ届くエンドポイントがある関数と、エンドポイントの処理そのものに、説明が無いときとする。JSDoc だけ、移動、コメントや書き方だけ（木が同じ）、どのエンドポイントにも届かない関数は対象にしない。届く変更は利用者に見える振る舞いの変更なので意図の記述を求める価値があり、届かないものにまで求めると形骸化するからである
- 雛形が生成した節を消したときも、その関数が説明の無い変更に戻るので、同じ検査で落ちる。「生成した節を消さない」という運用は、この検査が支える
- 内容の質は検査しない。代わりに、コメントと地図で、節の本文と自動要約を隣に並べる。レビューする人がその場で見比べられる

### 雛形の生成

人が書く PR で見出しの対応づけを正しく保つには、書かせるより作って渡す方が確実である。
地図のビルドに、`MAP_BASE` からの差分で変更メモの雛形を書くコマンドを足す（`pnpm --filter @maronn-openid-connect/map changes:draft`、名前は仮）。

- `##` 見出しは関数の名前で書き、同じ行の末尾に id を HTML コメントで添える（`## verifyClientSecret <!-- core:client-auth.ts#verifyClientSecret -->`）。読むときは名前、対応づけは id で行うので、同名の関数を取り違えない。人が自分で書くときは名前だけでよく、同名の関数が複数変わっていて曖昧なときだけ、検査が `core:verifyClientSecret` のような絞り込みを求める
- エンドポイントの処理の節は、エンドポイントの id で書く（`## token <!-- endpoint:token -->`）
- 各節の下に、自動要約と届くエンドポイントを HTML コメントで添え、意図を書く欄を空けておく
- すでにメモがあるときは、節の無い関数の分だけを足した案を PR のコメントに出す

雛形はコミットされる文書なので、地図が計算した事実（要約、届く先）を本文には書かず、コメントにとどめる。
計算した事実は次のビルドで変わりうるが、意図は変わらないからである。

## 画面

**エンドポイントの画面**は、エンドポイントを根にしたトレースである。
根のフレームの呼び出しノードがステップで、見出しにはステップのラベル、札には PR の変更の集計が付く。
いまの「ステップの詳細」の内容（受け取る値、次へ渡す値、仕様、失敗するとき）は、ステップのノードを選んだときに右の欄の詳細に出す。

**関数のページ**は、関数を根にしたトレースである。
「呼び出し元」は右の欄のタブとして残し、図が見せている関数の呼び出し元を出す。
そこから上の関数へ移るときは経路を捨てる（上へ向かう移動はトレースの定義に合わない）。

**このPRの変更**のページは、レビューの入口にする。
先頭に「説明の無い変更」を置き、続けて変わった関数ごとに、木の差分の要約、差分、変更メモ、そして「届く経路」（エンドポイント › ステップ › … と、そこに至る決定）を並べる。
届く経路を押すと、そのエンドポイントのトレースが変更まで展開され、決定が選ばれた状態で開く。
PR のコメントに書く Markdown の形は「変更メモと影響範囲」の節のとおりにする。

**コードの Drawer**は残し、アウトラインの各行からその行へ飛べるようにする（実装では行から飛ぶのをやめ、行のコードはその行の `</>` で読む。後述の「残る細部」）。
変わった関数には「差分 / 変更後の全文」の切り替えを足す。

## データとビルド

読み取りは、TypeScript のコンパイラ API を使う解析器に置き換える。
解析器は `packages/` の非公開のワークスペースパッケージ（名前は仮に `@maronn-openid-connect/map-analysis`）に置き、`apps/map` は表示だけを持つ。
解析側が持つのは、木の読み取り、木の差分と式の差分、影響範囲の計算、変更メモの解析と雛形の生成、`map.json` と関数ごとのファイルの書き出しである。
表示側が持つのは、アウトライン、図、決定の選択、ハッシュである。
解析器は各ルート（`packages/core`、`packages/experimental`、`packages/google-login`、`apps/hono`、`apps/nextjs`）の既存の `tsconfig.json` からプログラムを作り、関数ごとに木を出す。
呼び先の解決は型で行い、resolver や store のメンバーも受け取りの型から引く（名前の末尾で推定する規則は要らなくなる）。
関数の id はいまのカタログと同じ `<root>:<module>#<name>` にし、CLI のカタログ（`calls` と `calledBy`、`explain` が使う）と一致することをテストで確かめる。
CLI 側の字句解析による流れの読み取り（`extract/function-flow.ts`）は、地図が使わなくなった時点で消す。
解析器を標準のコンパイラ API に寄せるのは、正確さのためだけではない。
手書きの字句解析と文の読み取り（約 1,000 行）を拡張するより、コンパイラの構文木を歩く方が、地図の実装に加わる人にとって見通しがよい。

出力は二層にする。

- `data/map.json`：エンドポイント、関数の札（名前、要約、呼ぶ関数、外へ出る失敗、変更の要約）、機能、変更メモ。木は含めない
- `data/functions/<id のハッシュ>.json`：関数の木と、変わった関数なら変更前の木、差分の印、ノードごとの hunk。トレースで開いたときに読む

これで初期の読み込みは小さくなり、`controlFlows`（3.7 MB）と `edgeSets` は無くなる。
エンドポイントの木は、ステップの印と機能の札を持つ一本だけである。

型と関数名の整理は次のとおり。

- `FunctionFlow`（平らな `nodes` と `edges`）は `FlowTree` に置き換える。図はビルド時ではなく画面側で平らにする
- `FunctionChange` には `hunks` の代わりに、ノード id をキーにした差分の印と hunk、言葉の要約、`treeBefore` を持たせる
- `MapChanges` と変更メモの扱いは変えない

## 捨てるものと残すもの

捨てるもの。

- 道筋の列挙によるケース（`deriveCases`、`exitCases`、`activeOf`、`CasePicker`）。いまの `diagram.ts` の `activeOf` は名前が同じ別の関数で、選んだ決定で走るノードから図の箱と矢印を求める
- 機能の組み合わせごとの `controlFlows` と `edgeSets`
- 字句解析の流れの読み取り（`function-flow.ts`、`endpoint-flows.mjs`）
- 行の一致で札を付ける `nodeMark`、最短経路だけを返す `changesBelow`
- いまのハッシュの形（互換は取らず、新しく決める）

残すもの。

- 関数カタログ（`functions.ts`）と、CLI の `explain` / `graph`
- 変更の集め方（`changes.mjs` の git の差分、関数ごとの比較、変更メモの解析）。木の差分はこの上に足す
- 図の自動配置（Dagre）、三色の規則、札を灰色の濃淡で描く規則
- Shiki によるハイライトと、ソースをファイルごとに分けて置く仕組み

## 進め方

破壊的に変えてよいとしても、順序は要る。
前の段が後の段の土台になるように、四段に分ける。

1. **解析器と木**：TypeScript の解析器で全関数の木を出し、いまの平らな流れと（呼び出しの順、条件の数、終わりの数で）突き合わせるテストを書く。画面は木を平らにして今のまま動かす。ここで `controlFlows` と `edgeSets` を落とす
2. **トレースと決定**：アウトラインと決定の選択を入れ、ケースの列挙を消す。関数のページとエンドポイントの画面をトレースに統合する
3. **木の差分とレビュー**：変更前の木、ノード単位の差分、要約、経路の差分、「このPRの変更」の届く経路。過去にマージした PR をいくつか選び、その親との差分で地図を作って確かめる（`MAP_BASE=<親のコミット>` で手元に作れる）
4. **失敗の流れと仕上げ**：外へ出る失敗の計算、エラー時の表示、式の中の差分、スマートフォンの表示

第 1 段が終わった時点で、`/token` と `/authorize` のケースが名前付きで出ることを計測で確認する（いまの計測の指標を `scripts/` の検査として残す）。
この検査は地図の出力に対するもので、貢献者の PR を落とすためのものではない。

## 縮小案との関係

既存の作りを活かすなら、次の部分的な修正で症状の多くは抑えられる（前回の案）。

- 任意項目の条件を一つの箱に畳み、エラーを「エラー時」の修飾に戻す。これで exit ケースになる 52 関数のうち 36 個が収まり、`/token` は 7 ケースになる
- 関数のページに経路（どのステップから来たか）をハッシュとパンくずで持たせ、経路に沿うケースを既定で選ぶ
- 下で変わった関数の一覧に差分を折りたたんで埋め込み、経由に分岐のラベルを添える
- 変えた行を「箱の行と一致」ではなく「箱が受け持つ行の範囲」で札にする

しかし、この修正では道筋の列挙の上限が残る（16 関数は収まらない）、関数をまたぐ読みは依然としてページの移動になる、箱の無い行の変更は「付近を変更」という弱い札にしかならない。
本文のモデルは、これらを木、トレース、木の差分でそれぞれ無くす。
縮小案の各項目は、本文のモデルの中では「決定の既定値」「変更に至る道筋」「ノードの行の範囲」として自然に含まれる。

## 決めたこと

設計の相談で決まったことを、実装に入る人のために残す。

- JSDoc の一行目の lint は続ける
- `function` 宣言の規則は緩めない
- 変更メモは意図と背景を書く場所とし、何を変えたかとどこに効くかは地図が計算する
- 説明の無い変更で CI を落とすのは、届くエンドポイントがある関数の変更と、エンドポイントの処理の変更に限る
- 見出しは人が名前で書ける形を保ち、id は雛形が HTML コメントで添える。生成した節は消さない運用とし、消せば検査で落ちる
- アウトラインを主、図を従にする
- 解析は `packages/`、表示は `apps/map`
- 旧ハッシュとの互換は取らない
- 木の差分は式の中（演算子、リテラル、引数）まで取る
- 「変更まで展開」に深さと件数の上限を設けない
- 図は流れの形を描き、文はアウトラインが読む。図はアウトラインと同じく畳み、エンドポイントの本体はステップの箱の列にする
- アウトラインの行も図の箱も一行にする。収まらない分はカードと `</>` で読む。関数の中もエンドポイントと同じ読み方にする（言葉の無い文の続きは一行にまとめ、`return` は返す名前で言う）
- 図は箱の見出しが 11px 以上になる倍率（11/12.5）より小さくは開かない。欄に収まらない幅は横に動かして読む
- アウトラインは自然言語の一行を基本にし、コードは言葉が無い所と読者が開いた行にだけ出す。ステップは見出しに畳む
- 分岐の選択は行を消さず、選ばなかった側を不活性（灰色）にする
- 図の箱のクリックは選ぶだけにし、関数へ潜るのは重ねたときのカードのボタンから行う。図の上にパンくずを置く
- `try` は図の箱にせず、捕まえる範囲を囲む枠にする
- アウトラインと図の欄の幅は読者が変えられる（幅の仕切り。最初の検討では、アウトラインを主にするため外していた）
- 右の欄のタブ（図、差分、詳細、関数のページの呼び出し元）は、どれも図が見せているフレームについて述べる。詳細は選択が無くてもそのフレームを出し、選んだ行はその下に足す（行を選ばないと詳細が出ない作りはやめた）
- 欄は図のタブで始まり、読者が選んだタブを保つ。行や箱を押してもタブは変えず、右の欄がその行のフレームに移る（「左側を押したらまず図」は、最初のタブを図にし、図をその行へ動かすことで満たす）
- アウトラインと図は同じ規則でステップと守りを畳み、読者がステップを開け閉めした記録を一つにする。ステップは、PR の変更、下に開いたフレーム、選んだ決定を中に持つと開いて始まる。守りと任意項目の `if` は、変更が無く、成立側にフレームのある関数の呼び出しも決定も無いときだけ一行に畳む
- 呼び出しに「ここで失敗する」側（`fails`）を置く。「失敗で終わる」の選択は、失敗までの呼び出しをどれもこの側にする
- interface のメンバーを通る到達は、実装が呼ぶ先までたどる。アプリ（`apps/hono`、`apps/nextjs`）の実装は、そのアプリのエンドポイントにだけ届く
- hunk は変えた行の続きごとに、それを含む最小のノードに付ける。PR の札は、アウトラインの行と図の箱で同じ規則にする
- CI を落とす「届く変更」は、型で引ける呼び出しで届くものに限る。コメントや書き方だけの変更と、追えない呼び出しのほかからは届かない変更は、一覧と PR のコメントに出すだけにする

## 残る細部

設計の時点で決めずに残した細部は、実装で次のとおり決めた。
数値は 2026-11-04 に、全機能オンでビルドした地図で測った。

- 解析のパッケージの名前は仮の名前のまま `@maronn-openid-connect/map-analysis` とした
- 式の差分は、前後のコードを字句に分けて順序を保って対応づける（`packages/map-analysis/src/diff.ts`）。コメント、改行、末尾のカンマと文末のセミコロンは比べない。括弧が閉じるまで違う区間をつなぎ、違う区間が 4 つ以上あるか、置き換えた字句の数が 4 と短い方の半分の大きい方を超えるか、まるごと足したか消したコードが 30 字句を超えると「式を書き換えた」として前後を並べる。それ以下なら、置き換えは「`<` を `<=` に変えた」と言い、足した部分と消した部分はソースのその部分をそのまま引く（「`.trim()` を足した」）。同じ言い方が二か所以上なら一度だけ言い、（n 箇所）を添える
- 同じフレームで名前が重なる選択は、`try` の最初の呼び出し、その呼び出しの書き方、終わる場所の順で区別する。最後の手段の番号（`… (2)`）は、地図の検査で重なった名前として数える
- 「変更に至る道筋」は、関数の中の変えたところ（宣言、変えたノード、消したノードの位置）ごとに求め、何を変えたかの言葉を添える。同じフレームを開いて同じ側を選ぶ道筋は、よく使う選択では一つにまとめる
- 仮想スクロールは入れていない。行は開いたフレームの分だけ作り、最も大きいフレーム（`nextjs:app/authorize/route.ts#authorize`）でもノードは 137 個である
- 「失敗で終わる」に並べる、呼び先から伝わる失敗は、エラーと投げる関数の組ごとに一つにし、画面ではエラーごとにまとめる。`/token`（hono）では 104 組（エラーは 35 種）になる
- 下の変更の集計は、設計では深さを限るとしたが、「変更まで展開」と同じく下のすべての変更に及ぶようにした。interface のメンバーの呼び出しでは、変えた実装のうち、そのメンバーの実装の行の範囲にある変更だけを数える
- コードの Drawer は関数を単位に開き、アウトラインの行からその行へ飛ぶことはしていない。行のコードは、その行の `</>` で読む
- データのビルドは、ディレクトリを消さずにファイルをその場で書き、前のビルドの残りだけを最後に消す。開発サーバーが動いたままでもデータを作り直せるようにするためである
- 図の読みやすさ（全機能オンの 1,036 フレームを、ページが開くときの畳み方で測った。1440x900 の欄の図は 472x631、幅に合わせた倍率）：見出しが 11px 以上のフレームは 1,008（97.3%）、9px 未満は 21（2.0%）。畳む前の図では 468（45.2%）と 514 だった。成立側でフレームのある関数を呼ぶ守りを畳まなくしたので、この規則の前の 1,016（98.1%）から少し減った
- エンドポイントの根 34 個のうち 32 個が 11px 以上で開く（畳む前は 7 個）。残る二つは Next.js の `app/login/actions.ts#loginAction`（8.5px）と `app/(google-login)/login/google/route.ts#POST`（9.7px）で、0.88 倍で開いて横に動かして読む
- `/token`（hono）は 21 箱・12.5px・欄 1.95 個分（既定の機能では 16 箱・欄 1.5 個分）、`/token`（Next.js）は 22 箱・欄 2.03 個分で、根のうちで最も長い。畳む前は、hono が 59 箱・4.6px、Next.js が 102 箱・2.7px だった
- 1280x800 の欄（405x531）とスマートフォンのドロワー（389x702）で、幅に合わせて 11px に届くのは 81.7% と 81.3%。残りは 0.88 倍で開き、横に動かす必要があるのは 5.5% と 7.6%（1440x900 では 2.6%）
- 箱の幅は欄の幅で変えない。どの欄でも同じ配置にするためで、狭い欄は開く倍率の下限で補う
- 箱が 24 を超える関数（16 個）は、まっすぐな区間を一つの箱にまとめていない。最も多い `verifyIdJagAssertion` は、フレームのある関数を呼ぶ守りを畳まないので 69 箱になり、幅に合わせると 3.2px、0.88 倍で開くと欄 4.5 個分の高さで、横にも動かして読む
- 条件や `throw` の直前に呼ぶ関数と、`return` がそのまま返す呼び出しは、アウトラインではその行が受け持ち（▸ で開く）、ほかに先に評価する呼び出しは「先に」の行になる。図ではどれもその箱に含め、カードの「中の流れを見る」から開く
- すぐ終わる `catch` は、アウトラインでも図でも一行にする。その中のステップを読者が開くと、両方とも行に開く
- 図の検査（`src/lib/diagram.data.test.ts`）は、決定と終わりがどれも箱、行、畳んだステップのどれかにあること、`try` の枠が自分の箱だけを囲むこと、図がステップと守りをアウトラインと同じに畳むこと（変更の無いときと、九つ目ごとのノードを変えたとき）、11px に届くフレームが 9 割を下回らないことを確かめる。数値は貢献者のコードで変わるので、それ以上の閾値は置かない
