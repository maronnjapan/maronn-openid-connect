# 実装方針: 想定リクエストから読む地図とテスト

地図（`apps/map`）、テストの画面（`apps/tests`）、PR のコメントを、「想定するリクエスト」を起点に読める形へ組み替える。
あわせて、コードを別タブで速く読めるページを足す。
この文書は実装の指示書で、実装はまだ無い。
別のセッション（Claude Code、Codex）がこの文書を読んで実装する。

## 実装するセッションへ

- 「進め方」の段を一つずつ、段ごとに一つの PR にする。段の「終わりの確かめ方」を満たしてから次へ進む
- 規則と手順は `skills/provider-map-implementation/SKILL.md` に従う。この文書と食い違うときは、この文書の「書く量を増やさない」を優先する
- 依存は pnpm 11 で入れる（CI の Corepack の既定。pnpm 10 の `pnpm install --frozen-lockfile` は overrides の不一致で落ちる）
- 手元で計測つきのデータを作るには、`MARONN_REACH=1 MARONN_TEST_REPORTS=$PWD/work/test-reports pnpm --filter @maronn-openid-connect/app-hono test` の後に `MAP_TEST_REPORTS=$PWD/work/test-reports pnpm run build:map` を実行する（CI の `test` ジョブと `map` ジョブと同じ変数）
- PR #207 は閉じる予定である。そのブランチのコードを前提にせず、取り込まない

## 解決したいこと

地図とテストの画面の目的は、コードレビューの負荷を下げることである。
全体像と、個々の処理が何をしているかを、コードを全部読まずに把握したい。
いまの画面は、次の問いに答えにくい。

| 問い | いまの答え方 | 足りないこと |
|---|---|---|
| このリクエストを送ると、何が起きて何が返るか | ステップの一覧と、コードの分岐から選ぶ道筋 | リクエストから選べない。返るものが出ない |
| PAR のリクエストだと、通常と何が違うか | 機能の札と、全ステップの一覧 | そのリクエストで働くステップと素通りするステップが同じ重さで並ぶ |
| このステップは、このリクエストで何をしたか | ステップを開いて全分岐を読む | 通らなかった行も並ぶ |
| このリクエストについて、何がテストされているか | エンドポイントの全テストと、コードの道筋ごとの数 | テストがリクエストに結び付いていない |
| テストは必要なパターンを満たしているか | 失敗ごとの印（✓ △ ✗） | 何が「必要なパターン」かの一覧が無い |
| この PR で、何の振る舞いが変わるか | 変わった関数の表 | 関数の数が多いと読めない。リクエストの言葉になっていない |
| 動きは分かった。コードはどうなっているか | Drawer、GitHub、手元のエディタ | Drawer は関数単位。GitHub は遅い。手元は準備が要る |

## 現状の計測

全機能オンでビルドした地図（`main`、2026-11-20）を、ブラウザで開いて確かめた。

- 道筋の名前は、ステップの見出し、コードの条件（`'kind' in parsed: 成立`、`silent !== undefined: 成立 › 'kind' in silent: 成立`）、投げる関数（`validateMaxAge から`）である。「PAR でプッシュしたリクエスト」のようにリクエストを言う名前は無い
- フローの既定の道筋「おまかせ」は、決まっていない分岐を仮の側へ進む。既定の機能の `/authorize` では、18 場面のうち 8 個の分岐が仮である。つまり既定の再生は、実在するどのリクエストの動きでもない
- アウトラインは 20 ステップを同じ重さで並べる。通常の認可コードのリクエストでは、PAR、Request Object、JARM、`form_post`、フラグメント、インプリシット、ハイブリッドのステップは何もせずに次へ進むが、画面からは分からない

- リクエストの単位の振る舞いを最も多く確かめているのは、処理本体を直接呼ぶテストである。hono の `/authorize` では、HTTP で送る `page.test.ts` が 10 件、`processAuthorizationRequest(c)` を直接呼ぶ `pipeline.test.ts` が 38 件ある。後者はカタログでは `processAuthorizationRequest` のユニットテストである
- テストの数は、hono が API 203 とユニット 1,573、Next.js が API 23 とユニット 756、E2E が 158 である
- PR #205（DPoP）のコメントは、関数 154 個の表（40 行で打ち切り）、関数の外の変更があるファイルの列挙、エンドポイントごとの追加テストと関連関数の列挙からなる。discovery のテスト 1 件の期待値の変更だけで、数千字の差分が本文に入っている
- コメントは、コード 1 行あたり `apps/hono/src/oidc-provider` で 0.64 行、`packages/core/src` で 0.82 行ある（テストを除く。大半は JSDoc で、行内の `//` は 0.10 行と 0.05 行）。変更メモ（`apps/map/changes/`）は 13 ファイルで 1,458 行ある
- テストに付いた注釈のコメントは、`// @feature` が 28 件で、ほかは数件である

## 原因

症状は別々に見えるが、原因は一つである。
**読む軸が、コードの形（ステップ、分岐、関数）だけである。**

地図の道筋は、木の分岐から計算する。
これは正確で漏れが無いが、読者が持ってくる問いは「このリクエストだと」で始まる。
コードの分岐の名前から、それがどんなリクエストに当たるかを読者が逆算している。
欲しいのは逆で、リクエストを選ぶと道筋が出ることである。

## 設計の方針

**想定リクエスト**を、地図、テスト、PR の三つに共通の、もう一つの軸として足す。
コードの軸（アウトライン、決定、道筋）は残し、置き換えない。

想定リクエストは「こういう前提で、こういうリクエストを送ると、こう返る」を一件で言うものである。
例：「PAR でプッシュ済みの `request_uri` を渡す → ログイン画面へ 302」。

方針は五つである。

1. **定義は人が読める一覧に置く。** エンドポイントごとに、想定リクエストの名前と期待する結果を、YAML に一件数行で書く。これが「どんなパターンを想定しているか」の一覧になる
2. **結び付けは宣言と観測で行う。** 想定リクエスト一件につき、代表のテスト一つがコメント一行で宣言する。ほかのテストは、代表と同じ道筋を通ったかで結ぶ。テストの名前やパラメータから推測しない（既存の「規則であって推測ではない」という方針に合わせる）
3. **道筋は観測で求める。** 宣言したテストが実際に送ったリクエスト、返った応答、その間に動いた行から、通ったステップと行を求める。仮の分岐は無い
4. **差を見せる。** 想定リクエストごとに、ステップを「働いた」「素通りした」「通らない」に分ける。基準の想定リクエスト（通常の認可コード）との違いを一行で言う
5. **書く量を増やさない。** 書くのは観測できないことだけにし、書いたものは観測と照らす（次の節）

識別子は `premise` とする。
`scenario` は Gherkin のタグ `@scenario:`（`.github/scripts/lint-features.mjs` の `SUBJECT_PREFIXES`）、`case` は `EndpointCase` と `TestCase`、`scene` はフローの場面が使っているので避ける。
画面の言葉は「想定リクエスト」である。

## 書く量を増やさない

この設計で最も避けたいのは、画面を良く見せるための文章が増えることである。
文章は生成 AI が書くので、量を求めるほど、読まれない説明と、コードと食い違う説明が増える。
「現状の計測」のとおり、コメントはすでにコードの 6〜8 割の行数がある。
この設計は、説明の文章を足さずに成り立つようにする。

**書くのは、観測できないことだけにする。**
想定リクエスト一件につき書くのは、名前の一行、まとまり、期待する結果（閉じた語彙）と、代表のテストのコメント一行である。
リクエストの中身、前提、通るステップ、要る機能、仕様の節は書かない。
どれも、記録したリクエストと、すでにあるステップの `meta` から出せる。

**表示の言葉は、すでにあるものから作る。**
想定リクエストの表示の行は、次の三つだけで作る。

- ステップの見出し：`meta` の `label`
- 呼び出しの行：呼ぶ関数の JSDoc の一行目（lint がすでに求めている）
- 条件の行：条件のコードと、実際に通った側（`pushedParams === null → 不成立`）

条件の手前のコメントは、行の言葉に使わない（重ねたときの表示と `</>` で読める）。
行が動いたものだけに減るので、条件をコードのまま出しても読める。
こうしておけば、表示を良くするために行内のコメントを足す理由が無くなる。

**書いたものは、観測と照らす。**
期待する結果は観測した応答と、宣言は観測した道筋と照らし、食い違えばビルドが警告する。
照らせない自由記述の欄（前提の説明、リクエストの説明、期待の説明）は作らない。

量の見積りと歯止めは次のとおりである。

- 想定リクエスト一件につき、YAML 4 行とコメント 1 行。`/authorize` に 40 件あれば、160 行と 40 行である
- `title` は 40 字までとし、lint で落とす
- `// @premise` の行には id（と番号）しか書けない。説明を続けると lint で落とす
- PR のコメントに、その PR が足したコメントの行数とコードの行数を一行で出す（「コメント +412 行、コード +380 行」）。検査では落とさず、レビューで気づけるようにする
- `skills/provider-map-implementation/SKILL.md` に「地図やテストの画面の表示を良くする目的で、コメントや説明の欄を足さない」と書く

## 1. 想定リクエストの定義

`tests/catalog/premises/<endpoint>.yaml` に置く（`tests/catalog/aspects.yaml` の隣）。
定義はフレームワークに依らず、hono と Next.js で共有する。

```yaml
endpoint: authorize
baseline: code-pkce          # 差を言うときの基準
premises:
  - id: code-pkce
    title: 認可コード + PKCE で送る（未ログイン）
    group: 基本
    expect: login

  - id: par-pushed
    title: PAR でプッシュ済みの request_uri を渡す
    group: PAR
    expect: login

  - id: par-used
    title: 使用済みの request_uri を渡す
    group: PAR
    expect: error invalid_request_uri page
```

- `title` は人が読む一行である。機械は解釈しない。自由に書ける欄はこれだけである
- `expect` は閉じた語彙で書く。エンドポイントの処理結果の種類に対応させる（`/authorize` なら `AuthorizationOutcome` の `kind`）。`login`、`consent`、`code`、`error <コード> <返し方>`（返し方は `redirect`、`page`、`json`）などである。語彙はエンドポイントごとに `packages/test-catalog` に定義し、ビルドが観測した結果と照らす。画面の言葉（「ログイン画面へリダイレクトする」）は語彙から作る
- `group` は一覧のまとまりである（基本、PAR、Request Object、Implicit、Hybrid、prompt と SSO、エラー）
- id はエンドポイントの中で一意にし、全体では `<endpoint>/<id>`（`authorize/par-pushed`）と書く
- 要る機能は、働いたステップの機能の札から求める。仕様の節は、働いたステップの `spec` から求める

最初の一覧は人が書かない。
記録したリクエストを道筋の印（次の節）でまとめ、YAML の雛形を書くコマンドを足す（`pnpm --filter @maronn-openid-connect/map premises:draft`、既存の `changes:draft` と同じ考え）。
雛形は、まとめごとに `expect` を観測から埋め、代表のリクエストとテストの名前を HTML コメントで添える。
`title` は、実装するセッションがテストと仕様から書き、人は一覧を見て直す。

## 2. テストとの結び付け

想定リクエスト一件につき、代表のテスト一つが、`it` の直上のコメントで宣言する。
既存の `// @feature par`、`// @aspect boundary`、`// @test-id` と同じ読み方である（`packages/test-catalog/src/read-code.ts`）。

```ts
// @premise authorize/par-pushed
it('should expand a pushed request_uri into the pushed parameters', async () => { ... });
```

代表にできるのは、そのエンドポイントの処理本体を走らせるテストである。
HTTP で送るテスト（`app.request(...)`）でも、処理本体を直接呼ぶテスト（`processAuthorizationRequest(c)`）でもよい。
応答まで出せるので、両方あるときは HTTP で送るテストを代表にする。

- 一つのテストが同じエンドポイントの処理本体を何度も走らせるときは、最後の一回を採る。準備が先に来るからである。別の回を採るときは `// @premise authorize/par-used #2` と番号を書く
- 機能ファイルでは `@premise:authorize/par-pushed` のタグにする
- E2E テストも宣言できる（`// @premise authorize/par-pushed token/code-pkce`）。E2E は一覧に「宣言したテスト」として並ぶだけで、道筋は求めない（OP の計数がテストの単位で、リクエストごとに分けられないため）

ほかのテストは宣言しない。
ビルドが、記録した一回ごとの実行を**道筋の印**でまとめる。
道筋の印は、エンドポイントの処理本体でのステップの状態の並び、処理が終わったノード、結果の種類（`expect` の語彙）である。
代表と同じ印の実行をしたテストを、その想定リクエストに結ぶ。

結び付きは、確かさで二つに分ける（失敗とテストの結び付けと同じ考え）。

- **宣言したテスト**：その想定リクエストを確かめると宣言している
- **同じ道筋を通るテスト**：道筋と結果が同じである。何を確かめるつもりかは分からない

同じ印の想定リクエストが二つ以上あるとき（パラメータの値だけが違うもの）は、同じ道筋を通るテストをどれにも並べる。
区別したいテストにだけ、宣言を足す。
どの想定リクエストの印とも合わない実行は「未分類」である。
未分類は新しい想定リクエストの候補で、`premises:draft` が雛形にする。

未分類は検査で落とさず、数を画面と PR のコメントに出す。
一覧に無い id を宣言したとき、同じ id の定義が重なるとき、`// @premise` の行に id と番号のほかを書いたときは、`.github/scripts/lint-tests.mjs` で落とす。

## 3. 記録

計測した実行（`MARONN_REACH=1`）で、テストがエンドポイントの処理本体を一回走らせるごとに、何を送り、どの行が動き、何が返ったかを記録する。
`packages/test-reach` の Vitest の計測を広げて作る。
テストのコードと OP のコード（CLI が抽出する根）には手を入れない。

### いまあるもの

`packages/test-reach/src/vitest-setup.js` は、テストの前後で Istanbul の関数の計数（`globalThis.__VITEST_COVERAGE__` の `f`）の差を取り、動いた関数を元のソースの位置にして書き出す。
同じ計数の対象に、文（`s`、`statementMap`）と分岐（`b`、`branchMap`）もある。

### 足すもの

- **区切り**：テストが `Request` を作った時点を、一回の実行の始まりにする。計測の setup が `globalThis.Request` を、作られたことを控えるサブクラスに差し替え、その時点で計数の写しを取る。次の `Request` かテストの終わりまでが、一回分である
- **リクエスト**：そのとき作られた `Request`（メソッド、URL、ヘッダー、本文）
- **応答**：一回分の間に作られた `Response` のうち最後のもの（ステータス、ヘッダー、本文）。`globalThis.Response` も同じように差し替える。処理本体を直接呼ぶテストでは `Response` が作られないので、応答は無い
- **動いた行**：一回分の間に計数が上がった文と分岐を、元のソースのファイル、行、桁にしたもの。位置の戻し方は、いまの関数と同じである（`source-map.js`）
- **走った根**：一回分の間に計数が上がった、エンドポイントの処理本体の関数と、その回数

一回分は、エンドポイントの処理本体がちょうど一つ、ちょうど一回走ったときだけ使う。
走っていない一回分（ステップのユニットテストが文脈のために作る `Request`）は捨てる。
二回以上走った一回分（`Request` を先にまとめて作るテスト）は「区切れない」として数え、道筋には使わない。

本文は 16 KiB で切る。
書き出しは、いまの到達の記録の隣に、テストごとの一行として置く（`runs/vitest-<pkg>.jsonl`）。
動いた行は、ファイルごとの行の範囲と、分岐ごとの通った側にまとめて書く。

### 試して確かめたこと

`globalThis.Request` と `globalThis.Response` をサブクラスに差し替えて、hono の二つのテストファイルを走らせた（2026-11-21、テストはすべて通る）。

| ファイル | テスト | 控えた `Request` | 控えた `Response` |
|---|---|---|---|
| `endpoints/authorize/page.test.ts`（`app.request(...)` で送る） | 10 | 10 | 10 |
| `endpoints/authorize/pipeline.test.ts`（処理本体を直接呼ぶ） | 38 | 39 | 0 |

HTTP で送るテストは、リクエストと応答が一対ずつ取れる。
処理本体を直接呼ぶテストは、リクエストだけが取れる。
計数の写しを `Request` を作った時点で取ることと、Next.js のテストでの動きは、まだ試していない。

### カタログへの読み込み

`packages/test-catalog/src/run.ts` が `runs/*.jsonl` を読み、テストの id と関数カタログに結ぶ（いまの `reach/*.jsonl` と同じ流れ）。
木のノードが動いたかは、そのノード自身の行に動いた文があるかで決める。
決定の側は、分岐の計数から読む。
同じ行に `if` と `return` が並ぶ守り（`if (pushedParams === null) return params;`）を見分けるため、`packages/map-analysis` の木のノードに始まりの桁を足す（`TreeNode` はいま行だけを持つ）。

## 4. 観測した道筋

想定リクエストごとに、次を求める。

- **代表の例**：宣言したテストの一回分。宣言したテストが複数あれば、応答のあるもの、次にファイルと行の順で最初のもの。ほかは「ほかの例」として持つ
- **先に送ったリクエスト**：同じテストが代表の例より前に送ったリクエストと応答を、一行ずつ（`POST /par → 201`）。前提として出す
- **動いた行**：ファイルごとの行の範囲。アウトラインの行とコードを読むページの印に使う
- **ステップの状態**：下の規則で決める
- **選んだ側**：決定ごとの通った側。条件の行とフローの再生に使う
- **結果の種類**：`expect` の語彙。応答があれば応答から、無ければ処理が終わった `return` のノードから決める

### ステップの状態

| 状態 | 規則 |
|---|---|
| 通らない | そのステップのブロックの文が一つも動いていない |
| ここで失敗 | ステップの中の `throw` が動き、ステップの次のノードが動いていない |
| ここで応答 | パイプラインが、そのステップのブロックの中か直後の `return` で終わった |
| 素通り | ステップの関数が、最後の文より前の `return` で終わり、その `return` が値を返さないか、`undefined`、`null`、自分の引数の名前をそのまま返す |
| 働いた | 上のどれでもない |

素通りの規則は、機能のステップの書き方に合わせてある。
`resolvePushedAuthorizationRequest()` は、`request_uri` が PAR の URN でなければ `if (pushedParams === null) return params;` で終わる。
`resolveFormPostResponseContext()` は、`response_mode=form_post` でなければ `undefined` を返す。
規則で読めないステップは「働いた」に倒す。
素通りと誤って畳むと処理を見落とすが、働いたと誤っても一行増えるだけだからである。

同じ想定リクエストを宣言したテストの間で道筋の印が食い違えば、ビルドが警告する。
その想定リクエストは二つに分けるべきだという合図である。
`expect` と観測した結果の種類が食い違うときも警告する。

### データ

- `apps/tests/public/data/tests/premises/<hash>.json`：エンドポイント一つ分。想定リクエストごとに、定義、宣言したテストと同じ道筋を通るテストの id、代表の例とほかの例、先に送ったリクエスト、ステップの状態、選んだ側、基準との違い
- `apps/map/public/data/premises/<framework>--<endpoint>.json`：同じ内容から、地図とコードを読むページが使う分（定義、代表の例、先に送ったリクエスト、ステップの状態、選んだ側、動いた行）
- 索引（`tests.json`、`map.json`）には、エンドポイントごとの想定リクエストの数と url だけを置く

計測した実行が無いビルド（手元の `pnpm run build:map`）では、定義と宣言だけが入る。
道筋は「計測なし」と表示し、いまの道筋の選択へ案内する。

エンドポイントの画面の最初の選択を、想定リクエストにする。

- ② の行の言葉は、「書く量を増やさない」の三つの出どころ（ステップの見出し、呼ぶ関数の JSDoc の一行目、条件のコードと通った側）で作る
- 出すのは動いた行だけである。いまのアウトラインは通らない行を灰色で残すが、想定リクエストの表示では出さない
- 働いたステップは開いた状態で、その中の動いた行を二段まで出す。それより下は ▸ で開く
- 素通りのステップは「素通り n」の一行に畳み、開くと、どの `return` で終わったかをコードで言う（`pushedParams === null → params を返す`）
- 通らないステップは出さず、数だけ言う
- 「全部の行を出す」で、いまのアウトライン（通らない行は灰色、言葉もいまのまま）に切り替える。レビューで、通らなかった分岐を確かめるためである
- ① は代表の例のリクエストをそのまま出す。長い値（JWT、トークン）は省略し、押すと開く。複数の例は ‹ › で切り替える
- ③ は代表の例の応答をそのまま出す。代表が処理本体を直接呼ぶテストで応答が無いときは、結果の種類の言葉と、処理が終わった `return` の行を出し、「HTTP の応答は記録なし」と添える
- 「比べる」で、もう一つの想定リクエストを選ぶと、状態の違うステップだけに印を付けて左右に並べる
- フロー（`;p`）は、想定リクエストを道筋として再生する。選んだ側は観測なので「仮」の札は出ない
- ハッシュに想定リクエストを書く（`#hono--authorize;r=par-pushed`）
- Express と Fastify は、生成元である hono の記録を使う。Next.js は段 7 で足すまで「計測なし」と出す

想定リクエストの一覧（選択を開いたとき）は、まとまりごとに並べ、期待する結果とテストの数を添える。
宣言したテストの無いものには「テストなし」と出し、選ぶと定義だけを表示する。

`packages/test-catalog/src/`（`premises.ts` を足す。`read-code.ts`、`read-feature.ts`、`run.ts`、`model.ts`、`build.ts`）、`apps/tests/src/components/EndpointPage.tsx`、`CasePanel.tsx` の隣に新しい部品。

## 7. コードを読むページ

動きが分かった後に、コードの中身を速く読めるようにする。
新しいアプリ `apps/code`（Vite と React、`apps/tests` と同じ作り）を、地図と同じ Worker の `/code/` で配る。

### 配り方とデータ

- 地図のビルドが `apps/code` をビルドし、`dist/code/` に写す。`apps/map/scripts/copy-tests-viewer.mjs` と同じ段にする
- ハイライト済みのソースは、地図のデータをそのまま読む（`../data/sources/<hash>.json`。`code`、`tokens`、`foreground`、`background`、`features` を持つ。いま 458 ファイル）。ブラウザでは解析しない
- 索引は、地図のデータの段が `apps/map/public/data/code.json` に書く。ファイルの一覧（パスとソースの url）と、関数の一覧（id、名前、ファイル、行の範囲、`calls`、`calledBy`）である。`map.json`（3.3 MB）は読まない
- 動いた行は、4 節の `data/premises/` から読む

### 画面

- 地図とテストの画面の「コードを読む ↗」「`</>`」から、ファイルと行を指して別タブで開く（`/code/#apps/hono/src/oidc-provider/features/par/steps/resolve-pushed-request.ts:L52-L74;r=hono--authorize--par-pushed`）
- 左にファイルの木（地図の根だけ）と、想定リクエストを選んでいれば「このリクエストで動いたファイル」を通る順に並べる
- 想定リクエストを選ぶと、動いた行に印を付け、動かなかった行を薄くする
- 関数の名前を押すと定義へ移る。呼び出し元の一覧も出す
- ファイル名と関数名で検索できる
- PR のビルドでは、変わった行に印を付ける
- 機能に属する行の印（いまの Drawer の線と札）をそのまま出す
- 手元のエディタで開くリンクを添える。設定にリポジトリのパスを入れると、`zed://file/<パス>:<行>` と `vscode://file/<パス>:<行>` のリンクが出る（設定はこのブラウザに残す）。未設定なら `https://github.dev/...` を出す

### 定義への移動

二段に分ける。

1. **関数単位**：関数カタログの `calls` と `calledBy` で引く。関数の宣言と呼び出しの名前が押せる
2. **識別子単位**：ビルド時に TypeScript の型検査器から「識別子の位置 → 宣言の位置」の表を作る（`packages/map-analysis` はすでに各根のプログラムを作っている）。ファイルごとに `data/symbols/<hash>.json` に書き、型、定数、interface のメンバーにも飛べるようにする。根の外（`node_modules`）への参照は表に入れない

いまの地図の Drawer とテストの画面のコードの欄は残す。
どちらにも「別タブで読む ↗」を足す。

## 8. PR

### 地図の「このPRの変更」

先頭に「この PR で動きが変わる想定リクエスト」を置く。

- **足した想定リクエスト**：YAML の差分で分かる
- **動きが変わる想定リクエスト**：その想定リクエストで動いた行と、PR が変えた行が重なるもの
- **どの想定リクエストも通らない変更**：変えた行のうち、どの想定リクエストでも動かなかった行。リクエストの単位では確かめられていない変更なので、レビューで見る場所になる

それぞれから、変えた行に印を付けた想定リクエストの表示へ移れる。
いまの関数の一覧と届く経路は、その下に残す。

- テストの期待の変更は、変わった語だけを出す（いまは期待の全文を前後とも出す）
- 検査が落ちたときの「説明の無い変更」と雛形は、いまのとおり先頭に出す
- 末尾の英語の説明文（`Built from … The map shows …`）は一行にする
- コメントとコードの行数は、差分の追加行を TypeScript の字句で分けて数える（テストと生成物を除く）

想定リクエストがまだ無い段（段 0）では、「動きが変わるリクエスト」の節を出さず、ほかの節を先に入れる。

### PR の本文

人が読むのは、概要、実装したこと、影響の三つである。
`.github/pull_request_template.md` を足し、`skills/provider-map-implementation/SKILL.md` の「引き渡す」に同じ規則を書く。

- 本文は `<details>` の外で 40 行以内を目安にする。検査では落とさない

## 貢献者に課す規則

足す規則は二つだけにする。

- 機能を足す PR は、その機能の想定リクエストを一覧に足し、一件につき代表のテスト一つに `// @premise` を書く。足さなくても検査は落ちないが、その機能のリクエストは地図で選べず、PR のコメントの「どの想定リクエストも通らない変更」に数が出る。一覧に無い id と重複した id は lint で落とす
- 地図やテストの画面の表示を良くする目的で、コメントや説明の欄を足さない。`title` の長さと `// @premise` の行の形は lint で確かめ、コメントの増減は PR のコメントに出す

`skills/provider-map-implementation/SKILL.md` と `apps/map/docs/design-change-trail-and-decision-cases.md` の「貢献者に課す規則」に、この二つを足す。

## 決めたこと

- 想定リクエストは、YAML の一覧とテストの宣言で持つ
- 説明の文章は増やさない。書くのは名前の一行と閉じた語彙の期待だけにし、表示の言葉は観測とすでにある JSDoc から作る
- 宣言は想定リクエスト一件につき代表のテスト一つとし、ほかのテストは道筋の印で結ぶ
- コードを読むページを作る
- PR #207 は閉じる。記録は `packages/test-reach` を広げて作り、そのブランチのコードは使わない
- 記録の単位は、テストがエンドポイントの処理本体を一回走らせた分とする。HTTP で送るテストだけでなく、処理本体を直接呼ぶテストも代表にできる
- 識別子は `premise`、画面の言葉は「想定リクエスト」とする

一つ目から五つ目は、リポジトリの持ち主が決めた（2026-11-20、2026-11-21）。
残りは、その決定に合わせてこの文書が決めた。

## 範囲に入れないもの

- **仕様の要求の一覧**：「テストは必要なパターンを満たしているか」に答えるには、正解の一覧が要る。人が一から定義するのは難しく、生成 AI に文章で書かせると量が増えて確かめられない。後で足すなら、OIDF の Conformance Suite の module の id（`oidcc-ensure-request-without-nonce-fails` など。このリポジトリは Basic、Implicit、Hybrid、Dynamic、Config の五つのプランを実行できる）を取り込み、想定リクエストに `satisfies:` で結ぶ形にする。仕様の MUST を一文ずつ書き出した一覧は作らない。それまでは、6 節の「入力の網羅」と「テストなし」の行が、不足を見る手がかりである
- **E2E テストの道筋**：E2E の OP の計数はテストの単位で、リクエストごとに分けられない。E2E は宣言で並べるだけにする
- **ステップが受け渡す値の中身**：記録するのはリクエスト、応答、動いた行である。ステップの間で渡る値（`params`、`client`）の中身は記録しない
