# OIDC Provider Map

生成される OpenID Provider の地図。
`maronn-oidc generate` のフレームワークと機能を選ぶと、その構成のエンドポイントを一覧し、エンドポイントの処理を呼び出しの先まで一つの画面でたどれる。
PR の地図では、その PR が変えた関数がエンドポイントから何段下にあっても、何を変えたか（構造と式の差分）と差分のコードをその場で読める。

設計の考え方は [docs/design-change-trail-and-decision-cases.md](docs/design-change-trail-and-decision-cases.md) にある。

画面は `apps/tests` と同じ白基調・システムフォント・余白を使い、最初は処理の流れを中心に表示する。
上部には検索とフレームワークの選択、テストへのリンクを置き、PR の変更と追えない配線は左の一覧から開く。
左の一覧は ☰ で閉じられ、機能のオン・オフと生成コマンドは「機能」を開いて操作する。

## トレース：エンドポイントの処理を根にした木

エンドポイントの画面の中心はアウトラインで、エンドポイントの処理本体（hono の pipeline のハンドラー、Next.js の Route Handler）を、上から下へ一行ずつ読む。
一行は処理の流れの木のノード一つ（決定の側一つや、言葉の無い文の続き一つのこともある）で、まずその処理が何をするかを自然言語で書き、コードは言葉が無いところにだけ出す。

- ステップ：`// [step-id]` の印で囲んだブロックは、その見出し（「クライアントを認証する」）の一行に畳む。▸ で中を開く。中身がフレームのある関数の呼び出し一つだけのステップ（hono のステップ）は、その呼び出しの行になり、▸ でその関数の流れを開く
- 呼び出し：呼び先の関数の JSDoc の一行目（lint が求めるもの）、resolver や store のメソッドなら interface のメンバーの JSDoc
- 条件や処理：文の手前のコメント。条件が真偽を返す関数の呼び出し一つ（`if (!isPublicTokenClient(client))` のような否定を含む）なら、その関数の JSDoc を条件の形にした言葉（「パブリッククライアントか」）。どちらも無ければコード（`if (!keys)` など）で、コードから作った条件の言葉は行に重ねたときの表示に出す
- 言葉の無い文の続き：変数の定義や代入のように言葉の無い文が二つ以上続くところは「コード n 行」の一行にまとめ、何を用意するか（「`a`、`b` を用意する」）か、何に入れるか（「`x.y` に入れる」）を書く。ほかの文が混じれば「処理: …」と並べる。▸ でその文を一行ずつ開く。一つだけの文と、PR が変えた文はまとめない
- 終わり：`return` と `throw` には「終わり」「失敗」の札を付ける。`return` は、呼び出しをそのまま返すならその関数の JSDoc で、名前を返すなら「`x` を返す」「`a`、`b` を返す」と言う。コールバックの中の `return` はフレームを終えないので、札を付けない
- 守り（`if (!client) throw ...`）と任意項目の `if` は、`if (!client) → 失敗: TokenError(invalid_client) を投げる` のように一行で読む。ただし、その `if` か中を PR が変えたとき、成立側でフレームのある関数を呼ぶとき（その関数を開けるように）、成立側に決定があるときは、畳まずに全部の行を出す
- `try` は「ここから例外を捕まえる」の見出しの下に、捕まえる範囲の行を一段下げて並べ、最後に「例外が起きたとき → …」の行を置く

ざっと眺められるよう、どの行も一行に収める。
収まらない言葉は省略し、全文は行に重ねたときの表示と `</>` で読める。
`</>` はその行のコード、詳しい説明（コメントの全文、メソッドの説明と実装）、PR の変更の全部を開く。
上の「言葉 / コード」は、全部の行を言葉の一行かコードの一行に切り替える（コードにすると、言葉の無い文の続きも一文ずつに戻る）。
選んだ表示はこのブラウザに残る。
PR の変更は、札の横に一つ目の変更（「`<` を `<=` に変えた」）を同じ行で示し、「エラー時」の捕まる先（「失敗 → POST /token の catch」）も同じ行に出す。
条件や `throw` の直前に呼ぶ関数と、`return` がそのまま返す呼び出しは、その行が受け持ち、▸ でその関数を開ける。
ほかに先に評価する呼び出しは、その行の上に「先に」の行として出す。

呼び出しの ▸ を押すと、呼び先の関数の流れをその場で一段下げて開く。
何段でも開け、再帰はその関数の二度目で止める。
↗ はその関数を根にしたトレース（関数のページ）へ移る。
型で呼び先を引けない呼び出しは「追えない呼び出し」と示し、理由を添える。

行を押すと、その行を選び、図・詳細が指すフレームがその行のものに移る（閉じている欄は勝手に開かない）。
欄のタブは変えず、図ならその行の箱を囲んで見える所まで動かし、詳細ならその行の説明を足す。
別の関数の行なら、図の上のパンくず（`POST /token › authenticateTokenClient()`）が今どこを見ているかを示す。

### 決定を選んでたどる

決定の行には進む側のボタン（成立 / 不成立など）が並び、側の行（「成立」「例外が起きたとき」）を押しても選べる。
選ぶと、その側の行は活性のまま、ほかの側の行と、選んだ道筋では通らない後の行が灰色（不活性）になる。
行は消さないので、どこが選ばれていないかが見える。
もう一度押すと選択を外し、すべての行が活性に戻る。
子フレームの決定も同じ仕組みで選べ、エンドポイントから下の関数まで一本の道筋が決まる。
選んだ決定を中に持つステップは開く。

呼び出しには「ここで失敗する」という側もあり、よく使う選択の「失敗で終わる」がこの側を選ぶ（ハッシュでは `;d=s0b1s0:fails`）。
そう選んだ呼び出しの行には「ここで失敗」の札が付き、同じ並びの後の行は灰色になる。
失敗は、そのフレームでその呼び出しを囲む `catch` のある `try` のうち最も内側のものへ進み、その `catch` を通って `try` の後から続く。
そういう `try` が無ければ、フレームはそこで終わる。

機能のオン・オフはノードの機能の札で絞る。
オフの機能のブロックは木から外し、そのブロックが作る値を読む条件は値の無い側だけを残す。
機能が加えるエンドポイントは、左の一覧と見出しに `--enable par` のような札を付ける。
トレースでも機能のブロック・ステップに同じ札を付けるので、`/authorize` に追加される PAR の処理を通常の処理と見分けられる。
既定の機能には `refresh-token（既定）`、機能専用の関数には `par の実装` と示す。
共通の core 関数には、呼び出し元の機能の札を引き継がない。

### よく使う選択

「言葉 / コード」と同じ操作バーの「道筋を選ぶ」を開くと、木から計算した選択を並べる。
選ぶとその決定の組み合わせになり、複数選ぶと和集合になる。
「すべて表示」で選択を外す。選択中の数と「エラー時」のオンは、閉じたボタンにも表示する。
一覧の外を押すか Escape で閉じられ、選んだ道筋はそのまま残る。

- ステップ：エンドポイントの各ステップに至る決定。名前はステップの見出し（`/token` なら「refresh_token グラントを検証する」「authorization_code グラントを検証する」）
- 変更に至る道筋：PR の地図で、変えたところに至る決定。名前は変えた関数と通るステップ（「sign()（device_code を引き換える から）」）で、何を変えたかを添える。関数の中の二か所以上を変えたときは、変えたところごとに並ぶ（同じフレームを開いて同じ側を選ぶものは一つにまとめ、変えたところを並べて添える）。フレームをまたぎ、選ぶと間の呼び出しを開いて、変えた行を選ぶ。オフの機能を通る道筋は並べない
- 終わり方：`return` と本体の終わりごとに、そこへ至る決定。名前は区別に要るラベル（Next.js の `/token` なら `!keys: 成立`）だけで、守りを不成立で通った事実は書かない
- 失敗で終わる：`throw` と、呼び先から伝わる失敗。エラーごとにまとめ、呼び先からのものは「`verifyClientSecretHash` から」と投げる関数で示す。選ぶとその `throw` までのフレームを開き、途中の呼び出しをどれも「ここで失敗する」側にする

選択は木をたどって求めるので上限が無く、道筋の列挙や名前の無い「exit ケース」は無い。

### 失敗の流れとエラー時

関数がどう失敗するかは、JSDoc の `@throws` に頼らず木から求める。
`try` の外の `throw` と、`try` の外で呼ぶ関数の失敗を、カタログ全体で不動点まで集めたものが、その関数から外へ出る失敗である。
`catch` で受けた例外をそのまま投げ直す `try` は、捕まえなかったものとして数える。

「エラー時」をオンにすると、各呼び出しに「失敗すると → どこで捕まるか」を出す。
捕まる先は、トレースを上へたどって最初に見つかる `catch` である（`/token` なら根のフレームの `catch` と `respondTokenError`）。

### 図と詳細

操作バーの「図・詳細」でアウトラインの右の欄を開く。図、差分、詳細のタブを置く（関数のページでは、その前に呼び出し元）。
最初は欄を閉じておき、PC での開閉の選択はこのブラウザに残る。
欄は図のタブで始まり、開閉しても読者が選んだタブ、行、道筋をそのまま保つ。× または欄内の Escape で閉じる。
アウトラインの行や図の箱を選んでも、タブは変わらない。
どのタブも、図が見せているフレーム（パンくずの最後）について述べる。

- 図：そのフレーム一つ分の流れの形を一行の箱と矢印で描き、選んだ道筋を青にする
- 差分：そのフレームと、アウトラインがその下に開いているフレームのうち、この PR が変えたものの差分を実行順に並べる。interface のメンバーの呼び出しの先で変えた実装は、その呼び出しの位置に、メンバーの実装の行の範囲で並べる
- 詳細：何も選んでいなくても、そのフレームの説明（JSDoc、場所、仕様、失敗するとき、PR の変更、「コードを見る」、根でない関数なら「この関数を根にして開く」）を出す。行か箱を選ぶと、その下に選んだ行の説明（コード、行の範囲、呼び先の JSDoc、interface のメンバーの説明と実装、ステップなら受け取る値と次へ渡す値）を足す

図はアウトラインと同じ畳み方と言葉で、流れの形を描く。
ざっと眺められるよう、箱はどれも一行で、高さはそろえる。

- 箱の見出しはアウトラインの行と同じ言葉（ステップの見出し、呼び先の JSDoc、コメント）で、言葉が無いところはコード。収まらない分は省略する
- 終わり方は行を増やさず、見出しの末尾の札で示す（`→ 終わり`、赤の `→ 失敗`、いくつもあれば `×3`）
- 守りと任意項目の `if` は、アウトラインで一行になるものだけを一つの箱にし、すぐ終わる側は札にする。分かれ道の側、`switch` の case でも、すぐ終わるものは札にする
- 言葉の無い文が続くところ（変数の用意など）は一つの箱にし、何を用意するかを見出しにする
- `try` は箱にせず、捕まえる範囲を枠で囲み、枠の見出しに例外が起きたときを書く（`→ 例外: 失敗`、`→ 例外は無視して先へ`）。すぐ終わらない `catch` は、枠から出る赤い矢印の先に描く
- エンドポイントの本体は、ステップ一つを一つの箱にする。フレームのある関数の呼び出し一つだけのステップは、その呼び出しの箱になる
- ステップは、アウトラインで開いているものが図でも開く。PR が変えたノード、下に開いたフレーム、選んだ決定を中に持つステップは開いた状態で始まる。アウトラインの ▸ / ▾ でも、カードの「その場で開く / 畳む」でも、開け閉めすると両方が同時に変わる
- PR が変えたノードは、ほかの箱に畳まない
- 決定と終わりは、箱、札、枠、畳んだステップのどれかに必ず入る（`src/lib/diagram.data.test.ts` が全フレームで確かめる）

箱を押すと、その箱を選んでアウトラインの対応する行を示すだけで、ほかの関数へは移らない。
箱に重ねる（キーボードでは箱に移る、タッチでは触れる）と、カードにコード、言葉の全文、終わり方の全部が出る。
関数の中へ潜るのはカードの「中の流れを見る」で行う。
カードには、その箱が受け持つ呼び出しのうちアウトラインで開けるもの（箱の呼び出し、条件や `return` のために先に呼ぶ関数、箱に畳んだ側の呼び出し）ごとに、このボタンが並ぶ。
ステップをその場で開いたり畳んだりするのは、カードの「その場で開く / 畳む」で行う。
図の上のパンくず（`POST /token › authenticateTokenClient()`）が、根から今見ている関数までの道を示し、押すとその関数の図に戻る。
パンくずが四つ以上になると、根と、今の関数とその一つ上だけを残して間を「…」にまとめ、押すと間の関数を選べる（スマートフォンでは三つ以上で、根と今の関数だけを残す）。

箱の幅は 320px で、横に二つ並ぶ段があるときだけ 200px にする。
幅は配置だけで決め、欄の幅では変えないので、どの画面でも同じ配置になる。
選んだ道筋で変わるのは色だけで、箱は動かない。

図は、箱の見出しが 11px 以上になる倍率で開く。
幅に合わせた倍率がそれより小さくなるときは 0.88 倍で開き、選んだ箱（なければ始まりの箱）を中央に置く。
アウトラインの行を押すと、図はその箱を囲んで見える所まで同じ倍率で動く（ほかのタブを開いているときは、次に図を開いたときにその箱から見せる）。
別の関数の行なら、図もその関数へ移る。
アウトラインと図の欄の幅は、間の仕切りをドラッグして変えられる（左右の矢印キーでも変わり、ダブルクリックで元に戻る）。幅はこのブラウザに残る。

図の色は 3 つに限る。
灰色は選んだ道筋で通らない部分、青は通る部分と選んだ箱、赤は `throw`、`catch` の行とエラーの矢印である。
PR の札（後の節）はこの 3 色を使わない。

図は Dagre で接続関係に沿って自動配置する。
図の上部の一行で、向き（↓ 縦 / → 横）、拡大縮小、「幅」（幅に合わせる）、「全体」（全体を表示）、「戻す」（開いたときの倍率と位置に戻す）を操作する。
縮尺の数値を押すと 100% に戻る。
ドラッグで移動し、ピンチ（スマートフォンとトラックパッド）で拡大・縮小する。
2 本指スクロールとマウスホイールは移動に使い、図にフォーカスすると矢印キーで移動、`+` / `-` キーで拡大・縮小できる。
Tab で箱へ移ると、その箱が見える所まで図が動いてカードが出る。Enter か Space で選び、Tab でカードのボタンへ進み、Escape でカードを閉じる。
これらの操作には `react-zoom-pan-pinch` を使う。

開いたフレームと選んだ決定は URL のハッシュに書くので、たどった道筋をそのままリンクで渡せる（`#hono--token/s0b1s0/s0b1s0.s2;d=s0b1s0.s1:true;f=s0b1s0.s2`）。
ステップを名指すリンク（`#hono--token--select-signing-keys`）は、そのステップの行を選んで見せ、そのステップかエンドポイントを足す機能がオフならオンにする。

## フロー：リクエストをフローチャートの上で再生する

アウトラインの横の欄の図は幅が狭く、処理の全体を目で追いにくい。
操作バーの「▶ フローで見る」は、フレームを Mermaid のフローチャートの形で描き、ページの主役にした表示（フロー）へ切り替える。
左に再生の操作と説明、残りの幅いっぱいにフローチャートを置き、一つのリクエストが通る道筋を順に再生する。
「画面いっぱい」で、左の一覧とヘッダも隠してフローチャートを広げる（Escape で戻る）。
フローは URL のハッシュの `;p` で、選んだ道筋や開いたフレームと一緒に共有できる（`#hono--token;d=s0:try,s0b10s0:nullish;p`）。

### 想定リクエスト

各エンドポイントで目的を選ぶと、目的と期待する応答を表示し、そのケースのリクエストを地図の OP（後の「地図の OP」）で準備する。
たとえば `/authorize` では署名付き Request Object や PAR、`/token` では認可コードの交換や更新、`/device` では利用者コードの確認や承認を選べる。
準備は、ケースのリクエストに要るもの（認可コード、トークン、ログインのフォームの CSRF トークン、Cookie）を、読者のワークスペースの OP へ本物のリクエストを送って得る（[`packages/live-op/src/scenarios`](../../packages/live-op/src/scenarios)）。
`/token` の認可コードの交換なら、認可リクエスト、ログイン、同意を送り、クライアントへ戻るリダイレクトから認可コードを受け取る。
準備したリクエストは HTTP の形で表示し、コピーできる。
準備に送ったリクエストは、メソッド、パス、ステータス、OAuth のエラーとともに並べ、押すとそのエンドポイントのフローで開いて、通った道筋を再生する。
時計を進めたように、リクエストでない準備は一行ずつ添える。
「準備し直す」で、準備のリクエストからもう一度送る。

「地図の OP で試す」を開くと、準備したリクエストが実行欄に入る。
フローは、そのリクエストを送る前の試算で、通る道筋をすぐに再生する（後の「リクエスト」）。
実行すると、応答の横にケースが期待する応答を並べ、ステータス、OAuth のエラー、リダイレクト先のパスのどれかが違えば「✗ 期待と違う」と、どこが違うかを出す。
OP は状態を保つので、同じ認可コードの交換を二度実行すると、二度目は使用済みで `invalid_grant` になる。
地図内の実行には Hono の OP を使う。Next.js では目的と期待する応答だけを表示する。Google から実際の認証情報を受け取るケースでは、その前提を表示する。

ケースは `#hono--authorize;r=authorize-request-object` のように共有でき、tests でも同じ目的を選べる。
ケースを増やすときは、[目的と期待する応答](../../packages/test-catalog/src/scenarios) と [リクエストの準備手順](../../packages/live-op/src/scenarios) を同じ ID で追加する。
地図のビルドは全ケースを地図の OP で動かし、どのケースの道筋も、そのリクエストが動かしたものだけを通ることを確かめる。

### 道筋と仮の側

再生する道筋は「コードの道筋」で選ぶ。
並ぶのは「道筋を選ぶ」と同じ、木から計算した選択（ステップへ進む道筋、終わり方、失敗で終わる）で、オンの機能で通れるものだけである。
選ぶと、その選択の決定とフレームだけに置き換えて、最初から再生する。
アウトラインで選んだ決定があれば、その一つ目の選択をそのまま再生する（「自分で選んだ道筋」）。
「リクエスト」で書いたリクエストを実行するか、「最近のリクエスト」から開くと、それが通った道筋を再生する（「実行したリクエストが通った道筋」。後の「リクエスト」）。
送る前のリクエストは、その試算が通る道筋を再生する（「このリクエストを送ると通る道筋（試算）」）。

道筋を選ぶと、地図のビルドがその道筋を通ると確かめたケースを、「このケースで、この道筋を通るリクエストを作る: …」のボタンで並べる（`RootRequests` の `ways[].scenarios`）。
押すと、そのケースのリクエストを地図の OP で準備して実行欄に入れ、道筋はそのまま残す。
どのケースも通らない道筋では、パラメータの空欄から書き始める。

道筋が決めていない決定は、仮の側へ進む。
仮の側は、すぐには終わらない最初の側である（守りは通り抜け、`try` は例外なし、繰り返しは本体を一度）。繰り返しの中の `continue` と `break` はその繰り返しを抜け、本体の残りを通らずに、繰り返しの後へ進む（`continue` する守りも、仮には通り抜ける）。
仮に進んだ決定には「仮」の札を付け、その場面にほかの側のボタンを並べる。
側を押すと、その決定が道筋に加わる（アウトラインの側のボタンと同じ選択になる）。

### フローチャート

フローチャート（`src/lib/flowchart.ts`）は、横の欄の図と同じ畳み方（`src/lib/diagram.ts`）から作る。
どの箱が何を受け持つかは二つで変わらず、描き方だけが違う。
欄の図は一行の箱で流れの形を見せ、フローチャートは、各箱がこの流れで何をするかと、どこで終わるかまで描く。

- 始まり：長円（両端の丸い形）に、フレームの名前を書く。エンドポイントの根なら `POST /token`、関数なら宣言（`parseTokenRequest(c)`）と JSDoc の一文目
- 処理：角の丸い四角に二行で書く。一行目は箱の言葉（欄の図と同じ）、二行目はこの流れで何をするか。エンドポイントのステップなら種類と、受け取る値と次へ渡す値（`検証 · params, authorization → tokenClient`）、それ以外は箱のコード。収まらない分は省略し、全文はカードに出す
- 分かれ道：守り、`if` の分岐、`switch`、分岐する式、繰り返しのうち、図が一つの箱にするものはひし形にし、条件を二行までで書く（`if (!client)` は `!client`）
- 終わり：欄の図で箱の末尾の札だったもの（`→ 終わり`、`→ 失敗`、すぐ応答するステップ）は、それぞれ独立した終端にする。終わるものは長円に「応答して終わる」（関数のフレームでは「返して終わる」）と返すものを、失敗するものは赤い角丸に「失敗: TokenError(invalid_client)」を書く。`return` や `throw` そのものの箱も、この形で描く
- 終端は、出ていく箱の横（縦向きなら右、横向きなら下。空いていなければ反対側）に箱と同じ高さで置く。両側とも埋まっていれば次の項のように積み、それでも置けなければさらに外側に置く。本流は一列のまま、どこから出ていくかを横で読める
- 両側とも埋まっているとき（`switch` の四つの `case` が四つとも終わるなど）は、終端を箱の横に流れに沿って積み、矢印は箱から少し出て折れ、終端の高さで入る。ラベルはその最後の区間に置く。終端は、ほかの箱、ラベル、矢印の上に置かない
- `try`：捕まえる範囲を薄く塗った枠（サブグラフ）で囲み、上に見出しを置く。範囲の中の箱の終端も枠の中に置く。`catch` は、枠から出る赤い破線の矢印「例外」の先にある（すぐ終わるなら終端、そうでなければ `catch` の箱）

矢印はすべて描き、ラベルは背景のある小さな箱に入れる。
どの矢印も両端の箱のほかは横切らず、ラベルは箱にもほかのラベルにも重ならない。
ひし形から出る矢印は、配置（Dagre）がその矢印を出した側の角から出るので、最初の区間が隣の終端を横切らない。

- 分かれ道の矢印には進む側（`成立`、`不成立`、`値あり`、`case 'x'`）を、終端への矢印には出方（`成立`、`応答した`、`失敗`、`例外`）を書く。終端を持つ箱から先へ進む矢印には、残る側（`不成立`、`応答なし`）を書く
- エンドポイントのステップの間の矢印には、前のステップが次へ渡す値を書く。前のステップが作る値のうち、次かその先のステップが受け取るもので、無ければ作る値すべてである。何も作らないステップの後ろには書かない
- 色は図と同じ三つに限る（後の節「図と詳細」）。Mermaid らしさは、形、ラベルつきの矢印、動く矢印で出す

`src/lib/playback.data.test.ts` が、地図のよく使う選択をすべて再生し、どの場面にもフローチャートの箱があること、どの終わり方にも終端があること、終わる場面がどれも終端に着くことを確かめる。
どのフローチャートも、縦と横の両方の向きで、箱が重ならないこと、終端が箱の横に並ぶこと、矢印が両端の箱のほかを横切らないこと、ラベルが箱にもほかのラベルにも重ならないことを確かめる。

### 再生

再生は場面の列で、場面一つはフローチャートの箱一つに当たる。
アウトラインが一行に畳むもの（ステップ、守り、言葉の無い文の続き）は、フローチャートでも一つの箱なので、一つの場面になる。

- 「▶ 再生」で、場面を順に進める。丸い印が矢印の上を次の箱まで動き、着くと箱が濃くなって、ゆっくり脈打つ。フローチャートは今の箱が見える所まで動く
- 1× では場面一つに 2.6 秒とどまる（`sceneDuration`）。印は矢印 1 ピクセルに約 4 ミリ秒かけて進み（最短 0.32 秒、場面の時間の取り分まで）、箱に着いてから終端へ向かうまで 0.4 秒止まる。流れる矢印の破線は 1.2 秒で一巡りする。どれも、場面の札を読みながら印を目で追える速さにしてある
- 通った矢印は、Mermaid の動く矢印のように、破線が流れの向きに流れる。今通っている矢印は太くなる。この先で通る矢印は破線のまま止まっている
- 通った箱は薄く塗ったまま残る。この先で通る箱は青い枠になり、通らない箱は灰色のまま
- 場面がフレームを終えるとき（応答する、失敗する、`catch` が失敗を受け取って応答する）、印は箱に着いたあと、ラベルのある矢印を進んで終端まで行き、終端が光る（終わりは青、失敗は赤）。フローチャートは箱と終端が両方見える所まで動く
- ◀ ▶（← → キー）で一つずつ進め、つまみで好きな場面へ移る。フローチャートの箱や終端を押しても、その場面へ移る。速さは 0.5×、1×、2× から選ぶ（`SPEEDS`）
- 動きを減らす設定（`prefers-reduced-motion`）のときは、破線は流れず、印は動かず、箱と終端はすぐに変わる

場面の説明には、アウトラインと同じ言葉を出す。

- 見出し：箱の言葉。エンドポイントのステップなら、種類（読み取り、検証、振り分け、発行、保存、応答など）と、受け取る値、次へ渡す値
- 行：その箱が受け持つ処理。呼び出しはコード、決定は条件と進んだ側、終わりは「終わり」、失敗は「失敗」と投げるエラー、`catch` が受け取るときは「捕まえる」
- フレームのある関数の呼び出しには「中に入る ▸」があり、その関数が中で呼ぶ関数の名前と説明も開いて読める

### リクエスト

左の「リクエスト」は、リクエストを書いて地図の OP（後の「地図の OP」）へ送る欄である。
送ると、OP がそのリクエストで動かした順の記録から通った道筋を求め、再生は最初からその道筋をたどる。
値を書き換えて実行し直せば、値によって変わる道筋を見比べられる。

フローは、送る前からこの欄のリクエストに合わせて動く。
ケースが準備したリクエストと、書き換えたリクエストは、送る前に試算する（`POST /__live/preview`）。
試算では、地図の OP がワークスペースのいまの状態（DB、機能のストア、時計）のコピーでリクエストを動かし、コピーごと捨てる。
保存した記録も「最近のリクエスト」も変わらないので、試算した認可コードは、送るときにもまだ使える。
再生は、試算が動かした順を、送ったリクエストと同じようにたどる（ハンドラーを振り分ける根は動いたハンドラーとその呼び出しを開き、失敗した呼び出しは `throw` まで下る）。
フローチャートの道筋、場面、終わり方が、書き換えたリクエストのものに替わる。

- 試算は、書き換えてから 0.4 秒書かなかったときに一度だけ行う（`PREVIEW_DELAY`）。結果が来るまでは前の道筋を出したまま「試算中…」と添える。新しい試算を頼むと、前の試算の要求は取り消し（`LiveOpClient.preview` の `signal`）、後から来た古い結果も捨てる。フローの画面を離れたときも、試算中の要求を取り消す
- 試算の結果は「送る前の試算（地図の OP の今の状態のコピーで動かしました。OP の状態は変えていません）」として、ステータス、OAuth のエラー、`Location`、終わり方を出す。ヘッダー、ボディ、読み書きした記録は畳んでおく
- 試算で道筋が替わっても、再生は自分では始めず（再生中なら止まり）、いまの場面が残っていればそこに、無ければ近い場面にとどまる。実行したときは、これまでどおり最初から再生する
- 「想定リクエスト」の選択は、書き換えても変わらない
- 空欄のままのリクエスト、「最近のリクエスト」から開いたままのリクエスト、実行したままのリクエストは試算しない（フローはその記録をたどっている）。書き換えた後で、開いたリクエストや実行したリクエストに戻すと（「元のリクエストに戻す」）、その記録の道筋に戻り、ケースが準備したリクエストに戻すと（送っていなければ）試算し直す
- 空欄から書いたリクエストを空欄に戻すと（「元のリクエストに戻す」か、名前のある行をすべて消す）、試算をやめ、書き始める前の道筋（選んでいた道筋、自分で選んだ側、おまかせ。その前に実行したか開いたリクエストがあれば、その記録の道筋）に戻る。空欄は送るリクエストを持たないので、空欄そのものは試算しない
- 書き換えて送れない形になったリクエスト（GET のボディ、名前に使えない文字のヘッダー）は試算しない。出したままの結果には「この結果は書き換える前のリクエストのものです」と添え、フローはその道筋のままにする
- 「このリクエストを実行」で送っている間は試算しない。送っている間に書き換えたリクエストは、送った結果を出してから、送ったリクエストと違えば試算する
- Next.js の地図と、地図の OP に接続できないときは試算しない。試算が地図の OP に届かなかったときは、そのことを一つの警告で出し（ケースが準備したままのリクエストでも「このリクエストを試算できませんでした」）、次の書き換えでまた試算する。警告は、試算、実行、開いたリクエストのどれかが OP に届くと消える
- 試算の道筋は、URL のハッシュに残さない（`;d=` にも `;x=` にも書かない）。再読み込みでは試算をし直せず、残すと「自分で選んだ道筋」に見えるからである。試算の道筋から自分で側を選ぶと、その選択はこれまでどおりハッシュに残る

- メソッドとパスはエンドポイントのもので、クエリ、ボディ（フォームの欄、JSON の最上位のメンバー）、ヘッダーを、名前と値の行で書く。行は足したり消したりでき、JSON のメンバーの値は、文字列でない JSON として読めるものはその値で送る（`3600`、`true`、`["https://rp.example.com/cb"]`）。Basic の Authorization には、そのクライアント ID を添える
- 書き始めるのは、選んだケースのために準備したリクエスト、「最近のリクエスト」から開いたリクエスト、どちらも無ければパラメータの空欄である。「元のリクエストに戻す」で編集を戻す
- ブラウザが開くエンドポイント（認可、ログイン、同意、デバイス、CIBA、ログアウト）の GET には「ブラウザで開く ↗」があり、同じリクエストを新しいタブで地図の OP に送る。そのタブが送るログインや同意も読者のワークスペースに届き、「最近のリクエスト」に出る
- この欄はテストとは結び付けない。テストが送ったリクエストは、テストの画面で読む
- 実行すると、応答のステータスと OAuth のエラー（JSON のボディか、リダイレクト先の `error`）、応答のヘッダーすべて（Set-Cookie は一つずつ、`Location` も）、応答のボディを出す。時刻は OP の時計である
- 「道筋」は「実行したリクエストが通った道筋」になり、それが「道筋」の選択のどれで終わったか（「失敗: TokenError(invalid_grant)（validateAuthorizationCodeNotUsed から）」、「終わり方: …」、自分で応答するステップならそのステップ）を添えて、再生を最初から始める。失敗は、投げた `throw` の選択をそのまま名指す
- エンドポイントの処理が動いていないリクエスト（ルーティングやミドルウェアが答えた 404 や 405）は、「このリクエストではエンドポイントの処理は動いていません」と出し、仮の側の道筋は再生しない
- 再生する道筋が、そのリクエストが動かしていない所を通ったら（地図の読み方の不具合で、起きないはず）、その数を警告する
- 場面の側のボタンやほかの道筋を選ぶと、再生は実行したリクエスト（または試算）の道筋から離れる。「このリクエストの道筋に戻す」か、次の書き換え（その試算が来たとき）でまた従う。書いてすぐ消した書き換えのように、リクエストが変わらなければ試算はせず、離れたままにする。ほかの道筋やケースを選ぶと、実行の結果は消える
- 応答の下の「このリクエストが読んだ、OP の保存済みの情報」に、そのリクエストが読んだ記録（クライアント、認可コード、リフレッシュトークンなど）を読んだ順に並べる。見つからなかった記録は「OP に無い」、コレクションを全部調べたもの（使用済みのコードを出したときに、そのグラントのトークンを探すなど）は「（すべて）を調べた」、同意のように記録の中を引いたものは「testuser の client-2」と出す。ワークスペースがいまも持っている記録は、開くと中身（いまの値。時刻は OP の時計からの秒数を添える）を出し、それを保存したリクエストと変えたリクエスト（`x4` など。一つのリクエストが二度変えても一度だけ）を押すと、そのエンドポイントのフローで開く
- 続く「このリクエストが保存・変更・削除したもの」に、記録ごとに、リクエストが残した中身を出す（引き換えたコードの `used`、発行したトークン、使用済みのコードを出したときに取り消したトークンなど）

道筋を通るケースは、地図のビルドが見つける。
ビルドは、OP の外のものを要らない全ケースを、ケースごとに新しいワークスペースで地図の OP に準備して送り、その記録をエンドポイントの根にたどって、ケースが通った道筋をエンドポイントの処理本体ごとに `public/data/requests/<hash>.json`（`RootRequests`）へ書き、`map.json` の `requests` に URL を置く。
道筋とは、種類、行き先（`Selection.target`）、名前で結ぶ。

#### 最近のリクエスト

「最近のリクエスト」は、読者のワークスペースが答えたリクエストを、新しい順に並べる。
地図から送ったもの、ケースの準備やグラントが送ったもの、ブラウザのタブやクライアント（curl など）が OP のパスへ送ったものを、どこから来たか、メソッドとパス、ステータスと OAuth のエラー、OP の時計の時刻とともに出す。
「このエンドポイント」はパスがこのエンドポイントのもの（`/device/login` のような下のパスも）、「すべて」は全部で、フローを見ている間は 5 秒ごとに読み直す。
押すと、送り直さずに、そのリクエストを実行欄に入れて、通った道筋を再生する。
ほかのエンドポイントのものは、そのエンドポイントのフローを `;x=<id>` 付きで開く（`#hono--token;p;x=x12`）。
ハッシュの `;x=` は、再読み込みしても同じリクエストを開く。
OP は応答のヘッダー `x-map-exchange` にその交換の id を付けるので、curl で送ったリクエストも id で探せる。

#### 地図の OP の状態

「地図の OP の状態」は、読者のワークスペースが何であり、何を持っているかを出す。

- OP の時計と、進めた秒数。「+60 秒」「+10 分」「+1 時間」で時計を進め、期限切れのコードやトークンを確かめられる
- 「ワークスペースを作り直す」は、確かめてから、保存した記録、最近のリクエスト、進めた時計を消して始め直す
- OP の設定で登録したクライアント（認証方式、シークレット、`grant_types`、`redirect_uri`、地図での用途）と、ユーザーとパスワード
- 保存した記録をコレクションごとに。記録ごとに、保存したリクエストと変えたリクエストを押して、そのフローで開ける
- 「グラントを作る」：認可リクエストのクエリ、ログインするユーザー、コードを引き換えるかを書くと、地図の OP がブラウザとクライアントのように認可リクエスト、ログイン、同意（と引き換え）を送り、受け取ったコードとトークン、送ったリクエストを出す。PKCE（S256）の `code_verifier` と `code_challenge` は、このページが WebCrypto で作る

### 地図の OP

リクエストは、地図と一緒にデプロイした OP（地図の OP、[`packages/live-op`](../../packages/live-op)）で動かす。
設計は [docs/design-live-op.md](docs/design-live-op.md) にある。
OP は `apps/hono` のサーバーアプリ（`createServerApp`、全機能オン）そのもので、ページと同じオリジンで OP のパス（`/authorize`、`/login`、`/token` など）に答える。
Cloudflare Workers では地図の Worker が Durable Object で動かし、ローカルでは Vite の開発サーバーとプレビューが Node で動かす。
読者ごとにワークスペースを一つ持ち（id はブラウザの `localStorage` と Cookie `map_workspace`）、状態（メモリの DB、機能のストア、署名鍵、進めた時計）をリクエストの間で保つ。
使った認可コードは使ったまま、ログインしたセッションはログインしたままで、時計は本物の時計である。
ページは制御の API（`/__live/*`。`@maronn-openid-connect/live-op/client`）で、リクエストを送り、ケースを準備し、グラントを作り、交換の一覧と一つの交換、状態を読み、時計を進め、ワークスペースを作り直す。

道筋は、OP が動かした順の記録から求める。
OP は Istanbul の計数が上がるたびにその場所（プローブ）を順に記録し、リクエストごとの交換（exchange）に残す。
ページはプローブの表（`/__live/probes`。OP のビルドごとに一つ）を一度読み、記録を地図のフレームの呼び出しに分けて（`@maronn-openid-connect/map-analysis/traced` の `RequestTrace`）、呼び出しごとの計数を、テストカタログと同じ規則（`observe.ts`）で読む。
同じ関数を二度呼んでも、呼び出しごとに読むので混ざらない。
`followTrace` は、開いたフレームの決定を読み、ハンドラーを振り分ける根（`GET | POST /login`、`/device`、`/ciba`、`/logout` など）ではリクエストが動かしたハンドラーとその呼び出しを開き、失敗した呼び出しのフレームを開いて、投げた `throw` まで下る（`src/components/useRun.ts`）。
読者が開いたフレームも読み、読者が閉じたフレームは開き直さない。
規則で読めない形（三つ以上の項の `&&`、ローカルのコールバックの中の分岐）だけが仮の側へ進み、その数を添える。

- 動かせるのは hono の OP で、Express と Fastify の地図も同じエンドポイントの処理なので hono の OP で動かす。Next.js の OP は動かせない
- 地図の OP は全機能オンで動く。オフの機能があるときはその旨を出す（オフの機能のステップを通るリクエストは、生成した OP とは道筋が変わる）
- ページが地図の OP に接続できない（OP の無いところから配信した）ときは、リクエストの欄に「地図の OP に接続できません。…」と出す
- 地図の OP は遊び場としての制限を持つ。ボディは 64 KiB、URL は 16 KiB までで、超えると 413 を返す。ワークスペースの状態が 8 MiB を超えたとき、保存していた状態を読めないとき、OP のコードか設定が変わったときは、ワークスペースを作り直して理由を状態の `notice` に残す（[docs/design-live-op.md](docs/design-live-op.md) の「制限」）
- 地図のデータを作った OP と、いま動いている OP のプローブの表が違う（`map.json` の `liveOp.probes`）ときは、道筋がずれうるので、地図のデータを作り直すように警告する

### 呼び出しの中へ

再生が通るのは、トレースが開いているフレームだけである。
「中に入る ▸」はその呼び出しのフレームを開き、「一段深く」は道筋の上の、フレームのある呼び出しをすべて一段開く。
「一段浅く」は、いちばん深い段を閉じる。
開いたフレームに入ると、フローチャートはそのフレームのものに替わり、印は始まりから最初の箱へ進む。パンくずが今いる関数までの道を示す。
パンくずを押すと、そのフレームにいた最後の場面へ戻る。

「失敗で終わる」の道筋は、投げる関数までのフレームを開くので、再生は `throw` まで潜り、失敗を上へ運んで、捕まえる `catch` の先まで進む。
呼び出しが失敗するかどうかは、開いたフレームの中で実際に投げるかで決める（道筋が「ここで失敗する」と言う呼び出しは、中で投げなくてもそこで失敗する）。

### フローチャートの大きさと操作

フローチャートは、欄より狭い配置を 140% まで拡大して開く（`STAGE_SCALE`）。
それ以外の操作（向き、拡大縮小、移動、カード）は、横の欄の図と同じである（カードは `src/components/useDiagramCards.tsx` を共有する）。
このリクエストが通らない箱や終端、枠の見出しも、触れるとカードが出たままになり、Tab でカードのボタンへ進める。押しても場面は移らない。

## 関数のページ

関数を選ぶと、その関数を根にしたトレースを開く。
読み方はエンドポイントの画面と同じで、呼び出しの先をその場で開ける。
右の欄の「呼び出し元」タブには、使われるエンドポイント（その関数が処理の本体であるもの、その関数を置くファイルが実装するもの）、その関数に届くエンドポイントのステップ（間に挟まる関数を順に）、その関数を直接呼ぶ関数を並べる。
ほかのタブと同じく図が見せている関数について述べるので、呼び出しの中へ潜ると、潜った先の関数の呼び出し元になる。
呼び出し元へ移るときは、たどった経路を捨てて、その関数かエンドポイントのトレースを新しく開く。

## PR の地図：このPRの変更

PR の地図は、その PR が変えた関数とエンドポイントの処理本体に札を付ける。
札は灰色の濃淡で示す。

- `追加` `変更`：その関数を足した、またはコードを変えた。アウトラインでは、足した行と変えた行と、変えた関数を呼ぶ行にも付く
- `下で変更`：その呼び出しの先（さらに下を含む）のコードを変えた。interface のメンバーの呼び出しなら、表示しているフレームワークで動く実装か、その実装が呼ぶ先を変えた
- `説明` `移動` `メモ` `削除`：JSDoc だけ変えた、コードはそのままで別のファイルへ移した、コードは変えていないが変更メモが説明している、消した

下で変えたものがある呼び出しの行には、下で変えた関数の数と変更の集計（「下で変更 2（条件 +1、呼び出し 変更 1）」）を添える。
メンバーの呼び出しでは、変えた実装のうち、そのメンバーの実装の行の範囲にある変更だけを数える。
アウトラインの行と図の箱は、同じ規則で札を付ける（受け持つノードの札と、呼ぶ関数とメンバーの札のうち強い方）。

「変更まで展開」は、根から届くすべての変更まで、間の呼び出しを一度に開く。
深さと件数の上限は無い。
interface のメンバーの実装を変えたときは、そのメンバーを呼ぶ行まで開き、その行の「差分」で実装の差分を読む。

アウトラインでは、変えた行の札の横に一つ目の式の差分（「`<` を `<=` に変えた」「引数 `issuedAt` を足した」）を同じ行で示し、残りは「ほか n」として `</>` に並べる。
行の「差分」は、その行が受け持つノード（畳んだステップや一行の守りなら、その中のすべて）の hunk を、その行の下に開く。
フレームの宣言と JSDoc の変更は、そのフレームを開いた呼び出しの行に付き、根のフレームなら先頭の「宣言」の行に付く。
interface のメンバーの呼び出しの行の「差分」は、変えた実装の差分を、そのメンバーの実装の行の範囲で開く。
消したノードは、消した位置に打ち消し線で残す。

「このPRの変更」のページ（`#<framework>--changes`）は、先頭に説明の無い変更を並べる。
続けて、変更メモ（PR 全体の説明と、関数に当たらない節）、変えた関数の一覧（足したもの、コードを変えたもの、…の種類ごと）、関数の外の変更を置く。
右には、変更が届くエンドポイントと、そこへの経路の数を並べる。
変えた関数ごとに次を置く。

- 自動要約：木の差分から作った言葉（「条件 `expiresAt <= now`: `<` を `<=` に変えた」「条件 `secret.length < 8` を足した（失敗で抜ける）」）と件数。新しく外へ出る失敗とそれを捕まえる場所（「catch で捕まえて `respondTokenError(…)` が応答する」）、外へ出なくなった失敗、実装を変えた interface のメンバー、この変更を呼ぶかもしれない追えない呼び出し（後の「影響範囲」）も添える
- メモ：変更メモの、その関数の節
- 差分：その関数の hunk を行の順に並べたもの。どのノードの変更かは、トレースの行で読む
- 届く経路：その変更に届くエンドポイント、ステップ、間の関数（メンバーを通るなら、そのメンバーと変えた実装）、決定の数、要る機能、新しい失敗が捕まる場所。関数の中の二か所以上を変えたときは、変えたところごとにまとめる。押すと、トレースが変更まで展開され、決定が選ばれ、要る機能がオンになり、変えた行を選んだ状態で開く

### 木の差分

変更前の木も同じ解析で作り、変更後の木と枝ごとに、ノードの種類と正規化した要約で順序を保って対応づける。
対応づいたノードのコードが違えば `変更`、対応の無い変更後のノードは `追加`、対応の無い変更前のノードは消したノードである。
コメントと書き方（空白、末尾のカンマやセミコロン）だけの違いは、ノードの変更にしない。
コードがそれだけ違う関数は「コメントや書き方だけを変えた（木は同じ）」として一覧に載せ、CI の検査には入れない。
変えたノードは式の中まで比べ、演算子、リテラル、引数、呼び先の置き換えを言葉にする。
足した部分と消した部分は、ソースのその部分をそのまま引く（「`.trim()` を足した」）。
interface のメンバーの実装を持つノードの要約は、そのメンバーの名前から始める（「`AuthorizationCodeStorage.consume` の実装: …」）。
対応づかない書き換えは前後のコードを並べる。
差分の hunk は、変えた行の続きごとに、それを含む最小のノードに付け、前後の文脈の行はそのノードの行に収める。
どのノードにも属さない行（JSDoc と宣言）の変更は、フレームの始まりの変更として扱う。
呼び出し元には、下の変更の集計を上げる。

### 影響範囲

変更がどこに効くかは地図が計算する。

- 呼び先は TypeScript の型で解決する。interface のメンバーを通る呼び出しも追い、store や resolver の実装を変えると、そのメンバーの全呼び出し箇所に届く。実装の中から別のメンバーや関数を呼ぶなら、その先も同じように上へたどる（store の実装 → それを呼ぶ resolver の実装 → resolver のメンバーを呼ぶ core の関数 → エンドポイント）
- `apps/hono` の実装は Hono・Express・Fastify のエンドポイントにだけ、`apps/nextjs` の実装は Next.js のエンドポイントにだけ届く。`packages/` の関数はどちらにも届く
- エンドポイントごとに、変更までの経路（開くフレームと決定の組み合わせ）と、その経路に要る機能を求める。関数の中の二か所以上を変えたときは、変えたところごとに経路を求める
- 外へ出る失敗が増えたり減ったりした関数は、その変化を示す。新しい失敗には、経路ごとにどの `catch` が捕まえるか（どこでも捕まえずにエンドポイントの外へ出るか）を添える
- hono（Express と Fastify はその写し）と Next.js の写しは別々に数える
- 型で呼び先を引けない呼び出しは「追えない」と明示する。そのうち、変更へ上がる道筋にあるメンバーと同じ名前のメソッドを呼ぶものは、変更を呼ぶかもしれない呼び出しとして挙げる。届く経路と CI の検査には入れない

### 変更メモと CI

何を変えたかは木の差分が、どこに効くかは地図が示し、変更メモ（[changes/](changes/README.md)）には意図と背景を書く。
地図のビルドは、変更メモの見出しが名前を挙げる関数が実在するかを確かめ、コードを変えた関数で節の無いものを「説明の無い変更」とし、そのうち CI の検査の対象（次の文）を PR コメントの先頭に一覧する。
CI（`.github/workflows/ci.yml` の `map` ジョブの地図のビルド）を落とすのは、エンドポイントに届く関数か、エンドポイントの処理本体に説明の節が無いときと、それらの関連するテストをこの PR が足しも変えもせず、節に `テストを変えない理由:` の行も無いときである。
関連するテストの変わらない変更は、PR のコメントの説明の無い変更の次と検査の出力に出る（地図の画面には出さない）。
コメントや書き方だけの変更と、追えない呼び出しのほかからは届かない変更では落とさない。
本文の質は検査せず、自動要約を隣に並べる。
PR のコメントは、説明の無い変更（と足す節の雛形）、関連するテストに変更の無い実装の変更、変更メモの要旨、確かめること（その二つの数と、足したコメントとコードの行数。コードが 400 行を超えると、PR を分けるよう促す）、リンク（地図の「このPRの変更」 `#changes`、テストの画面の「この PR のテスト」 `/tests/#/pr`、Codecov）、変わった関数、テストの差分、ビルドしたコミットと Run の一行の順に並べる。
変わった関数（札、関数、場所、自動要約、届くエンドポイント、メモの一行目の表と、新しい失敗が捕まる場所と追えない呼び出し）とテストの差分は、それぞれ `<details>` に畳む。

節の雛形は次のコマンドで作れる。
MAP_BASE からの差分で、まだ節の無い関数ごとに見出し（`## 名前 <!-- id -->`）と、自動要約と届く先の HTML コメントを書き、意図の欄を空けておく。

```bash
MAP_BASE=origin/main pnpm --filter @maronn-openid-connect/map changes:draft
```

## 変更の履歴

左の一覧の「変更の履歴」（`#<framework>--history`）は、main に入った変更を新しい順に並べる。
PR のマージとスカッシュ、PR を通さずに push したコミットとマージで、PR を通さないものは赤い「PR なし」の札で示す。
別のブランチにマージされた PR（main を pull したマージを push したときなど）は、それを main に入れた変更の中に「この変更で main に入った PR」として並べ、番号でも開ける。
浅い clone の最も古いコミットは、何を変えたかが分からないので、ファイルと関数を並べない。
タイトル・関数・ブランチ・番号（`#207`）で絞り込め、関数を変えたものだけ、PR を通さないものだけにも絞れる。

変更を押すと、その変更のページ（`#<framework>--history--pr-207`、PR の無いものはコミットの先頭）を開く。
生成 AI が作った PR でも、何をしたかを後から追えるよう、次を並べる。

- PR の本文（ビルドに `MAP_PULLS` を渡したとき）と、その PR が足した変更メモ（GitHub のそのコミットのファイルへのリンク）
- 足した・変えた・消した関数。関数カタログと同じ読み方（行頭の `function` 宣言、JSDoc から本体の終わりまで）で、変更前後のテキストと差分の行から求める。今もある関数は、関数のページとコードを読むページへ開ける。▸ でその関数の差分を開く。差分は OSS が出すコード（関数カタログの根のファイル）だけで、テスト、文書、道具の変更は入らないので、GitHub の PR の差分より速く、見たい関数だけを読める
- 関数の外の変更（import、型、定数など）を、ファイルごとに同じように開ける。差分を地図に載せなかったファイルは、その理由（ファイルの差分が長い、変更全体の差分が多い）と並べる
- 今の地図で、その関数が届くエンドポイント（選んでいるフレームワークの）
- コミット（ブランチのコミットを古い順に）と、変えたファイル

関数のページの右の欄の「変えた PR」タブは、その関数を変えた変更を新しい順に並べ、押すとその変更のページを開く。
データは `history/<hash>.json`（後の「データとビルド」）で、ページを開いたときに一度だけ読む。

### AI が読む変更の履歴

同じデータを、AI（Claude Code、のちに地図に載せる AI）が直接読めるよう、コマンドで Markdown にする。
差分だけを渡すと AI は渡された差分しか見ないので、変えた関数ごとに、差分と並べて**今のコードの場所**（ファイルと行）と今それを呼ぶものを書き、AI がそのコードを開いて、差分を手がかりに判断する形にする。

```sh
pnpm map:history                                  # 最近の変更を、開くキー（pr-219 など）と変えた関数の数で並べる
pnpm map:history pr-219                           # 変更の意図、関数ごとの差分と今の場所、関数の外の変更
pnpm map:history pr-219 --summary                 # 大きな変更の見取り図：本文の要旨、今のファイルごとの関数と行、差分の行数
pnpm map:history pr-219 --function verify         # その変更の一つの関数
pnpm map:history --function verifyClientSecret    # 関数を変えた変更を新しい順に、変更メモのその関数の節と、その関数の差分で
```

- 変更は `pr-219`、`219`、`'#219'`（シェルでは `#` から後がコメントになるので囲む）、変更のコミット、マージしたブランチのコミット（`git log` や `git blame` が出すもの。データに無いブランチの中のマージは、git でそれを含む変更を探す）で指す。履歴には同じ PR 番号を持つ変更があるので、新しい方を `pr-<番号>` で、ほかをコミットの先頭で出し（出したキーは必ずその変更を開く）、番号で開いた変更には同じ番号のほかの変更を並べる
- 関数は名前、`root:name`、`module#name`、id で指す（変更メモの見出しと同じ読み方）。同じ名前が複数あれば id の一覧を出す。エンドポイントの処理は履歴が関数ごとには追わないので、そのファイルを変えた変更を、変更メモのうちその処理を id（`<!-- endpoint:token -->`）で挙げた節と、ファイルの関数の外の差分で並べ、その処理が呼ぶ関数と、その行（行の無い処理はファイル）の履歴を読む `git log` も出す
- 意図は、PR の本文（ビルドに `MAP_PULLS` を渡したとき）と変更メモである。関数の履歴では、変更メモのうちその関数を見出しに挙げた節を、地図と同じ読み方（id、名前、`root:name`、`module#name`）で並べる（エンドポイントの処理は id で挙げた節だけ）。コミットのメッセージの本文を読む `git log` も出す
- 差分は OSS が出すコードだけで、テストや文書を含む変更全体と、地図に載せなかったファイルの差分は、ブリーフに書いた `git show` で読む
- 「今のコード」の行は地図をビルドしたときのコードのもので、「今これを呼ぶもの」は型で辿れる呼び出しだけである（登録・初期化からの呼び出しは入らない）。ブリーフの冒頭にもそう書く
- 読む地図は、既定でビルドした `apps/map/public`（`pnpm run build:map` か `pnpm --filter @maronn-openid-connect/map data` で作る）で、`--site`（または `MAP_SITE`）にデプロイした地図の URL も渡せる
- `--limit <n>` で、一覧と関数の履歴の件数を変える。大きな変更をそのまま出すと、`--summary` か `--function` を使うよう標準エラーに出す

Markdown にするのは `packages/map-analysis/src/history-brief.ts` で、型と変更メモの読み方だけを読み込むので、地図のページからも同じものを使える。

## コードの Drawer

エンドポイントの見出しの「コードを見る」や、詳細と関数のページの「コードを見る」で、右からコードの Drawer を開く。
コードはエディタと同じようにたどる。
Ctrl（Mac では ⌘）を押している間、宣言へ移れる名前に下線が付き、押すとその宣言を開く（タッチだけの画面ではタップで開く）。
関数カタログの関数はその関数として開き、ほかの宣言（型、interface のメンバー、定数、引数など）はファイル全体をその行で開いて、名前に印を付ける。
interface のメンバーへ移ったときは、その実装を並べる。
宣言の名前そのものを押すと、それを使う場所を、使う関数の名前と行で並べる。
← と → のボタン（Alt + ← / →）で、たどった場所を戻る・進む。
リンクはビルド時に型検査器で引いた表（後の「データとビルド」の `sources/<hash>.json`）で、地図の根の外（hono、node）の宣言には付かない。
関数には JSDoc とオーバーロードを含め、元ファイルの行番号を表示する。
PR の地図で変えた関数は、「差分」と「変更後の全文」を切り替えられる。
Drawer は関数を単位に開き、アウトラインの一行のコードはその行の `</>` で読む。

TypeScript と TSX のハイライトは [Shiki](https://shiki.style/) でビルド時に生成する。
配色と背景は付属の `github-light` / `github-dark` テーマを使い、ページの明暗設定に従って切り替える。
ファイル全体を解析してから関数の範囲を表示するため、複数行のコメントや文字列の文脈を保つ。
差分の削除行は変更前、追加行と文脈行は変更後のファイル全体を解析した色で表示する。
ブラウザには Shiki を含めず、ハイライト済みのデータを必要なときだけ読み込む。

表示するのはリポジトリの全機能を含むソースで、Express と Fastify は生成元である Hono のソースを表示する。
機能専用ファイルと `(feature: par)` などのブロックには、行番号の右の太い線と範囲の先頭の `par の実装` の札を付ける。
関数の途中から表示する場合も、最初に見える行に機能名を出す。共有ファイルでは、その範囲の外に線を付けない。
Drawer の上には、そのコードに含まれる機能の生成条件を並べる。機能専用のライブラリも「機能の実装」として示す。
閉じるボタン、Escape キー、Drawer の外側のクリックで閉じ、開いたボタンにフォーカスを戻す。

## コードを読むページ

地図と同じ Worker の `./code/` に、コードをエディタのように読むページを置く（`code/index.html`、`src/code/`）。
Drawer の「別タブで読む ↗」と、テストの画面のコードの欄の「コードを読む ↗」から、そのファイルの行を指して開く。

- 左はファイルの一覧（地図の根のファイル。ファイルが一つも無く、下のディレクトリが一つだけのディレクトリは、`packages/core/src` のように一行にまとめる）。開いているファイルの上のディレクトリは開いておく
- 上の検索（Ctrl/⌘ + P）は、ファイルと関数を名前で探す。名前がそのままのもの、名前の始まりが合うもの、名前の中に含むもの、パスに含むものの順に並べる
- コードの名前の移り方は Drawer と同じで、Ctrl/⌘ + クリックで宣言へ、宣言の名前では、それを使う場所か、interface のメンバーなら実装を、下の欄に並べる
- ファイルは常に全体を表示する。関数へ移ったときは、その関数の行に線を引き、その行から見せる。パンくずは、パスと、見ている行を含む関数を示す
- ← と → のボタン（Alt + ← / →）で、たどった場所を戻る・進む
- 見ている場所は URL のハッシュに書く（`#packages/core/src/client-auth.ts:L142-L235`）。行の範囲を書いたリンクは、その範囲に線を引いて開く。地図の根に無いファイル（テストなど）は、その旨を出す

ページは `map.json` を読まず、データの段が書く索引 `code.json`（ファイル、関数とエンドポイントの処理本体の行、interface のメンバーの実装、機能）と、`sources/<hash>.json` だけを読む。

## スマートフォン

幅 900px 未満の画面では、アウトラインだけを表示する。
アウトラインの上の帯には、左上のメニューのボタンの横に、根の名前と「言葉 / コード」、「図・詳細」を置く。
「図・詳細」からドロワーを開き、図、差分、詳細（関数のページでは呼び出し元も）をタブで切り替える。
図のドロワーは画面の幅いっぱいに開き、操作は一行にまとめる（拡大縮小はピンチで行い、縮尺の数値だけを残す）。
アウトラインの行は言葉に幅の 4 割を残し、下の変更の集計の言葉、変更の一行、決定のボタン、↗ と「差分」は行から外して `</>` の中に置く。
左上のメニューから、検索、フレームワーク・機能・エンドポイントの選択、画面の説明、「道筋を選ぶ」を操作できる。

## データとビルド

React + Vite の静的ページで、Cloudflare Workers に静的アセットとして置く（`wrangler.jsonc`）。
同じ Worker（`worker/index.ts`）が、OP のパスと `/__live/*` を地図の OP（前の「地図の OP」）のワークスペースの Durable Object へ渡し、ほかのパスにはページを返す。
ページは表示だけを受け持ち、解析は非公開のワークスペースパッケージ [`@maronn-openid-connect/map-analysis`](../../packages/map-analysis) がビルド時に行う。
例外は木をたどる歩み（`packages/map-analysis/src/walk.ts`）で、読者が選んだ道筋に沿ってページの中で動かす。
型だけを import する小さなモジュールなので、ページは `@maronn-openid-connect/map-analysis/walk` としてそのまま読み、テストカタログも同じものでケースのステップを求める。
同じデータの段で [`@maronn-openid-connect/test-catalog`](../../packages/test-catalog) がテストを読む。

1. CLI の `explain --format json` を全機能オンで 4 フレームワーク分まとめ、関数カタログを読む
2. 関数とエンドポイントの処理本体を TypeScript のコンパイラ API で読み、処理の流れの木にする。呼び先は型で解決する
3. MAP_BASE があれば、変更前のコードからも木を作り、木の差分、式の差分、影響範囲、変更メモの対応づけを求める
4. テストを読んでカタログにし、関数カタログとエンドポイントに結び付ける。MAP_TEST_REPORTS があれば、その実行の結果と到達も結び付ける。地図の OP（`packages/live-op`）がビルドしてあれば、OP の外のものを要らない全ケースを、ビルドのプロセスの中の地図の OP で、ケースごとに新しいワークスペースに準備して送り、その記録を根の木でたどって、ケースが通った道筋を求める（前の「リクエスト」）。MAP_BASE があれば、変更前のカタログとの差分を求め、関連するテストの変わらない変更を検査の対象にし、`changes.md` の説明の無い変更の次にその一覧を、末尾に畳んだテストの差分を足す
5. 次のファイルを `public/data/` に書く

- `map.json`：索引。フレームワーク、コマンド、機能、エンドポイントとステップ、関数カタログ（呼び先、呼び出し元、外へ出る失敗）、interface のメンバー（説明、実装、実装が呼ぶもの）、PR の変更の一覧。木は含まない
- `functions/<hash>.json`：フレーム一つ分。木、よく使う選択、PR の地図では変更前の木、ノードの差分、式の差分、ノードごとの hunk。フレームを開いたときに読む
- `sources/<hash>.json`：ハイライト済みのソース。Drawer を開いたときに読む。名前ごとに宣言の場所（`links`）を、宣言ごとにそれを使う場所（`uses`）を持つ（`packages/map-analysis/src/symbols.ts`。型検査器で引き、地図の根の外の宣言は持たない）。リンクの先を開けるよう、地図の根のファイルはすべて書く
- `code.json`：コードを読むページの索引（`CodeIndex`。`packages/map-analysis/src/code-index.ts`）。ファイル、関数とエンドポイントの処理本体の行、interface のメンバーの実装、機能だけを持ち、`map.json` の 6 分の 1 ほどの大きさである
- `changes.md`：PR の変更の Markdown。PR のコメント（`.github/scripts/map-comment.mjs`）がこれを使い、`<!-- oidc-provider-map-links -->` の行をリンクに置き換える
- `requests/<hash>.json`：エンドポイントの処理本体一つ分の、ケースのリクエストの記録（`RootRequests`）。道筋ごとにそれを通ったケースと、ケースごとの応答のステータスと OAuth のエラー、通った道筋、根が動いたか、食い違いと仮の側の数を持つ。`map.json` の `requests` が根ごとの URL を、`liveOp.probes` がケースを動かした OP のプローブの表のハッシュを持つ。フローを開いたときに読む
- `history/<hash>.json`：main に入った変更の一覧。main（PR の地図では MAP_BASE の、ほかはリモートの main（`origin/main`、`upstream/main` など）のうち、HEAD の持つコミットを main に入れた最も新しいコミット（HEAD のブランチをマージしたもの、その上に積んだブランチのマージを含む。PR の変更の起点 `git merge-base` までの履歴がそろう。その間の HEAD の持たない変更も並ぶ）。リモートの main を持たない clone では HEAD）の first-parent の履歴を `packages/map-analysis/src/history.ts` が読み、PR のマージ、スカッシュ、PR を経ない直接のコミットごとに、コミット、変えたファイル、カタログと同じ読み方で求めた足した・変えた・消した関数、変更メモを並べる
- `history/<hash>.json`（変更ごと）：変更の、OSS が出すコード（関数カタログの根のファイル）だけの差分（`HistoryDetail`）。git の差分（前後 3 行の文脈、GitHub と同じもの）を、変更した関数ごとと関数の外とに切り分けて持つ（ほかの関数の行が変わるところで hunk を切るので、一つの関数の差分にはその関数の行だけが入る）。変更が書いた変更メモの本文も持つ。テスト、文書、道具の変更は入れない。変更のページを開いたときと、`pnpm map:history` が読む。差分が長すぎるファイル（2,000 行を超えるもの）と、変更全体で 20,000 行を超えた後のファイルは hunk を持たず、どちらの理由かを残す（ライブラリのファイルを先に入れる）

テストの画面のデータ（`tests.json`、`outline.json`、`tests/`）は `apps/tests/public/data` に書く（中身は [docs/design-test-catalog.md](docs/design-test-catalog.md) の「データ」）。
地図の `public/data` にテストのファイルは無い。

`pnpm run build` は、データとページを作った後、テストの画面をビルドして（`pnpm --filter @maronn-openid-connect/tests build`）、その `dist/` を地図の `dist/tests/` に写し（`scripts/copy-tests-viewer.mjs`）、最後に検査する。
検査より前に写すので、検査が落ちても `dist/` にはテストの画面が入る。
写す段は、テストの画面がビルドされていないとき、そのデータが無いとき、地図のデータにテストのファイルが残っているときに落ちる。

関数の id はカタログと同じ `<root>:<module>#<name>`、hono のエンドポイントの処理本体は `endpoint:<id>` である。
解析パッケージのテストは、木から求めた呼び先が CLI のカタログの calls / calledBy と一致すること、本体の全行がどれかのノードに属することを確かめる。

ビルドの最後に `scripts/check-map.mjs` が地図の出力を検査し、次の数を出す。
名前の無い選択（exit ケース）と、同じフレームで重なる名前（番号だけで区別した名前を含む）、ノードに属さない行、PR が変えた行のうちノードに属さないもの、説明の無い変更である。
全機能オンの `/token` に、refresh_token と authorization_code の名前付きの選択があることも確かめる。
コードのリンク（`links`）がどれも名前の上にあり、地図が持つファイルの宣言の名前へ行くことも確かめる（`checkLinks`）。
ケースを地図の OP で動かしたビルドでは、OP の外のものを要らない hono のケースがどれも一つの根で一度動いたこと、ケースが通った道筋がどれもその根のよく使う選択であることを確かめる。
どのケースも、再生する道筋がそのリクエストが動かしたものだけを通り、根を動かし（404 や 405 を期待するケースを除く）、期待するステータスと OAuth のエラーを OP が返したことも確かめる。
これは地図の出力に対する検査で、貢献者のコードの形には向けない。
図の検査（`src/lib/diagram.data.test.ts`）も同じ考えで、ビルドしたデータがあるときだけ走る（`ci.yml` の `map` ジョブでは `build:map` の後のテスト）。
決定と終わりがどのフレームの図からも欠けないこと、`try` の枠が自分の箱だけを囲むこと、図がステップと守りをアウトラインと同じに畳むこと、幅に合わせて見出しが 11px に届くフレームが 9 割を下回らないことを確かめる。

`MAP_PR`、`MAP_PR_TITLE`、`MAP_PR_URL` は、ページに出す PR の番号、タイトル、URL である。
`MAP_TEST_REPORTS` は、テストの実行が書いたディレクトリ（Vitest と Playwright の JSON、到達の記録）である。
無ければ、テストの札はコードから読んだものだけになる。
`MAP_PULLS` は、GitHub の PR の一覧の JSON ファイル（`gh api 'repos/{owner}/{repo}/pulls?state=closed' --paginate --slurp` の出力）である。
あれば、履歴の PR のタイトルは GitHub のものになり、PR の本文が付く。
PR は番号と、その PR をマージしたコミット（`merge_commit_sha`）が変更のコミットと一致するときだけ対応づける。main の履歴には、別のリポジトリから取り込んだコミット（番号がこのリポジトリの別の PR を指す）もあるからである。対応づいた変更だけを GitHub の PR へリンクし、ほか（`MAP_PULLS` の無いビルドでは、すべて）はコミットへリンクする。別のブランチへマージされ、それと一緒に main に入った PR も対応づけるので、CI は base を絞らずに閉じた PR を読む。
rebase でマージした PR のコミットは番号を持たず、GitHub もどのコミットがその PR のものかを一覧に出さないので、PR を通さない変更として並ぶ。
`MAP_REPOSITORY` は、履歴がリンクする GitHub のリポジトリ（`owner/name`）である。
無ければ `GITHUB_REPOSITORY` を、それも無ければ `origin` の URL を使う。

```bash
# ルートで: CLI、解析パッケージ、テストカタログ、地図の OP（packages/live-op）をビルドしてから地図をビルドする（dist/ に静的ページ、dist/tests/ にテストの画面）
pnpm run build:map

# このディレクトリで
pnpm run dev              # データを作って Vite の開発サーバー（http://127.0.0.1:3610。同じオリジンで地図の OP が Node で答える）
MAP_BASE=origin/main pnpm run dev   # origin/main からの変更（コミットしていないものを含む）を載せた地図
MAP_BASE=origin/main pnpm run data  # 開発サーバーを動かしたまま、データだけを作り直す（ページを読み込み直すと載る）
pnpm run build            # データを作って dist/ にビルドし、テストの画面を dist/tests/ に入れ、地図の出力を検査する
pnpm run check            # public/data の地図の出力だけを検査する
pnpm run changes:draft    # MAP_BASE からの差分で変更メモの雛形を書く
pnpm run deploy           # ビルドして wrangler deploy（https://maronn-oidc-map.<subdomain>.workers.dev）
pnpm run worker:dev       # デプロイするのと同じ Worker（ビルドした dist/ と、Durable Object の地図の OP）を wrangler dev で手元に動かす（http://127.0.0.1:8787）
pnpm test                 # ページの純粋な部分（トレース、決定、図、フローの再生、ハッシュ、変更の札、検索）のテストと、Worker のテスト（worker/*.test.mjs）
```

開発サーバーは地図だけを配るので、ヘッダの「テスト」は開発サーバーでは開かない。
テストの画面は `pnpm run data` の後に、その開発サーバー（`pnpm --filter @maronn-openid-connect/tests dev`）で開く。
ビルドした `dist/` を `pnpm run preview` で配れば、`/tests/` も開く。

データのビルドは `public/data` のファイルをその場で書き、前のビルドの残りだけを最後に消す（ディレクトリを消して作り直さない）。
そのため、変更メモを書いた直後などに開発サーバーを止めずに `pnpm run data` で作り直してよい。
それでも古いデータや「読み込めませんでした」が出るときは、開発サーバーを起動し直す。

`wrangler deploy` は `CLOUDFLARE_API_TOKEN` と `CLOUDFLARE_ACCOUNT_ID`（または `wrangler login`）を使う。
Worker の名前は `wrangler.jsonc` の `name` で変える。

## Workers で認可リクエストを確認する

リポジトリのルートで `pnpm sample:hono-cloudflare` を起動すると、Hono の OP が Wrangler とローカル D1 で動く。
別のターミナルで次を実行すると、地図とテスト画面と同じ生成処理で ES256 署名付き Request Object を作り、実際に OP に送る。

```bash
pnpm --filter @maronn-openid-connect/map request:check
```

Cloudflare 上で試す場合は `pnpm deploy:hono-cloudflare` でサンプル OP と D1 をデプロイし、保存された issuer を渡す。

```bash
pnpm --filter @maronn-openid-connect/map request:check "$(cat samples/hono-cloudflare/.deploy/issuer)"
```

このコマンドは実行ごとに検証用クライアントを 1 件登録する。
登録した公開鍵で Request Object を検証できれば、`GET /authorize` は `transaction_id` 付きの `/login` にリダイレクトする。

## PR ごとのプレビューと main のデプロイ

`.github/workflows/ci.yml` の `map` ジョブが、`test` ジョブの後に、リポジトリのシークレット `CLOUDFLARE_API_TOKEN` と `CLOUDFLARE_ACCOUNT_ID` で次を行う。
`test` ジョブが書いたテストの結果と到達（`work/test-reports` の artifact `test-reports`）を `MAP_TEST_REPORTS` で受け取り、テストの画面に載せる。
テストが落ちても、そこまでの結果で作る。
閉じた PR の一覧を `gh api`（`GITHUB_TOKEN`）で `work/pulls.json` に読み、`MAP_PULLS` で渡して、変更の履歴に PR の本文を載せる。
読めなくても地図は作り、履歴は git のタイトルとコミットだけになる。
テストの画面は地図の `dist/tests/` に入るので、どのデプロイでも地図の URL の `/tests/` で開く。

- **PR**（opened / synchronize / reopened）：その PR のコードから地図をビルドし、PR ごとの Worker `maronn-oidc-map-pr-<番号>` へ `wrangler deploy --name maronn-oidc-map-pr-<番号>` する（`.github/scripts/map-preview.mjs`）。PR ごとに固定の URL を持ち、push のたびに同じ URL が新しくなる。プレビューへのリンクと、畳んだ変更の表は PR のコメントに書く（push ごとに同じコメントを書き換える）。説明の無い変更か、関連するテストの変わらない変更で地図のビルドが落ちても、デプロイとコメントは行い、ジョブは失敗のままにする
- **PR を閉じた**：`.github/workflows/map-preview.yml` が、その Worker を（Durable Object ごと）`wrangler delete --name maronn-oidc-map-pr-<番号>` で消す。`map` ジョブと同じ concurrency の group で順に走り、`map` ジョブは PR が閉じていればプレビューを作らない
- **main への push**：`wrangler deploy` で本番（いまは `https://maronn-oidc-map.<subdomain>.workers.dev`）を更新する

PR ごとに Worker を分けるのは、地図の OP のワークスペースが Durable Object にあるからである（[docs/design-live-op.md](docs/design-live-op.md) の「ホスト」）。
同じ Worker の Worker Preview（`wrangler preview`）やバージョンのプレビュー URL は、本番の Durable Object の名前空間に届き、そこでは main の OP が動く。
そのため `wrangler.jsonc` は `preview_urls` を `false` にし、`wrangler versions upload` でプレビューを作るスクリプトも置かない。
`map-preview.mjs` は、`wrangler.jsonc` が Durable Object を持たないときだけ Worker Preview `pr-<番号>` を作り（失敗したら PR ごとの Worker へ `wrangler deploy` する）、閉じたときは Preview と Worker の両方を消す。
どの場合も Actions の artifact（`oidc-provider-map`）にビルド結果が残る。
`dist/` を静的に配信すれば同じ地図が見られるが、地図の OP は動かないので、リクエストの欄は「地図の OP に接続できません」と出す。

## 直接呼ばれない配線

上の「追えない配線」は、ミドルウェア登録、コンテキストへの書込み、コールバック、モジュール初期化を場所と理由付きで一覧する。届く先を証明できないものを、実行トレースに混ぜず残す。ファイル、コード、理由で絞り込み、型で分かる参照先は関数のページへ開ける。`#hono--wiring` / `#nextjs--wiring` で共有できる。機能をオフにしたときの配線除去までは確定しない。

`map.json.wiring` は索引の関数を持たないモジュールも読む。動的なキー・外部 callback の呼び先・middleware の mount や実行順を推測しない。設計と調査の根拠は [配線の設計](docs/design-traceable-wiring.md)、再現可能な全件棚卸しは [監査記録](docs/wiring-audit/README.md)、今後の作業手順は [実装用・レビュー用 skills](../../skills/README.md) にある。

## 構成

- `src/lib/trace.ts`：トレースの状態（開いたフレーム、選んだ決定）、選んだ決定で走るノード（「ここで失敗」を含む）、ノードへ至る決定、ステップと守りの畳み方（図と共通）、変更まで開くフレームと下の変更の到達、アウトラインの行、失敗を捕まえる `catch`
- `src/lib/diagram.ts`：焦点のフレームの木をアウトラインと同じ畳み方で箱と矢印にし、選んだ道筋の箱、行、矢印と、箱の札を求める
- `src/lib/graph.ts`：Dagre による図の自動配置、箱の幅、見出しを一行に収める省略
- `src/lib/camera.ts`：図を開く倍率と位置、選んだ箱が見える所までの移動
- `src/lib/playback.ts`：フローの再生。トレースが開いているフレームを通る歩み（`@maronn-openid-connect/map-analysis/walk`）、図の箱ごとの場面、場面の行、場面の時間と速さ、もう一段開く呼び出し
- `src/lib/flowchart.ts`：フローのフローチャート。図を始まり・処理・ひし形・終端とサブグラフにし、矢印のラベルとステップの間の値を付け、終端を箱の横に置く配置、場面の列が通る箱と矢印
- `src/lib/history.ts`, `src/components/HistoryScreen.tsx`：変更の履歴（一覧の絞り込み、変更のキー、関数を変えた変更、今の地図で届くエンドポイント、GitHub へのリンク）と、その画面と関数のページのタブ
- `src/lib/hash.ts`：URL のハッシュ（`#hono--token/s4/s4.s2;d=s4.s1:true`、`#hono--token;p`、`#hono--token;p;x=x12`、`#hono--fn--verifyClientSecret`、`#hono--changes`、`#hono--wiring`、`#hono--history--pr-207`）
- `src/lib/changes.ts`：PR の変更の札（行と箱で共通）、下の変更の集計、変更に至る道筋の選択、届く経路の名前とまとめ方、失敗が捕まる場所、差分の行番号、変更メモの本文
- `src/lib/words.ts`：アウトラインの行と図の箱の言葉（JSDoc、コメント、言葉の無い文の続き、`return` が返すもの、決定の側の名前）
- `src/lib/model.ts`：機能の絞り込み、`generate` のコマンドライン、関数に届くステップと呼び出し元、検索
- `src/lib/source.ts`, `src/components/CodeDrawer.tsx`：ソースの行と、コードを読む Drawer
- `code/index.html`, `src/code/`：コードを読むページ（ファイルの一覧、名前で開く検索、URL のハッシュは `src/code/lib.ts`）
- `src/lib/links.ts`, `src/components/SourceView.tsx`：コードの名前のリンク（行を名前で切る、移る先、使う場所、戻る・進むの履歴）と、リンク付きのコードの表示
- `src/components/Trace.tsx`, `TraceView.tsx`, `SelectionBar.tsx`：アウトライン、決定のボタン、よく使う選択、図・差分・詳細のタブ
- `src/components/FlowPlayer.tsx`：フローの再生の操作、場面の説明。`FlowRequest.tsx` がリクエストを書いて実行する欄と応答（道筋を通るケースは `src/lib/requests.ts`、データは `useRequests.ts` が読む）を、`RequestCase.tsx` が想定リクエストとその準備を、`RecentExchanges.tsx` が最近のリクエストを、`LiveStatePanel.tsx` が地図の OP の状態とグラントを、`StoredRecords.tsx` が読んだ・書いた記録とその出どころを出す（記録の言葉は `src/lib/records.ts`）。フローチャート（`FlowChart.tsx`）は、再生の位置を受け取って矢印を流し、印を動かす
