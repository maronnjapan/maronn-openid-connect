# Provider の配線と地図をレビューする

リポジトリルートの `skills/references/provider-map-evidence.md` を最初に読む。この skill はレビュー用。実装・修正を依頼された場合は `skills/provider-map-implementation/SKILL.md` を使う。

既定では指摘を返す。コードの編集、追跡される生成物の書換え、commit/push、GitHub のレビュー・コメント投稿は、利用者がその作業も依頼した場合に行う。検証に必要なビルド、一時出力、独立した worktree の作成は進めてよい。

## 比較対象と根拠を確認する

1. 実際の PR の base/head、レビューする SHA、差分、作業ツリーを確認する。マージ先 `main` と、背景ブランチや調査用 checkpoint の比較を混同しない。
2. 意図と変更メモを読んでから、実装と型の経路を追う。報告書の件数や既存の監査 JSON は手掛かりとし、今回の SHA の成功の根拠として流用しない。
3. 対象に必要な検査を実行し、PR の base を指定した新しい地図を読む。作業中の編集があれば、その編集をレビュー対象へ混ぜずに検証する。
4. 実装者の主張と、自分で確認した事実・確認できなかったことを区別する。

## 到達の欠落と誤判定を調べる

- endpoint の root から actual call node と sites を辿り、core までの型の橋を確かめる。カタログに載っただけ、`calls` に名前があるだけ、あるいは同じ関数の範囲に行があるだけで到達としない。
- factory の作成と返されたメンバーの実行を分ける。interface 単位の保守的な接続を、特定 instance の provenance として説明していないか確かめる。
- callback を引数や hook へ登録しただけで即時実行と見なしていないか調べる。名前・inline・spread・別名・indexed callable・defaulted optional options・匿名契約も確認する。配列 callback は API と型の根拠を確認する。
- context の値の型が分かることと、値を構築した処理へ戻れることを分ける。動的 key、上書き、module initializer、middleware の mount/filter/実行順を推測で埋めていないか調べる。
- PR の `changes.frames[].reach` に、実際の変更箇所、必要な feature、source の境界が反映されるか確かめる。削除した frame や移動は、base 側の出力とも照合する。
- `wiring` と untraceable call に場所・理由があり、画面と PR でも読めるか確かめる。未解決を黙って消すことと、偽の実行経路を作ることの両方を探す。

## 同型の全件と生成を調べる

共通資料の形の棚卸しを使い、各候補に call/実装の橋/配線診断、または対象外の理由が対応することを確かめる。件数だけ、題材の名前だけ、inspect スクリプトの表示フィルタだけで網羅としない。`uncovered` と型 API の失敗が無視されていないか調べる。

Hono と Next.js の対応、feature のオン・オフ、owner block の削除、import 境界、CLI の生成を確認する。samples が手編集ではなく現在の CLI から生成されたものか、matrix が対象の構成を検証しているか調べる。

関数宣言・JSDoc・step marker、意図を書く変更メモ、破壊的変更の changeset を確認する。新しい規則に機械的検査があるか、到達先を手で列挙する負担が持ち込まれていないか調べる。

`expect`（`expect.any` 等を含む）が `it` のコールバック本体だけにあるか確認する。共通 helper、test-support、`describe`、ライフサイクル hook へ隠れた検証も対象にし、helper が返す値を呼び出し元のテスト本体で検証する。Playwright の `test` と `playwright-bdd` の登録済み `Given` / `When` / `Then` は、その runner のテスト本体として扱う。`.github/scripts/lint-expect-scope.mjs` を実行し、移動の際にエラーの型・code・status や途中の redirect 等の検証が落ちていないか差分も照合する。

## 検査の主張を検証する

実行した検査の SHA、コマンド、終了結果、失敗出力と対処を確認する。コードを変える前の成功、実行していないテスト、環境制限による失敗を成功に読み替えない。ローカルと CI、unit/package tests とブラウザ E2E・外部 OIDF テストを区別する。

検査が通っていても、呼び出しを落とす解析や callback を即時実行と誤認する解析は見逃し得る。実際のデータと再現条件を確認する。検査を追加する提案は、意味のある回帰を防ぐものに絞る。

## 指摘を返す

実際に修正すべき不具合を、影響に応じた P0–P3 の優先度順に返す。各指摘には次を含める。

- ファイルと必要最小限の行、発生条件・具体的な入力または構成。
- 期待と実際の差、その根拠となるコード・型・生成データ・検査出力。
- どの動作やレビュー判断に影響するか、必要なら最小の再現手順。

コードやデータで確認できないことを断定しない。理由付きの保守的な未解決は、合意した範囲なら制約として述べ、不具合として水増ししない。指摘がなければそう述べ、レビューした範囲、実行した検査、未確認の範囲を短く添える。利用者から依頼がなければ、この結果を GitHub へ投稿しない。
