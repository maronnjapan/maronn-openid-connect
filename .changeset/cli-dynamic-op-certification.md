生成する OP が、private_key_jwt のクライアント認証、`request_uri`、ログイン画面と同意画面のクライアントの表示を扱えるようにする（OpenID Certification の Dynamic OP プロファイルに合わせる）

- private_key_jwt（OIDC Core 1.0 §9）: トークン、イントロスペクション、リボケーション、PAR、Device Authorization、CIBA のエンドポイントが、クライアントアサーションを core の部品で検証する（base の新しいファイル `client-auth.ts`）。`aud` はそのエンドポイントの URL か issuer。鍵は `private_key_jwt` の用途の鍵か `jwks_uri` の鍵で、`jti` の再送は期限まで拒否する（`stores.ts` の `clientAssertionJtiStore`。`--db sql` は新しいテーブル `client_assertion_jtis`、`--db kv` は `client_assertion_jti:<hash>` のキー、`--db` 無しはメモリ）。`registerClient()` に `tokenEndpointAuthMethods: ['private_key_jwt']` と `tokenEndpointAuthSigningAlg` を登録でき、`--db sql` は新しいテーブル `client_private_key_jwt_auths`、`--db kv` はクライアントのレコードの `private_key_jwt` に保存する。discovery は `token_endpoint_auth_methods_supported` に `private_key_jwt` を、`token_endpoint_auth_signing_alg_values_supported` に `ProviderConfig.tokenEndpointAuthSigningAlgValuesSupported`（既定は RS256、RS384、RS512、ES256、ES384、ES512）を広告し、イントロスペクションとリボケーションの `*_endpoint_auth_methods_supported` と `*_endpoint_auth_signing_alg_values_supported` も同じにする
- `request_uri`（OIDC Core 1.0 §6.2）: request-object 機能の新しいステップ `fetch-request-uri` が、認可エンドポイントの `[resolve-client]` の後、`[resolve-request-object]` の前に、URL の `request_uri` から Request Object を取得し、`request` と同じく検証する。設定は `requestUriParameterSupported`（既定 `true`）、`requireRequestUriRegistration`（既定 `false`）、`allowInsecureRequestUri`、`requestUriTimeoutMs`、`requestUriMaxBytes`、`requestUriMaxLength`（既定 512）。discovery は `request_uri_parameter_supported: true` と `require_request_uri_registration` を広告する（機能を外した OP は従来どおり `false` を広告し、`request_uri_not_supported` で拒否する）。取得の失敗はリダイレクトせずに固定文言の `invalid_request_uri` で拒否し、理由は `console.warn` に出す。`registerClient()` に `requestUris` を登録でき、`--db sql` は新しいテーブル `client_request_uris`、`--db kv` はクライアントのレコードの `request_uris` に保存する
- **名前の変更**: Hono / Express / Fastify の `createApp` / `applyOidc` のオプション `clientJwksFetch` を `outboundFetch` に改め、`jwks_uri` と `request_uri` の取得で共有する。Next.js は `_oidc-provider/provider.ts` の `outboundFetch` を書き換える
- クライアントの表示（OIDC Dynamic Client Registration 1.0 §2）: ログイン画面と同意画面が、クライアントの `clientName`（無ければ client_id）、`logoUri` の画像、`policyUri`、`tosUri`、`clientUri` のリンクを表示する（Hono / Express / Fastify は `views.tsx` の `ClientSummary`、Next.js は `_oidc-provider/client-summary.tsx`）。URL は https のものだけを画面に入れ、`ProviderConfig.allowInsecureClientDisplayUris`（開発用）で http も入れる。`requireClientDisplayUriHostMatch` では、`logoUri` と `policyUri` のホストが `redirectUris` のホストと同じときだけ入れる（同 §9.1）。`registerClient()` に登録でき、`--db sql` は `clients.name` と新しいテーブル `client_display_uris`、`--db kv` はクライアントのレコードの `name` と `display_uris` に保存する
- `--enable dynamic-client-registration`: `tokenEndpointAuthMethods` の既定に `private_key_jwt` を足す。private_key_jwt の登録は `jwks` か `jwks_uri` を要し、`token_endpoint_auth_signing_alg` と、request-object 機能のある OP では `request_uris` を登録できる。登録した `client_name`、`logo_uri`、`policy_uri`、`tos_uri`、`client_uri` は、ログイン画面と同意画面に表示する
- 新しいテーブルはどれも `CREATE TABLE IF NOT EXISTS` なので、`schema.sql` を実行し直せば既存のデータベースにも足される。行の無いクライアントの読み方は変わらない
