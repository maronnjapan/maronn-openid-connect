# OIDC Provider Map

生成される OpenID Provider の地図。
`maronn-oidc generate` のフレームワークと機能を選ぶと、その構成のエンドポイントを一覧し、エンドポイントの処理を呼び出しの先まで一つの画面でたどれる。
PR の地図では、その PR が変えた関数がエンドポイントから何段下にあっても、何を変えたか（構造と式の差分）と差分のコードをその場で読める。

設計の考え方は [docs/design-change-trail-and-decision-cases.md](docs/design-change-trail-and-decision-cases.md) にある。

## トレース：エンドポイントの処理を根にした木

エンドポイントの画面の中心はアウトラインで、エンドポイントの処理本体（hono の pipeline のハンドラー、Next.js の Route Handler）を、上から下へ一行ずつ読む。
一行は処理の流れの木のノード一つで、まずその処理が何をするかを自然言語で書き、コードは言葉が無いところにだけ出す。

- ステップ：`// [step-id]` の印で囲んだブロックは、その見出し（「クライアントを認証する」）の一行に畳む。▸ で中を開く。呼び出し一つだけのステップ（hono のステップ）は、▸ でその関数の流れを開く
- 呼び出し：呼び先の関数の JSDoc の一行目（lint が求めるもの）、resolver や store のメソッドなら interface のメンバーの JSDoc
- 条件や処理：文の手前のコメントか、条件が呼ぶ関数の JSDoc。どちらも無ければコード（変数の定義や `if (!keys)` など）
- 終わり：`return` と `throw` には「終わり」「失敗」の札を付け、`return` は返す関数の JSDoc で言う
- 守り（`if (!client) throw ...`）と任意項目の `if` は、`if (!client) → 失敗: TokenError(invalid_client) を投げる` のように一行で読む
- `try` は「ここから例外を捕まえる」の見出しの下に、捕まえる範囲の行を一段下げて並べ、最後に「例外が起きたとき → …」の行を置く

ざっと眺められるよう、どの行も一行に収める。
収まらない言葉は省略し、全文は行に重ねたときの表示と `</>` で読める。
`</>` はその行のコード、詳しい説明（コメントの全文、メソッドの説明）、PR の変更の全部を開く。
上の「言葉 / コード」は、全部の行を言葉の一行かコードの一行に切り替える。
PR の変更は、札の横に一つ目の変更（「`<` を `<=` に変えた」）を同じ行で示し、「エラー時」の捕まる先（「失敗 → POST /token の catch」）も同じ行に出す。
条件の中や `return` の中で呼ぶ関数は、その行が受け持ち、▸ でその関数を開ける。

呼び出しの ▸ を押すと、呼び先の関数の流れをその場で一段下げて開く。
何段でも開け、再帰はその関数の二度目で止める。
↗ はその関数を根にしたトレース（関数のページ）へ移る。
型で呼び先を引けない呼び出しは「追えない呼び出し」と示し、理由を添える。

行を押すと、右の欄が図になり、その行の箱を囲んで見える所まで動かす。
別の関数の行なら、図もその関数へ移り、図の上のパンくず（`POST /token › authenticateTokenClient()`）が今どこを見ているかを示す。

### 決定を選んでたどる

決定の行には進む側のボタン（成立 / 不成立など）が並び、側の行（「成立」「例外が起きたとき」）を押しても選べる。
選ぶと、その側の行は活性のまま、ほかの側の行と、選んだ道筋では通らない後の行が灰色（不活性）になる。
行は消さないので、どこが選ばれていないかが見える。
もう一度押すと選択を外し、すべての行が活性に戻る。
子フレームの決定も同じ仕組みで選べ、エンドポイントから下の関数まで一本の道筋が決まる。

機能のオン・オフはノードの機能の札で絞る。
オフの機能のブロックは木から外し、そのブロックが作る値を読む条件は値の無い側だけを残す。

### よく使う選択

画面上部の「よく使う選択」に、木から計算した選択を並べる。
選ぶとその決定の組み合わせになり、複数選ぶと和集合になる。
「すべて表示」で選択を外す。

- ステップ：エンドポイントの各ステップに至る決定。名前はステップの見出し（`/token` なら「refresh_token グラントを検証する」「authorization_code グラントを検証する」）
- 変更に至る道筋：PR の地図で、変えたノードに至る決定。フレームをまたぎ、選ぶと間の呼び出しを開く
- 終わり方：`return` と本体の終わりごとに、そこへ至る決定。名前は区別に要るラベル（`exchanged: 成立`）だけで、守りを不成立で通った事実は書かない
- 失敗で終わる：`throw` と、呼び先から伝わる失敗。エラーごとにまとめ、呼び先からのものは「`verifyClientSecretHash` から」と投げる関数で示す。選ぶとその `throw` までのフレームを開く

選択は木をたどって求めるので上限が無く、道筋の列挙や名前の無い「exit ケース」は無い。

### 失敗の流れとエラー時

関数がどう失敗するかは、JSDoc の `@throws` に頼らず木から求める。
`try` の外の `throw` と、`try` の外で呼ぶ関数の失敗を、カタログ全体で不動点まで集めたものが、その関数から外へ出る失敗である。
`catch` で受けた例外をそのまま投げ直す `try` は、捕まえなかったものとして数える。

「エラー時」をオンにすると、各呼び出しに「失敗すると → どこで捕まるか」を出す。
捕まる先は、トレースを上へたどって最初に見つかる `catch` である（`/token` なら根のフレームの `catch` と `respondTokenError`）。

### 図と詳細

アウトラインの右に、図、経路の差分、詳細のタブを置く。

- 図：焦点のフレーム一つ分の流れの形を箱と矢印で描き、選んだ道筋を青にする
- 経路の差分：開いているフレームのうち、この PR が変えたものの差分を実行順に並べる
- 詳細：選んだ行の説明。呼び先の JSDoc、外へ出る失敗、ステップが受け取る値と次へ渡す値、interface のメンバーの説明と実装

文はアウトラインが読むので、図はアウトラインと同じ畳み方で、流れの形だけを描く。

- 守りと任意項目の `if` は一つの箱にし、すぐ終わる側は箱の中の行（`→ throw invalidAssertion(…)`）にする。分かれ道の側、`switch` の case、`catch` でも、すぐ終わるものは行にする
- 中身が一文の繰り返しは一つの箱にし、条件と `return` の中の呼び出しはその箱に含める
- エンドポイントの本体は、ステップ一つを一つの箱にし、終わり方を行に添える。呼び出し一つだけのステップ（hono のステップ）の箱を押すと、その関数を開いて図の焦点を移す。それ以外のステップ（▸）はその場で中を開き（▾）、もう一度押すと畳む
- PR が変えたノードは畳まない。変えたノードを含むステップは、開いた状態で始まる
- 決定と終わりは、箱、行、畳んだステップのどれかに必ず入る（`src/lib/diagram.data.test.ts` が全フレームで確かめる）

箱の幅は 320px で、横に二つ並ぶ段があるときだけ 200px にする。
幅は配置だけで決め、欄の幅では変えないので、どの画面でも同じ配置になる。
選んだ道筋で変わるのは色だけで、箱は動かない。

図は、箱の見出しが 11px 以上になる倍率で開く。
幅に合わせた倍率がそれより小さくなるときは 0.88 倍で開き、選んだ箱（なければ始まりの箱）を中央に置く。
アウトラインの行を選ぶと、図はその箱が見える所まで同じ倍率で動き、別のフレームの行なら図の焦点もそのフレームへ移る。
図の箱を押すと、アウトラインの対応する行を選んで、その行まで送る。

図の色は 3 つに限る。
灰色は選んだ道筋で通らない部分、青は通る部分と選んだ箱、赤は `throw`、`catch` の行とエラーの矢印である。
PR の札（後の節）はこの 3 色を使わない。

図は Dagre で接続関係に沿って自動配置する。
図の上部の一行で、向き（↓ 縦 / → 横）、拡大縮小、「幅」（幅に合わせる）、「全体」（全体を表示）、「戻す」（開いたときの倍率と位置に戻す）を操作する。
縮尺の数値を押すと 100% に戻る。
ドラッグで移動し、ピンチ（スマートフォンとトラックパッド）で拡大・縮小する。
2 本指スクロールとマウスホイールは移動に使い、図にフォーカスすると矢印キーで移動、`+` / `-` キーで拡大・縮小できる。
Tab で箱へ移ると、その箱が見える所まで図が動き、Enter か Space で押したことになる。
これらの操作には `react-zoom-pan-pinch` を使う。

開いたフレームと選んだ決定は URL のハッシュに書くので、たどった道筋をそのままリンクで渡せる（`#hono--token/s0b1s0/s0b1s0.s2;d=s0b1s0.s1:true;f=s0b1s0.s2`）。

## 関数のページ

関数を選ぶと、その関数を根にしたトレースを開く。
読み方はエンドポイントの画面と同じで、呼び出しの先をその場で開ける。
横の「呼び出し元」には、その関数に届くエンドポイントのステップ（間に挟まる関数を順に）と、その関数を直接呼ぶ関数を並べる。

## PR の地図：このPRの変更

PR の地図は、その PR が変えた関数とエンドポイントの処理本体に札を付ける。
札は灰色の濃淡で示す。

- `追加` `変更`：その関数を足した、またはコードを変えた。アウトラインでは、足した行と変えた行にも付く
- `下で変更`：その呼び出しの先（さらに下を含む）のコードを変えた。呼び出しの行に、下の変更の集計（「条件 +1、呼び出し 変更 1」）を添える
- `説明` `移動` `メモ` `削除`：JSDoc だけ変えた、コードはそのままで別のファイルへ移した、コードは変えていないが変更メモが説明している、消した

「変更まで展開」は、根から届くすべての変更まで、間の呼び出しを一度に開く。
深さと件数の上限は無い。
アウトラインでは、変えたノードの下に式の差分（「`<` を `<=` に変えた」「引数 `issuedAt` を足した」）と差分のコードを置き、消したノードは消した位置に打ち消し線で残す。

「このPRの変更」のページ（`#<framework>--changes`）は、先頭に説明の無い変更を並べ、続けて変えた関数ごとに次を置く。

- 自動要約：木の差分から作った言葉（「条件 `expiresAt <= now`: `<` を `<=` に変えた」「条件 `secret.length < 8` を足した（早期リターン）」）
- 差分：関数の行の範囲の差分。ノードの行の範囲で切って、どのノードの変更かを示す
- メモ：変更メモの、その関数の節
- 届く経路：その変更に届くエンドポイントと、そこまでの決定と必要な機能。押すと、トレースが変更まで展開され、決定が選ばれた状態で開く

### 木の差分

変更前の木も同じ解析で作り、変更後の木と枝ごとに、ノードの種類と正規化した要約で順序を保って対応づける。
対応づいたノードのコードが違えば `変更`、対応の無い変更後のノードは `追加`、対応の無い変更前のノードは消したノードである。
変えたノードは式の中まで比べ、演算子、リテラル、引数、呼び先の置き換えを言葉にする。
対応づかない書き換えは前後のコードを並べる。
差分の hunk は、その行を含む最小のノードに付ける。
呼び出し元には、下の変更の集計を上げる。

### 影響範囲

変更がどこに効くかは地図が計算する。

- 呼び先は TypeScript の型で解決する。interface のメンバーを通る呼び出しも追い、store や resolver の実装を変えると、そのメンバーの全呼び出し箇所に届く
- エンドポイントごとに、変更までの経路（開くフレームと決定の組み合わせ）と、その経路に要る機能を求める
- 外へ出る失敗が増えたり減ったりした関数は、その変化を示す
- hono（Express と Fastify はその写し）と Next.js の写しは別々に数える
- 型で呼び先を引けない呼び出しは「追えない」と明示する

### 変更メモと CI

何を変えたかは木の差分が、どこに効くかは地図が示し、変更メモ（[changes/](changes/README.md)）には意図と背景を書く。
地図のビルドは、変更メモの見出しが名前を挙げる関数が実在するかを確かめ、コードを変えた関数で節の無いものを「説明の無い変更」として PR コメントの先頭に一覧する。
CI（`.github/workflows/map-preview.yml` の地図のビルド）を落とすのは、エンドポイントに届く関数か、エンドポイントの処理本体に説明の節が無いときだけである。
本文の質は検査せず、自動要約を隣に並べる。

節の雛形は次のコマンドで作れる。
MAP_BASE からの差分で、まだ節の無い関数ごとに見出し（`## 名前 <!-- id -->`）と、自動要約と届く先の HTML コメントを書き、意図の欄を空けておく。

```bash
MAP_BASE=origin/main pnpm --filter @maronn-openid-connect/map changes:draft
```

## コードの Drawer

エンドポイントの見出しの「コードを見る」や、詳細と関数のページの「コードを見る」で、右からコードの Drawer を開く。
「表示するコード」で、エンドポイントのファイル全体、ステップの関数、そこから呼ぶ関数（core まで）を切り替える。
関数には JSDoc とオーバーロードを含め、元ファイルの行番号を表示する。
PR の地図で変えた関数は、「差分」と「変更後の全文」を切り替えられる。

TypeScript と TSX のハイライトは [Shiki](https://shiki.style/) でビルド時に生成する。
配色と背景は付属の `github-light` / `github-dark` テーマを使い、ページの明暗設定に従って切り替える。
ファイル全体を解析してから関数の範囲を表示するため、複数行のコメントや文字列の文脈を保つ。
差分の削除行は変更前、追加行と文脈行は変更後のファイル全体を解析した色で表示する。
ブラウザには Shiki を含めず、ハイライト済みのデータを必要なときだけ読み込む。

表示するのはリポジトリの全機能を含むソースで、Express と Fastify は生成元である Hono のソースを表示する。
閉じるボタン、Escape キー、Drawer の外側のクリックで閉じ、開いたボタンにフォーカスを戻す。

## スマートフォン

幅 900px 未満の画面では、アウトラインだけを表示する。
図、経路の差分、詳細は画面下のボタンからドロワーで開く。
図のドロワーは画面の幅いっぱいに開き、操作は一行にまとめる（拡大縮小はピンチで行い、縮尺の数値だけを残す）。
左上のメニューから、検索、フレームワーク・機能・エンドポイントの選択、画面の説明、よく使う選択、関数の呼び出し元を操作できる。

## データとビルド

React + Vite の静的ページで、Cloudflare Workers に静的アセットとして置く（`wrangler.jsonc`）。
ページは表示だけを受け持ち、解析は非公開のワークスペースパッケージ [`@maronn-openid-connect/map-analysis`](../../packages/map-analysis) がビルド時に行う。

1. CLI の `explain --format json` を全機能オンで 4 フレームワーク分まとめ、関数カタログを読む
2. 関数とエンドポイントの処理本体を TypeScript のコンパイラ API で読み、処理の流れの木にする。呼び先は型で解決する
3. MAP_BASE があれば、変更前のコードからも木を作り、木の差分、式の差分、影響範囲、変更メモの対応づけを求める
4. 次のファイルを `public/data/` に書く

- `map.json`：索引。フレームワーク、コマンド、機能、エンドポイントとステップ、関数カタログ（呼び先、呼び出し元、外へ出る失敗）、interface のメンバー、PR の変更の一覧。木は含まない
- `functions/<hash>.json`：フレーム一つ分。木、よく使う選択、PR の地図では変更前の木、ノードの差分、式の差分、hunk。フレームを開いたときに読む
- `sources/<hash>.json`：ハイライト済みのソース。Drawer を開いたときに読む
- `changes.md`：PR の変更の Markdown。PR のコメントがこれを引用する

関数の id はカタログと同じ `<root>:<module>#<name>`、hono のエンドポイントの処理本体は `endpoint:<id>` である。
解析パッケージのテストは、木から求めた呼び先が CLI のカタログの calls / calledBy と一致すること、本体の全行がどれかのノードに属することを確かめる。

ビルドの最後に `scripts/check-map.mjs` が地図の出力を検査し、次の数を出す。
名前の無い選択（exit ケース）と重複した名前、ノードに属さない行、PR が変えた行のうちノードに属さないもの、説明の無い変更である。
これは地図の出力に対する検査で、貢献者のコードの形には向けない。
図の検査（`src/lib/diagram.data.test.ts`）も同じ考えで、ビルドしたデータがあるときだけ走る（`map-preview.yml` では `build:map` の後のテスト）。
決定と終わりがどのフレームの図からも欠けないことと、幅に合わせて見出しが 11px に届くフレームが 9 割を下回らないことを確かめる。

`MAP_PR`、`MAP_PR_TITLE`、`MAP_PR_URL` は、ページに出す PR の番号、タイトル、URL である。

```bash
# ルートで: CLI と解析パッケージをビルドしてから地図をビルドする（dist/ に静的ページ）
pnpm run build:map

# このディレクトリで
pnpm run dev              # データを作って Vite の開発サーバー（http://127.0.0.1:3610）
MAP_BASE=origin/main pnpm run dev   # origin/main からの変更（コミットしていないものを含む）を載せた地図
pnpm run build            # データを作って dist/ にビルドし、地図の出力を検査する
pnpm run check            # public/data の地図の出力だけを検査する
pnpm run changes:draft    # MAP_BASE からの差分で変更メモの雛形を書く
pnpm run deploy           # ビルドして wrangler deploy（https://maronn-oidc-map.<subdomain>.workers.dev）
pnpm run deploy:preview   # ビルドして wrangler versions upload（プレビュー URL が出る。本番は変わらない）
pnpm test                 # ページの純粋な部分（トレース、決定、図、ハッシュ、変更の札、検索）のテスト
```

`wrangler deploy` は `CLOUDFLARE_API_TOKEN` と `CLOUDFLARE_ACCOUNT_ID`（または `wrangler login`）を使う。
Worker の名前は `wrangler.jsonc` の `name` で変える。

## PR ごとのプレビューと main のデプロイ

`.github/workflows/map-preview.yml` が、リポジトリのシークレット `CLOUDFLARE_API_TOKEN` と `CLOUDFLARE_ACCOUNT_ID` で次を行う。

- **PR**（opened / synchronize / reopened）：その PR のコードから地図をビルドし、同じ Worker の **Worker Preview** `pr-<番号>`（`wrangler preview --name pr-<番号>`）を作る・更新する。PR ごとに固定の URL を持ち、push のたびに同じ URL が新しくなる。URL と変更の表は PR のコメントに書く（push ごとに同じコメントを書き換える）。説明の無い変更で地図のビルドが落ちても、デプロイとコメントは行い、ジョブは失敗のままにする
- **PR を閉じた**：その Preview を `wrangler preview delete --name pr-<番号>` で消す
- **main への push**：`wrangler deploy` で本番（いまは `https://maronn-oidc-map.<subdomain>.workers.dev`）を更新する

Worker Previews はオープンベータ（wrangler 4.135 以降）なので、`wrangler preview` が失敗したときは `.github/scripts/map-preview.mjs` が PR ごとの Worker `maronn-oidc-map-pr-<番号>` へ `wrangler deploy` し、閉じたときにその Worker も消す。
どの場合も Actions の artifact（`oidc-provider-map`）にビルド結果が残り、`dist/` を静的に配信すれば同じ地図が見られる。

## 構成

- `src/lib/trace.ts`：トレースの状態（開いたフレーム、選んだ決定）、選んだ決定で走るノード、ノードへ至る決定、変更まで開くフレーム、アウトラインの行、失敗を捕まえる `catch`
- `src/lib/diagram.ts`：焦点のフレームの木をアウトラインと同じ畳み方で箱と矢印にし、選んだ道筋の箱、行、矢印を求める
- `src/lib/graph.ts`：Dagre による図の自動配置、箱の幅、見出しの折り返し
- `src/lib/camera.ts`：図を開く倍率と位置、選んだ箱が見える所までの移動
- `src/lib/hash.ts`：URL のハッシュ（`#hono--token/s4/s4.s2;d=s4.s1:true`、`#hono--fn--verifyClientSecret`、`#hono--changes`）
- `src/lib/changes.ts`：PR の変更の札、下の変更の集計、差分の行番号、変更メモの本文
- `src/lib/model.ts`：機能の絞り込み、`generate` のコマンドライン、関数に届くステップと呼び出し元、検索
- `src/lib/source.ts`, `src/components/CodeDrawer.tsx`：コードの選択肢とソースを読む Drawer
- `src/components/Trace.tsx`, `TraceView.tsx`, `SelectionBar.tsx`：アウトライン、決定のボタン、よく使う選択、図と詳細のタブ
- `src/components/`：ほかに、エンドポイントの画面、関数のページ、このPRの変更のページ、左の一覧、検索、メニュー
- `src/types.ts`：データの形（`@maronn-openid-connect/map-analysis/model` の再輸出）
- `scripts/build-data.mjs`, `scripts/check-map.mjs`, `scripts/draft-notes.mjs`：解析パッケージを呼ぶデータのビルド、地図の出力の検査、変更メモの雛形
- `changes/`：PR ごとの変更メモ（[書き方](changes/README.md)）
