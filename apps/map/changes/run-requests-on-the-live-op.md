# 地図のリクエストを、デプロイした OP（地図の OP）で動かし、実際に動いた順に読む

地図のフローでリクエストを実行すると、これまではページの Web Worker の中の OP（`packages/map-sandbox`）が、ビルド時に作った前提の写しの上で、止めた時計で動いていた。
これを、`apps/hono` のサーバーアプリ（`createServerApp`、全機能オン）を地図と一緒にデプロイした OP（`packages/live-op`、地図の OP）で動かすようにした。
Cloudflare Workers では地図の Worker が、読者ごとのワークスペースを一つの Durable Object にして OP を動かし、地図のページと同じオリジンで OP のパス（`/authorize`、`/login`、`/token` など）に答える。
ローカルでは Vite の開発サーバーとプレビューが、同じ OP を Node で動かす。

この変更は地図とその解析、地図の OP、テストカタログだけを変え、関数カタログの関数とエンドポイントの処理は変えていない。
`apps/hono` は、署名鍵を `OIDC_SIGNING_KEY_JWK` から読めるようにした（`settings.ts`。関数カタログの外）。

## 背景

地図の OP で動かしたリクエストの結果は、本物の OP と違うことがあった。

- リクエストごとに前提の写しから始まるので、使った認可コードを次のリクエストでまた使え、ログインした Cookie を持ち越せなかった。ログインや同意の画面へのリクエストは、読者が書くとトランザクションも Cookie も無く、いつも「認可リクエストが進行中でない」で終わった
- 時計が止まっていて、期限切れを確かめられなかった
- 通った道筋は、リクエスト全体の Istanbul の計数を行の規則で読んで求めていた。同じ関数を二度呼べば両方の側に数が付いて決まらず、リスト末尾の呼び出し（`return f()`）が失敗したかは読めず、`GET | POST /login` のようにハンドラーの組から作った根は読まなかった。決まらない分岐は仮の側（多くは成功する側）へ進むので、エラーを返したリクエストが成功の道筋で再生された

## 何を変えたか

- 地図の OP は、ワークスペースの状態（DB、機能のストア、署名鍵、時計）をリクエストの間で保つ。認可コードは一度引き換えると次は `invalid_grant` になり、ブラウザのタブで開いたログイン画面からの要求も同じワークスペースに届く（Cookie `map_workspace`）。時計は本物で、期限切れは「時計を進める」で確かめる
- OP は、Istanbul の計数が上がるたびにその場所（プローブ）を順に記録する（`packages/live-op/src/recorder.ts`）。地図はその順から、関数の呼び出しごとの計数を作り、同じ規則で読む（`packages/map-analysis/src/traced.ts`）。呼び出しが投げたかは、最後に動いたのが `throw` か、投げた呼び出しか、次のノードが動かずに止まった文（地図の外のコードが投げた）かで決める。根が動いていないリクエスト（405 など）は、そう示す
- 再生した道筋と、そのリクエストが実際に動かしたものが両方の向きで合うかを確かめる（`walkMismatches`：動いていない行を通らない、動いた呼び出しを飛ばさない、記録の側と違う側に進まない）。地図のビルドは全ケースのリクエストを OP で動かし、動いたフレームをすべて開いてこれを確かめる
- ケースの準備は、そのケースのリクエストに要るもの（認可コード、トークン、ログインのフォームの CSRF トークン、Cookie）を、OP へ本物のリクエストを送って得る。値はどれも OP が返したものである

## 残ること

- Next.js の OP は動かさない（Hono の OP で動かすのは今までと同じ）
- 仮の側は、規則でも呼び出しの記録でも決まらない形（三つ以上の項の `&&`、空の `catch`）にだけ残る。その道筋も、動いた行だけを通り、動いた呼び出しを飛ばさない
- ログインと同意の根（ハンドラーの組）には、失敗のほかに名前の付いた道筋が無いので、そのケースは道筋の一覧に載らない（再生はハンドラーの中まで正しく進む）
- デバイスと CIBA のトークンのエラーは、どれも引き換えの関数が投げ直す失敗として名前が付く
- 再帰と、同じフレームの非同期の呼び出しが交互に進む形は、呼び出しを分けきれない（今の OP のコードには無い）
