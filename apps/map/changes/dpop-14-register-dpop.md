# CLI の拡張機能に dpop を加え、--enable dpop で生成できるようにする（DPoP の段 14）

DPoP（RFC 9449）を生成 OP に入れる段の 14 個目で、段 12 と段 13 で足した DPoP の機能のディレクトリを、CLI の機能の一覧に `dpop`（拡張機能、既定は無効）として登録する。
これまでは一覧に無かったので `--enable dpop` は知らない機能として拒まれ、ディレクトリはどの生成にも入らなかった。後の段でエンドポイントに DPoP の処理を足すたびに、`--enable dpop` の生成物を CLI の組み合わせの型検査（`only-dpop`、`all` など）で確かめ、地図でもそのコードを `dpop` の機能として示すために、エンドポイントに手を入れる前のこの段で登録する。
機能の登録（`feature.ts`）がするのは三つだけである。DPoP の設定の既定値（`dpopConfigDefaults`）を `ProviderConfig` に重ねる、ディスカバリーで `dpop_signing_alg_values_supported` を返す（設定した alg のうち `jwk.ts` が署名を検証できるものだけ。RFC 9449 §5.1）、`cors` のフックで、クライアントが直接呼ぶエンドポイントの CORS に `DPoP` リクエストヘッダーを許し、`WWW-Authenticate` を読ませる（§4.1 / §7.1）。
DPoP proof の検査はまだどのエンドポイントからも呼ばないので、`--enable dpop` で生成した OP もトークンはすべて Bearer のままで、ディスカバリーの項目と CORS のヘッダーのほかは、`dpop` の無い OP と同じに答える。`dpop` を有効にしない生成物は何も変わらない（サンプルはマニフェストに `"dpop": false` が増えるだけ）。
このリポジトリの apps はすべての機能を有効にしているので、apps のディスカバリーと CORS のテストの期待もこの段で変えた。
CLI では、拡張機能の定義（これまでは「上流の ID プロバイダーを package で取り込むもの」）を「実験的ではない任意の機能」に改め、生成の後に出す拡張機能の案内を、有効にした拡張機能ごとに出すようにした（これまでは拡張機能が google-login だけだったので、どの拡張機能を有効にしてもその案内を出していた）。
